# フロントエンド実装方針：プラン購入フロー

このドキュメントでは、ユーザがプランを購入する際のフロントエンド側の実装方針を説明します。

## 全体の流れ

ユーザがプランを選択してから購入が完了するまでの流れは、以下の5つのステップに分かれます。

1. **プラン一覧を表示する**
2. **ユーザがプランを選択する**
3. **支払いフォームを表示する**
4. **ユーザが支払い情報を入力する**
5. **支払い完了後の処理を行う**

それぞれのステップについて、詳しく説明します。

---

## ステップ1: プラン一覧を表示する

### 何をするのか

ユーザが選択できるプランの一覧を画面に表示します。例えば「Freeプラン」「Standardプラン」「Premiumプラン」などが表示されます。

### フロントエンドでやること

バックエンドAPIに対して「利用可能なプラン一覧をください」というリクエストを送ります。APIから受け取ったプランの情報を画面に表示します。

### 必要なバックエンドAPI

- **エンドポイント**: `GET /api/plans?platform=web`
- **目的**: Web版で利用可能なプラン（Stripe決済）の一覧を取得する
- **重要**: `platform`パラメータは必須です
  - Web版では常に `platform=web` を指定
  - iOS版アプリでは `platform=ios` を指定
  - Android版アプリでは `platform=android` を指定
- **レスポンスに含まれる情報**:
  - platform: リクエストしたプラットフォーム（"web"）
  - plans: プランの配列
    - プランID
    - プラン名（例: "Standardプラン"）
    - 料金（例: "月額1,000円"）
    - プランに含まれる機能の説明（例: "モデルAとモデルBへの無制限アクセス"）
    - platformProductId（Stripe価格ID）

### APIの呼び出し例

```javascript
// React/TypeScriptでの実装例
const fetchPlans = async () => {
  try {
    const response = await fetch('/api/plans?platform=web', {
      method: 'GET',
      headers: {
        'Authorization': `Bearer ${authToken}`,
        'Content-Type': 'application/json',
      },
    });

    if (!response.ok) {
      if (response.status === 400) {
        // platformパラメータエラーの処理
        const error = await response.json();
        console.error('パラメータエラー:', error.error.details);
      }
      throw new Error('プラン取得に失敗しました');
    }

    const data = await response.json();
    // data.platform が "web" であることを確認
    // data.plans にプラン配列が格納されている
    setPlans(data.plans);
  } catch (error) {
    console.error('プラン取得エラー:', error);
  }
};
```

### 表示する情報

各プランについて、以下の情報をユーザにわかりやすく表示します。

- プラン名
- 料金
- 利用できる機能の一覧
- 利用回数制限がある場合は、その内容
- 選択ボタン

---

## ステップ2: ユーザがプランを選択する

### 何をするのか

ユーザが表示されたプランの中から、購入したいプランを一つ選びます。選択ボタンをクリックすると、次のステップに進みます。

### フロントエンドでやること

1. ユーザがどのプランを選択したかを記録します
2. 選択したプランのIDと、現在ログインしているユーザのIDを用意します
3. バックエンドAPIに対して「このユーザがこのプランを購入したいので、支払いの準備をしてください」というリクエストを送ります

### 必要なバックエンドAPI

- **エンドポイント**: `POST /api/subscriptions/checkout-session`
- **目的**: Stripe Checkout Sessionを作成し、支払いフォームを開くための情報を取得する
- **リクエストに含める情報**:
  - ユーザID（ログイン中のユーザ）
  - プランID（選択されたプラン）
- **レスポンスに含まれる情報**:
  - client_secret（Stripeの支払いフォームを開くための秘密の文字列）

### このステップでの注意点

このAPIを呼び出した時点では、まだ支払いは発生していません。支払いフォームを開くための準備をしているだけです。

---

## ステップ3: 支払いフォームを表示する

### 何をするのか

Stripeが提供する支払いフォームをアプリの画面内に埋め込んで表示します。このフォームの中で、ユーザがクレジットカード情報を入力できるようにします。

### フロントエンドでやること

1. Stripe公式のReactコンポーネント（`EmbeddedCheckout`）を使用します
2. 前のステップで取得した`client_secret`を、このコンポーネントに渡します
3. 支払いフォームをモーダル（画面の上に重ねて表示されるウィンドウ）の中に表示します

### 技術的な詳細

Stripeのドキュメント（https://docs.stripe.com/payments/accept-a-payment?platform=web&ui=embedded-components&client=react）に従って、以下のような実装を行います。

```javascript
import { EmbeddedCheckout } from '@stripe/react-stripe-js';

// clientSecretは前のステップで取得した値
<EmbeddedCheckout clientSecret={clientSecret} />;
```

### return_urlの設定について

Checkout Sessionを作成する際、バックエンド側で`return_url`というものを設定します。これは「支払いが完了した後、ユーザをどのページに戻すか」を指定するURLです。

例えば、`https://yourapp.com/billing/complete?session_id={CHECKOUT_SESSION_ID}`のようなURLを設定します。

`{CHECKOUT_SESSION_ID}`の部分は、Stripeが自動的に実際のセッションIDに置き換えてくれます。

---

## ステップ4: ユーザが支払い情報を入力する

### 何をするのか

ユーザが支払いフォームの中にクレジットカード情報を入力し、支払いボタンをクリックします。

### フロントエンドでやること

このステップでは、フロントエンド側で特別な処理を行う必要はありません。Stripeのフォームが自動的に以下の処理を行います。

- クレジットカード情報のバリデーション（正しい形式かどうかのチェック）
- Stripeのサーバーへの送信
- 決済処理
- 完了画面の表示

### ユーザがキャンセルした場合

ユーザが支払いフォームの中で「キャンセル」や「戻る」ボタンを押した場合、以下のような動作になります。

- 支払いフォームが閉じる、または初期状態に戻る
- `return_url`には遷移しない（支払いが完了していないため）

フロントエンド側では、以下の対応を行います。

1. モーダルを閉じるボタンを用意する
2. モーダルが閉じられたら、プラン一覧画面に戻る
3. バックエンド側では何もしない（Checkout Sessionは自動的に有効期限切れになるので、放置してOK）

---

## ステップ5: 支払い完了後の処理を行う

支払い完了後の処理は、2段階で行われます。

### 第1段階: 即座のプラン有効化（return_url経由）

#### 何が起こるのか

支払いが完了すると、Stripeの支払いフォームの中に完了画面が表示されます。その後、自動的に`return_url`で指定したページに遷移します。

例: `https://yourapp.com/billing/complete?session_id=cs_test_xxx`

#### フロントエンドでやること

このフローでは、ユーザが支払い完了後に即座にプランの機能を使えるようにするため、3つのステップを順番に実行します。

**ステップ1: セッション状態を確認する**

1. `/billing/complete`というページ（またはルート）を用意します
2. URLのクエリパラメータから`session_id`を取得します
3. バックエンドAPIに対して「このセッションIDの支払いはどうなっていますか？」と問い合わせます

**ステップ2: 支払いが成功していたら、即座にプランをアクティベートする**

4. セッション状態確認APIの結果が「成功」だった場合、すぐに次のAPIを呼び出します
5. バックエンドAPIに対して「このセッションに基づいて、プランを今すぐ有効化してください」とリクエストします
6. このAPIが成功すると、データベース上でプランが即座に有効になります

**ステップ3: 結果に応じた画面を表示する**

7. アクティベーションAPIからの応答に応じて、適切な画面を表示します

#### 必要なバックエンドAPI（第1段階用）

**API 1: セッション状態確認API**

- **エンドポイント**: `GET /api/subscriptions/checkout-session/{session_id}/status`
- **目的**: 指定されたCheckout Sessionの状態を確認する
- **レスポンスに含まれる情報**:
  - 支払いの状態（complete / incomplete / expired）
  - プラン名
  - 支払い金額
  - 次回請求日

**API 2: プランアクティベーションAPI**

- **エンドポイント**: `POST /api/subscriptions/activate-from-session`
- **目的**: 支払い成功したセッションに基づいて、即座にプランを有効化する
- **リクエストボディ**:
  ```json
  {
    "session_id": "cs_test_xxx"
  }
  ```
- **レスポンス**:
  ```json
  {
    "success": true,
    "plan_id": "plan_xxx",
    "plan_name": "Standardプラン",
    "activated_at": "2025-11-19T12:34:56Z",
    "next_billing_date": "2025-12-19"
  }
  ```
- **役割**:
  - Stripeに対してセッション情報を検証する
  - セッションに紐づくユーザIDとリクエスト送信者が一致するか確認する
  - データベースにサブスクリプション情報を記録する
  - ユーザにプランを適用する
  - 権限を付与する
  - このセッションIDを「処理済み」としてマークする（冪等性の確保）

#### 処理の流れ（詳細）

```
1. ユーザがreturn_urlに到着
   ↓
2. フロントエンド: セッション状態確認APIを呼び出す
   ↓
3. バックエンド: Stripeに状態を問い合わせて返す
   ↓
4. フロントエンド: status が "complete" かチェック
   ↓
5-a. completeの場合:
     フロントエンド: プランアクティベーションAPIを呼び出す
     ↓
     バックエンド: 以下を順番に実行
       - Stripeでセッション情報を再検証
       - セッションIDが既に処理済みかチェック（冪等性）
       - 未処理の場合のみ、以下を実行:
         * サブスクリプション情報をDBに記録
         * プランをユーザに適用
         * 権限を付与
         * セッションIDを処理済みとしてマーク
       - 既に処理済みの場合は、既存の情報を返す
     ↓
     フロントエンド: 成功画面を表示

5-b. complete以外の場合:
     フロントエンド: エラー画面を表示
```

#### 画面表示のパターン

APIからの応答に応じて、以下のような画面を表示します。

**パターン1: 支払い成功＆アクティベーション成功の場合**

- 「課金が完了しました」というメッセージを表示
- 「プランが有効になりました。今すぐご利用いただけます」という補足を追加
- 契約したプラン名と次回請求日を表示
- 「マイページへ」ボタンまたは「プランの機能を使ってみる」ボタンを表示

**パターン2: 支払い失敗の場合**

- 「支払いに失敗しました」というメッセージを表示
- 失敗の理由（カードが無効、残高不足など）を表示
- 「もう一度試す」ボタンを表示

**パターン3: アクティベーションAPIの呼び出しに失敗した場合**

- 「支払いは完了しましたが、プランの有効化に時間がかかっています」というメッセージを表示
- 「数分以内に有効化されます。しばらくお待ちください」と案内
- 「マイページへ」ボタンを表示
- ※この場合、後述のWebhookが自動的にアクティベーションを完了します

**パターン4: 処理中の場合**

- 「支払い処理を確認中です」というメッセージを表示
- 数秒待ってから再度セッション状態確認APIを呼び出す（ポーリング）

#### 重要な設計ポイント

**ポイント1: 冪等性の確保**

同じ`session_id`で複数回アクティベーションAPIが呼ばれても安全であることが重要です。バックエンド側では、以下のように実装します。

- セッションIDをキーにして、既に処理済みかをチェック
- 処理済みの場合は、新しい処理を行わず、既存の結果を返す
- これにより、ユーザがページをリロードしても、重複してプランが適用されることを防ぎます

**ポイント2: Webhookとの関係**

このアクティベーションAPIが成功した場合、後でWebhookも同じセッションIDに対して処理を試みます。しかし、冪等性チェックにより、Webhookは「既に処理済み」と判断して何もしません。

逆に、アクティベーションAPIが失敗した場合、Webhookが確実にアクティベーションを完了させます。これにより、どちらか一方が失敗しても、最終的には必ずプランが有効化されます。

### 第2段階: 確実性を保証するフォールバック処理（Webhook）

#### 何が起こるのか

第1段階のアクティベーションAPIは、ユーザが支払い完了後に即座にプランを使えるようにするための処理です。しかし、以下のような理由で失敗する可能性があります。

- ユーザがreturn_urlに到達する前にブラウザを閉じてしまった
- ネットワークエラーでアクティベーションAPIの呼び出しに失敗した
- アプリがクラッシュした

こうした場合でも、プランが確実に有効化されるようにするため、Stripeは別の経路で「支払いが確定しました」という通知をバックエンドに送ります。これをWebhookと呼びます。

Webhookは以下のようなイベントを送信します。

- `checkout.session.completed`（支払いが完了した）
- `invoice.payment_succeeded`（請求の支払いが成功した）
- `customer.subscription.created`（サブスクリプションが作成された）

#### Webhookの役割

Webhookは、第1段階のアクティベーションAPIの「フォールバック（予備）」として機能します。

- **アクティベーションAPIが成功した場合**: Webhookは冪等性チェックにより「既に処理済み」と判断し、何もしません
- **アクティベーションAPIが失敗した場合**: Webhookが自動的にアクティベーション処理を実行します

これにより、どちらか一方が失敗しても、最終的には必ずプランが有効化されることが保証されます。

#### フロントエンドでやること

フロントエンド側では、Webhookに関する処理を行う必要はありません。これは完全にバックエンド側の責任です。

ただし、アクティベーションAPIが失敗した場合（パターン3）の画面では、「Webhookによって数分以内に自動的にアクティベーションが完了する」という前提で、ユーザに適切なメッセージを表示します。

#### バックエンド側で何が起こるか（参考情報）

Webhookを受信したバックエンドは、以下の処理を行います。

1. イベントが本当にStripeから送られてきたものかを署名検証で確認する
2. セッションIDが既に処理済みかをチェックする（冪等性）
3. 未処理の場合のみ、以下を実行する:
   - ユーザのプラン情報を「有料会員・プランX」に更新
   - 次回更新日時を保存
   - サブスクリプションIDを保存
   - 権限を付与
   - セッションIDを処理済みとしてマーク
4. 既に処理済みの場合は、何もせずに成功応答を返す

この冪等性により、return_url経由とWebhook経由の両方が実行されても、処理が重複することはありません。

## ユーザ体験の時間軸

支払い完了後、ユーザが実際にプランの機能を使えるようになるまでの時間軸を説明します。即座のアクティベーション方式を採用することで、ほとんどの場合、ユーザは数秒以内にプランを利用開始できます。

### 通常のケース: return_url経由での即座のアクティベーション（数秒以内）

**タイミング1: 支払い完了とreturn_urlへの遷移（1〜2秒）**

- ユーザが支払いボタンをクリックする
- Stripeが決済処理を実行する
- 完了画面が表示され、return_urlに遷移する

**タイミング2: セッション状態確認とアクティベーション（1〜2秒）**

- フロントエンドがセッション状態確認APIを呼び出す
- 支払いが成功していることを確認する
- すぐにアクティベーションAPIを呼び出す
- バックエンドがプランを有効化する

**タイミング3: ユーザへの通知と即座の利用開始（即座）**

- 「プランが有効になりました。今すぐご利用いただけます」という画面が表示される
- ユーザがすぐにプランの機能を利用できる

**合計所要時間**: 支払いボタンのクリックから2〜4秒程度

### フォールバックケース: Webhook経由でのアクティベーション（数秒〜数分）

return_url経由のアクティベーションが失敗した場合（ブラウザを閉じた、ネットワークエラーなど）の時間軸です。

**タイミング1: 支払い完了（1〜2秒）**

- ユーザが支払いボタンをクリックする
- Stripeが決済処理を実行する
- この時点でユーザがブラウザを閉じてしまう、またはネットワークエラーが発生する

**タイミング2: Webhookの送信と受信（数秒〜数十秒後）**

- Stripeがバックエンドに対してWebhookを送信する
- バックエンドがWebhookを受信し、署名を検証する

**タイミング3: Webhookによるアクティベーション（即座）**

- セッションIDが未処理であることを確認する
- プランを有効化する
- ユーザにメール通知を送る（「プランが有効になりました」）

**タイミング4: ユーザがアプリに戻って利用開始**

- ユーザが後でアプリにログインする
- プランが有効になっていることを確認できる
- 機能を利用開始できる

**合計所要時間**: 支払い完了から数秒〜1分程度（ユーザがアプリに戻るタイミングは除く）

### 設計上の利点

**即座の利用開始**

従来の「Webhookのみ」の方式では、ユーザは数秒〜数十秒待つ必要がありました。しかし、return_url経由の即座のアクティベーションにより、ほとんどのユーザは支払い直後からプランを利用できます。

**確実性の保証**

return_url経由が失敗しても、Webhookが確実にアクティベーションを完了させます。どちらか一方が成功すれば良いという冗長構成により、ほぼ100%の成功率を実現できます。

**処理の重複がない**

冪等性チェックにより、return_url経由とWebhook経由の両方が実行されても、処理が重複することはありません。データベースに二重に記録されたり、料金が二重に請求されたりする心配はありません。

## 状態管理の実装方針

フロントエンド側で管理する必要がある状態を整理します。

### 管理する状態

1. **選択中のプラン**
   - プランID
   - プラン名
   - 料金

2. **支払いフローの進行状況**
   - プラン選択中
   - Checkout Session作成中
   - 支払いフォーム表示中
   - 支払い処理中
   - 支払い完了
   - エラー発生

3. **Checkout Session情報**
   - session_id
   - client_secret

4. **エラー情報**
   - エラーメッセージ
   - エラーの種類

### 状態管理ライブラリの選択

ReactのContext APIやZustand、Reduxなどの状態管理ライブラリを使用して、これらの状態を一元管理します。

### ページ遷移との関係

支払いフローは複数のページ（またはステップ）にまたがるため、状態をセッションストレージに保存しておくことで、ページをリロードしても状態を復元できるようにします。

## エラーハンドリング

想定されるエラーパターンと、その対処方法を説明します。

### エラー1: Checkout Session作成APIの呼び出しに失敗

**原因の例**:

- ネットワークエラー
- ユーザの認証が切れている
- 選択されたプランが既に利用不可になっている

**対処方法**:

- エラーメッセージを表示する
- 「もう一度試す」ボタンを表示する
- ネットワークエラーの場合は自動リトライを行う（最大3回まで）

### エラー2: 支払い処理に失敗

**原因の例**:

- クレジットカードが無効
- 残高不足
- カードの利用制限

**対処方法**:

- Stripeのフォーム内で自動的にエラーが表示される
- ユーザが別のカードを試せるようにする
- または、プラン選択画面に戻れるボタンを表示する

### エラー3: セッション状態確認APIの呼び出しに失敗

**原因の例**:

- ネットワークエラー
- session_idが無効

**対処方法**:

- 「確認中です」というメッセージを表示する
- 数秒後に自動的に再試行する（最大5回まで）
- それでも失敗する場合は、「購入履歴を確認してください」と案内する

### エラー4: アクティベーションAPIの呼び出しに失敗

**原因の例**:

- ネットワークエラー
- バックエンドサーバーの一時的な障害
- タイムアウト

**対処方法**:

**自動リトライ（推奨）**:
- エラーが発生したら、即座に1回だけ自動リトライを試みる
- リトライも失敗した場合は、パターン3の画面（「支払いは完了しましたが、プランの有効化に時間がかかっています」）を表示する
- Webhookが自動的にアクティベーションを完了させるため、ユーザに特別な操作を求めない

**手動リトライ（オプション）**:
- 「もう一度試す」ボタンを表示して、ユーザが手動でアクティベーションAPIを再実行できるようにする
- ただし、通常はWebhookが自動的に処理するため、手動リトライは不要

**重要**: このエラーが発生しても、Webhookが確実にプランを有効化するため、ユーザに過度な不安を与えないようにすることが大切です。

## モーダルとページ遷移の設計

支払いフローをどのように画面に表示するかの方針を説明します。

### 推奨パターン: モーダルを使用

支払いフォームはモーダル（画面の上に重ねて表示されるウィンドウ）で表示することを推奨します。

**理由**:

- ユーザが今いるページから移動する必要がない
- キャンセルした場合、モーダルを閉じるだけで元のページに戻れる
- 支払いプロセスが「一時的な操作」であることが視覚的にわかりやすい

**実装方法**:

1. プラン選択ボタンをクリックすると、モーダルが開く
2. モーダル内にStripeの`EmbeddedCheckout`コンポーネントを表示
3. 支払い完了後、return_urlに遷移（この際、モーダルは自動的に閉じる）

### 代替パターン: 専用ページに遷移

支払いフォームを専用の独立したページで表示することもできます。

**利点**:

- URLが変わるので、ブラウザの「戻る」ボタンが使える
- ページ全体を支払いに集中させられる

**欠点**:

- ページ遷移の回数が増える
- キャンセル時の処理が複雑になる

## セキュリティの考慮事項

フロントエンド実装で注意すべきセキュリティの観点を説明します。

### 1. client_secretの扱い

`client_secret`は機密情報ではありませんが、適切に扱う必要があります。

**やるべきこと**:

- APIレスポンスから受け取った`client_secret`を、そのままStripeコンポーネントに渡す
- メモリ上でのみ保持し、ローカルストレージには保存しない

**やってはいけないこと**:

- `client_secret`をURLパラメータに含める
- `client_secret`を他のユーザと共有できる形で保存する

### 2. ユーザ認証の確認

支払いフローを開始する前に、必ずユーザがログインしていることを確認します。

**実装方法**:

- プラン選択ボタンをクリックした際、認証トークンが有効かチェック
- 認証が切れている場合は、ログイン画面にリダイレクト
- ログイン後、元のプラン選択画面に戻す

### 3. session_idの検証

return_urlで受け取った`session_id`が、本当に現在のユーザのものかをバックエンド側で検証します。

**フロントエンド側でやること**:

- URLから取得した`session_id`を、そのままAPIに渡す
- APIが「このセッションはあなたのものではありません」というエラーを返したら、適切なエラーメッセージを表示

## 必要なバックエンドAPIの一覧

フロントエンド実装に必要なバックエンドAPIをまとめます。

### 1. プラン一覧取得API

- **エンドポイント**: `GET /api/plans`
- **認証**: 必要
- **役割**: 利用可能なプラン一覧を返す

### 2. Checkout Session作成API

- **エンドポイント**: `POST /api/subscriptions/checkout-session`
- **認証**: 必要
- **リクエストボディ**:
  ```json
  {
    "plan_id": "plan_xxx"
  }
  ```
- **レスポンス**:
  ```json
  {
    "client_secret": "cs_test_xxx"
  }
  ```
- **役割**: Stripe Checkout Sessionを作成し、client_secretを返す

### 3. セッション状態確認API

- **エンドポイント**: `GET /api/subscriptions/checkout-session/{session_id}/status`
- **認証**: 必要
- **レスポンス**:
  ```json
  {
    "status": "complete",
    "plan_name": "Standardプラン",
    "amount": 1000,
    "next_billing_date": "2025-12-19"
  }
  ```
- **役割**: Checkout Sessionの現在の状態を返す

### 4. プランアクティベーションAPI（新規追加）

- **エンドポイント**: `POST /api/subscriptions/activate-from-session`
- **認証**: 必要
- **リクエストボディ**:
  ```json
  {
    "session_id": "cs_test_xxx"
  }
  ```
- **成功レスポンス**:
  ```json
  {
    "success": true,
    "plan_id": "plan_xxx",
    "plan_name": "Standardプラン",
    "activated_at": "2025-11-19T12:34:56Z",
    "next_billing_date": "2025-12-19"
  }
  ```
- **エラーレスポンス例**:
  ```json
  {
    "success": false,
    "error": "session_not_found",
    "message": "指定されたセッションが見つかりません"
  }
  ```
- **役割**: 支払い成功したセッションに基づいて、即座にプランを有効化する
- **重要な機能**:
  - Stripeに対してセッション情報を検証する
  - セッションに紐づくユーザIDとリクエスト送信者が一致するか確認する
  - セッションIDが既に処理済みかチェックする（冪等性）
  - 未処理の場合のみ、以下を実行:
    - データベースにサブスクリプション情報を記録する
    - ユーザにプランを適用する
    - 権限を付与する
    - セッションIDを処理済みとしてマークする
  - 既に処理済みの場合は、既存の情報を返す（重複処理しない）

### 5. 現在のプラン情報取得API

- **エンドポイント**: `GET /api/subscriptions/current`
- **認証**: 必要
- **レスポンス**:
  ```json
  {
    "plan_id": "plan_xxx",
    "plan_name": "Standardプラン",
    "status": "active",
    "next_billing_date": "2025-12-19",
    "cancel_at_period_end": false
  }
  ```
- **役割**: 現在ログイン中のユーザのプラン情報を返す

## まとめ

フロントエンド側で実装する主な処理は以下の通りです。

1. バックエンドAPIからプラン一覧を取得して表示する
2. ユーザがプランを選択したら、Checkout Session作成APIを呼び出す
3. 取得した`client_secret`を使って、Stripeの支払いフォームを表示する
4. 支払い完了後、return_urlに遷移する
5. **セッション状態確認APIで支払いが成功したことを確認する**
6. **支払い成功を確認したら、即座にアクティベーションAPIを呼び出してプランを有効化する**
7. アクティベーション成功後、「プランが有効になりました。今すぐご利用いただけます」と表示する
8. エラーが発生した場合は、適切なエラーメッセージを表示し、必要に応じてリトライを促す

### この設計の重要なポイント

**即座の利用開始**

return_url経由でアクティベーションAPIを呼び出すことで、ユーザは支払い完了後、数秒以内にプランを利用開始できます。従来の「Webhookを待つ」方式と比べて、大幅にユーザ体験が向上します。

**確実性の保証**

return_url経由のアクティベーションが失敗しても、Webhookが自動的にフォールバックとして機能します。どちらか一方が成功すれば良いという冗長構成により、ほぼ100%の成功率を実現できます。

**冪等性による安全性**

バックエンド側で冪等性を確保することで、return_url経由とWebhook経由の両方が実行されても、処理が重複することはありません。ユーザがページをリロードしても、安全に動作します。

**2段階処理の理解**

「ユーザ体験としての即座のアクティベーション（return_url）」と「確実性を保証するフォールバック（Webhook）」の2段階があることを理解することが重要です。この設計により、速度と信頼性の両方を実現しています。

バックエンド側の実装（Webhook処理、冪等性チェック、データベース更新など）については、別の責務が担当するため、フロントエンド側では「必要なAPIを呼び出す」という形で連携します。
