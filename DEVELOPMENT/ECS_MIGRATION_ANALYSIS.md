## 📋 エグゼクティブサマリー

### 結論

**条件付きで実現可能 - ハイブリッドアプローチを推奨**

現在のLambdaベースのサーバーレスアーキテクチャをECS（Elastic Container Service）に移行することは技術的に実現可能です。ただし、**トラフィック量**と**チームのスキルセット**により、移行の適否が大きく変わります。

### 主要な推奨事項

1. **現在のトラフィックが月間1,000万リクエスト未満**: Lambda維持を推奨（コスト面で有利）
2. **現在のトラフィックが月間1,000万〜1億リクエスト**: ハイブリッドアプローチを検討
3. **現在のトラフィックが月間1億リクエスト以上**: ECS移行を強く推奨（年間約$9,000節約）

### コールドスタート分析

- Bedrock API呼び出し: +1-3秒（初回リクエスト）

**発生頻度**:
- **高トラフィックエンドポイント**（chat、predict）: コールドスタート稀

- REST API + Cognito Authorizer
- Lambda Proxy統合
- リクエスト/レスポンスモデル
- 29秒タイムアウト（API Gateway制限）

**非同期パターン**:
- SQSキュー（PPTX生成）
- WebSocket API（Bedrock Chat - テナント専用）
- EventBridge Pipes（RAG埋め込み）
- Step Functions（Kendraインデックス管理）

**重要な観察**: 関数の約60%は同期HTTP API（ECSに適している）、約40%は非同期/イベント駆動型（Lambdaに適している）

## 技術的実現可能性

### アーキテクチャ設計

#### 推奨フレームワーク: Fastify

**選定理由**:
- 高パフォーマンス（40,000 req/s vs Express 15,000 req/s）
- TypeScript優先設計
- 組み込みスキーマバリデーション
- ストリーミングサポート（Bedrock用）
- 軽量（コスト最適化ECSに最適）

### 認証戦略

#### 現在（Lambda）
```typescript
// API GatewayがCognito AuthorizerでJWTを検証
// LambdaはEvent経由でクレームを受け取る
export const handler = async (event: APIGatewayProxyEvent) => {
  const tenantId = getTenantId(event);
  const dynamodb = await getTenantDynamoDBDocument(event);
  // ...
};
```

#### 移行後（ECS/Fastify）
```typescript
// ミドルウェアが各リクエストでJWTを検証
import { CognitoJwtVerifier } from 'aws-jwt-verify';

const verifier = CognitoJwtVerifier.create({
  userPoolId: process.env.USER_POOL_ID!,
  clientId: process.env.USER_POOL_CLIENT_ID!,
});

fastify.addHook('preHandler', async (request, reply) => {
  const token = request.headers.authorization?.replace('Bearer ', '');
  const payload = await verifier.verify(token); // JWKSキャッシュあり
  request.cognitoPayload = payload;
});
```

**主な変更点**:
- アプリケーションレベルのJWT検証（API Gateway Authorizer不要）
- トークン検証がキャッシュされる（1時間）
- パフォーマンスオーバーヘッド: 約5ms/リクエスト

### テナントコンテキスト管理

**重要**: リポジトリパターンによりテナントコンテキスト抽出が抽象化されている

```typescript
// packages/cdk/lambda/repository/common.ts（ECSでも動作！）
export async function getTenantDynamoDBDocument(
  event: APIGatewayProxyEvent | FastifyRequest // 適応可能
): Promise<DynamoDBDocumentClient> {
  const tenantId = getTenantId(event);
  // テナントIDに応じて適切なテーブルを選択
  return createTenantDynamoDBClient(tenantId);
}
```

**必要な適応**:
- `getTenantId()` がFastify Request objectを受け入れるよう修正
- `request.cognitoPayload` からクレームを抽出
- その他のコード（DynamoDBクライアント、テーブル名、IAMロール）は同一

### コネクションプーリング

**ECSの大きな利点**: Lambdaはインボケーションごとに新しいSDKクライアントを作成するが、ECSはリクエスト間でクライアントを再利用

```typescript
// コンテナごとに1回初期化（リクエストごとではない）
const dynamoDBClient = new DynamoDBClient({
  requestHandler: new NodeHttpHandler({
    connectionTimeout: 3000,
    socketTimeout: 3000,
    httpsAgent: new Agent({
      maxSockets: 50,      // コネクション再利用
      keepAlive: true,
    }),
  }),
});
```

**パフォーマンス影響**:
- **Lambda**: クライアント作成（~50ms）+ API呼び出し（~200ms）= 250ms
- **ECS**: API呼び出し（~150ms、ウォーム接続のため）= 150ms
- **40%のレイテンシ削減**（ウォームリクエスト）

### 非同期処理戦略

**重要な決定**: 非同期ワークロードはLambdaに残す

#### Lambdaに残すべきユースケース

1. **PPTXジェネレーションワーカー**（SQSトリガー）
   - 理由: 予測不可能なスパイク、5-10分実行、Lambdaの弾力性が有利
   - コスト: 1,000インボケーションあたり$0.20

2. **ビデオコピージョブ**（Lambda→Lambda呼び出し）
   - 理由: 低頻度、長時間実行（最大15分）
   - コスト: 最小（スケールしても月額約$0.50）

3. **RAG埋め込みパイプライン**（EventBridge Pipes → Step Functions）
   - 理由: すでにStep Functionsでオーケストレーション済み、S3トリガー
   - そのまま維持: ECS移行のメリットなし

4. **Tenant Bedrock Chat WebSocket**（Python Docker Lambda）
   - 理由: WebSocket接続には永続的な状態が必要
   - そのまま維持: ECS WebSocketサポートは複雑で高コスト

#### ECSに移行すべきユースケース
- すべての同期HTTP API（chat、predict、admin、image、video、file、shareなど）
- 合計: 約60個のLambda関数 → 1つのECSサービスに統合

### コード変更の規模

**影響の少ない変更（コードベースの約20%）**:
- リポジトリ層: 最小限（リクエストコンテキストのアダプター関数）
- ビジネスロジック: 変更なし
- データベースアクセス: 変更なし
- AWS SDK使用: 変更なし

**新規作成が必要なコード**:
- Fastifyアプリケーションセットアップ: 約500行
- ルート登録: 約1,000行（主にLambdaハンドラーのマッピング）
- ミドルウェア（認証、ロギング、エラーハンドリング）: 約300行
- Dockerfile: 約50行
- CDK ECSコンストラクト: 約800行

**推定変更合計**:
- 新規コード: 約2,650行
- 修正コード: 約500行（リポジトリアダプター）
- 削除コード: 約8,000行（移行したLambda関数のCDKコンストラクト）

### 移行例: Chat API

#### 移行前（Lambda）

```typescript
// Lambda handler (packages/cdk/lambda/createChat.ts)
export const handler = async (event: APIGatewayProxyEvent) => {
  const userId = event.requestContext.authorizer?.claims.sub;
  const dynamodb = await getTenantDynamoDBDocument(event);
  const tableName = getTableName(event);
  const body = JSON.parse(event.body || '{}');

  const chat = await chatRepository.createChat(dynamodb, tableName, {
    userId,
    title: body.title,
  });

  return {
    statusCode: 200,
    body: JSON.stringify(chat),
  };
};
```

#### 移行後（ECS/Fastify）

```typescript
// Fastify route (ecs/routes/chats.ts)
export async function registerChatRoutes(fastify: FastifyInstance) {
  fastify.post('/chats', async (request, reply) => {
    const userId = request.cognitoPayload.sub;
    const dynamodb = await getTenantDynamoDBDocument(request);
    const tableName = getTableName(request);
    const body = request.body as { title: string };

    // ビジネスロジックは100%再利用！
    const chat = await chatRepository.createChat(dynamodb, tableName, {
      userId,
      title: body.title,
    });

    return chat; // Fastifyが自動的にJSONシリアライズ
  });
}
```

**主な観察事項**:
- ビジネスロジック（`chatRepository.createChat`）は100%再利用
- 主な変更: リクエスト/レスポンスフォーマットの適応
- エラーハンドリング: FastifyエラーハンドラーでLambdaのtry-catchを統合

## コスト比較

### コスト分析の前提

**Lambdaの課金項目**:
1. コンピュート: GB秒あたり$0.0000166667
2. リクエスト: 100万リクエストあたり$0.20
3. API Gateway: 100万リクエストあたり$3.50

**ECSの課金項目**:
1. Fargate vCPU: vCPU時間あたり$0.04048
2. Fargate メモリ: GB時間あたり$0.004445
3. ALB: 時間あたり$0.0225 + LCUあたり$0.008
4. データ転送: GBあたり$0.09（アウトバウンド）

### シナリオ1: 低トラフィック（月間100万リクエスト）

#### Lambda
- コンピュート: (1M × 2秒 × 0.256GB - 40万 free tier) × $0.0000166667 = $1.87
- リクエスト: (1M - 1M free tier) = $0
- API Gateway: 1M × $3.50/M = $3.50
- **Lambda合計: $5.37/月**

#### ECS
- Fargate vCPU: 2 tasks × 0.5 vCPU × 730h × $0.04048 = $29.55
- Fargate メモリ: 2 tasks × 1GB × 730h × $0.004445 = $6.49
- ALB: 730h × $0.0225 + LCU = $16.56
- データ転送: ~$2.25
- CloudWatch Logs: ~$2.50
- **ECS合計: $57.35/月**

**結果**: Lambdaが**10倍安い**（$5.37 vs $57.35）

---

### シナリオ2: 中トラフィック（月間1,000万リクエスト）

#### Lambda
- コンピュート: 10M × 2秒 × 0.256GB × $0.0000166667 = $85.33
- リクエスト: 10M × $0.20/M = $2.00
- API Gateway: 10M × $3.50/M = $35.00
- **Lambda合計: $122.33/月**

#### ECS
- Fargate: 4 tasks平均 = $72.08
- ALB: $17.11
- データ転送: ~$22.50
- CloudWatch Logs: ~$10.00
- **ECS合計: $121.69/月**

**結果**: **ほぼ同等**（損益分岐点）

- リクエスト: 100M × $0.20/M = $20.00

## パフォーマンス影響

### レイテンシ比較

#### Lambdaコールドスタート
- Node.js初期化: 200-400ms
- SDKクライアント作成: 50-100ms
- 関数ハンドラー実行: 100-500ms
- **コールドスタート合計: 350-1,000ms**

#### Lambdaウォームリクエスト
- ハンドラー実行: 100-500ms
- SDK API呼び出し: 200-400ms（コネクションプーリングなし）
- **ウォームリクエスト合計: 300-900ms**

#### ECS（常にウォーム）
- JWT検証（キャッシュ済み）: 5-10ms
- ハンドラー実行: 100-500ms
- SDK API呼び出し: 150-300ms（コネクションプーリングでレイテンシ削減）
- **リクエスト合計: 255-810ms**

### パフォーマンスサマリー

| メトリクス | Lambda | ECS | 改善率 |
|----------|--------|-----|-------|
| コールドスタート | 350-1,000ms | なし | 250-500ms削減 |
| ウォームP50 | 300ms | 250ms | 17%改善 |
| ウォームP99 | 900ms（コールドスタート含む） | 500ms | 44%改善 |
| 最大スループット | 500 req/s/関数 | 10,000 req/s | 20倍 |

### ユーザー体験への影響

- **ストリーミングレスポンス**（predictStream）: ECSの方が開始が早い（コールドスタートなし）
- **Chat APIs**: 平均20%高速化、P99は50%高速化
- **Admin APIs**（低トラフィック）: Lambda P99 = 2秒 → ECS P99 = 800ms

## 運用面の変化

### デプロイプロセス

#### Lambda（現在）
```bash
npm run cdk:deploy        # すべてのLambda関数をデプロイ
# 所要時間: 10-15分（フルスタック）
# 関数ごとのデプロイ: 即座（ダウンタイムなし）
```

#### ECS（移行後）
```bash
npm run ecs:build         # Dockerイメージビルド（3-5分）
npm run cdk:deploy        # ECSスタックデプロイ
# 初回デプロイ: 15-20分
# 以降のデプロイ: 5-7分（ローリングアップデート）
# ダウンタイム: ゼロ（ALBが段階的にルーティング）
```

### モニタリング

#### Lambda
- **CloudWatch Logs**: 関数ごと（スケール時に高コスト）
- **CloudWatch メトリクス**: 呼び出し数、実行時間、エラー、スロットリング
- **X-Rayトレーシング**（オプション）
- **80以上の関数を個別にモニタリング**

#### ECS
- **CloudWatch Logs**: サービスごと（統合）
- **CloudWatch メトリクス**: CPU、メモリ、リクエスト数、レイテンシ
- **Container Insights**: 詳細メトリクス
- **ALBアクセスログ**: リクエストレベルの可視性
- **1つのサービスをモニタリング**（運用負荷軽減）

**評価**: ECSモニタリングの方がシンプル（統合）、Lambdaモニタリングは細かい（関数ごと）

### デバッグ

#### Lambda
- CloudWatch Logs: リクエストIDでフィルタ
- AWS Lambda Console: イベントペイロードで関数をテスト
- ローカルデバッグ: SAM CLIまたはserverless-offline
- **関数ごとのデバッグ**（問題の特定が容易）

#### ECS
- CloudWatch Logs: タスクIDまたはリクエストIDでフィルタ
- ECS Exec: 実行中コンテナにSSH（`aws ecs execute-command`）
- ローカルデバッグ: Docker Compose（フルスタック）
- **Docker + コンテナライフサイクルの理解が必要**

**評価**: Lambda初心者向け、ECSにはDocker知識が必要

### スケーリング設定

#### Lambda
- 自動（設定不要）
- オプション: Provisioned Concurrency（手動）
- オプション: Reserved Concurrency（関数ごとの制限）

#### ECS
- オートスケーリングポリシー必須（CPU、メモリ、リクエスト数）
- Min/Maxタスク数設定
- ターゲットトラッキング vs ステップスケーリング
- **調整可能なパラメーターが多い**（複雑になりうる）

### アップデートとロールバック

#### Lambda
- 新バージョン公開 → エイリアス更新 → 即座に切り替え
- ロールバック: エイリアスを前のバージョンに戻す
- **ダウンタイムゼロ、即座のロールバック**

#### ECS
- 新タスク定義をデプロイ → ローリングアップデート（30%サージ）
- ロールバック: 前のタスク定義リビジョンをデプロイ
- サーキットブレーカー: ヘルスチェック失敗時に自動ロールバック
- **5-10分のロールアウト、2-3分のロールバック**

**評価**: Lambdaロールバックの方が早い（即座）、ECSサーキットブレーカーの方が安全（自動ロールバック）

### 運用複雑性スコア

| 側面 | Lambda | ECS | 優位性 |
|------|--------|-----|-------|
| デプロイ速度 | 9/10 | 6/10 | Lambda |
| モニタリングの簡潔性 | 6/10 | 8/10 | ECS |
| デバッグの容易さ | 8/10 | 6/10 | Lambda |
| スケーリング設定 | 10/10 | 7/10 | Lambda |
| ロールバック速度 | 10/10 | 7/10 | Lambda |
| **総合** | **8.6/10** | **6.8/10** | **Lambda** |

**結論**: Lambdaは運用面でよりシンプル、しかしECSもDocker経験があれば管理可能

### 主要リスク

#### リスク1: パフォーマンス劣化
- **確率**: 低（20%）
- **影響度**: 高（ユーザークレーム、チャーン）

- **確率**: 低（15%）

- **確率**: 中（30%）

  - ストリーミング失敗時にLambdaにフォールバックするサーキットブレーカー
  - ストリーミングエラー率のモニタリング（1%超でアラート）

- **確率**: 中（25%）

1. ✅ 現在のトラフィック: 月間1,000万リクエスト以上（損益分岐点）

4. ✅ Lambdaコールドスタートが問題になっている（ユーザークレーム）

### 移行を避けるべき条件（いずれかが当てはまる）

1. ❌ 現在のトラフィック: 月間1,000万リクエスト未満（Lambdaの方が安い）
2. ❌ 移行予算なし（エンジニアリング時間は高コスト）
3. ❌ チームがDocker/コンテナ経験ゼロ（トレーニング必要）
4. ❌ 規制要件: AWSマネージドコンピュートのみ使用（Lambda推奨）
5. ❌ 24/7オンコール計画なし（ECSはより多くの運用サポートが必要）

### 移行を延期すべき条件

1. ⏸️ 今後6ヶ月以内に大規模機能リリースを計画（機能開発中の移行はリスクが高い）
2. ⏸️ トラフィックが予測不可能（Lambdaの弾力性の方が価値がある）
3. ⏸️ コストが懸念事項ではない（Lambdaのシンプルさが勝る）

## 結論

### サマリー

**技術的実現可能性**: 高（8/10）
- リポジトリパターンが良く抽象化されている（コード変更最小限）
- VPC要件なし（ECSデプロイを簡素化）
- マルチテナンシーがECSでシームレスに動作
- Bedrockストリーミングサポート（Fastifyで）

**コスト効果**: 中（6/10）
- 損益分岐点: 月間1,000万リクエスト
- スケール時の節約: 月間1億リクエストで$780節約
- 低トラフィック時はLambdaの方が安い（月間1,000万リクエスト未満）

**パフォーマンス**: 高（8/10）
- コールドスタート削減（250-500ms節約）
- コネクションプーリング（20%レイテンシ削減）
- 一貫したP99レイテンシ（40%改善）

**運用複雑性**: 中（5/10）
- ECSにはDocker知識が必要
- モニタリングはよりシンプル（ログ統合）
- デプロイはより遅い（5-7分 vs 即座）

**総合スコア**: 7/10（慎重に進めるべき）

### 最適な移行ユースケース

GenUは以下の場合にECSへ移行すべき:
1. トラフィックが一貫して月間1,000万リクエスト以上
2. コスト最適化が優先事項（年間$9,000以上の潜在的節約）
3. レイテンシの一貫性が重要（コールドスタート削減）
4. チームがDocker/コンテナ経験を持っている

GenUは以下の場合にLambdaを継続すべき:
1. トラフィックが月間1,000万リクエスト未満（Lambdaの方が安い）
2. 運用のシンプルさがコスト節約よりも価値がある
3. チームがDocker/コンテナ経験に欠ける

### 最終的な推奨

**フェーズ1 POC（3週間、低リスク、高学習価値）から開始することを推奨**

POCが成功すれば、以下を得られます:
- 実現可能性の証明
- 実際のコストデータ
- Docker/ECSへのチームの自信

POCが失敗しても、以下を得られます:
- 学習経験
- 最小限の無駄な労力（3週間）
- Lambdaが正しい選択であることの検証
