#### grantId生成フォーマット

```typescript
function generateGrantId(sourceType: string, sourceId: string): string {
  // フォーマット: {sourceType}_{sourceId}_{uuid}
  return `${sourceType}_${sourceId}_${randomUUID()}`;
}

// 例: "subscription_sub-123_a1b2c3d4-e5f6-7890-abcd-ef1234567890"
```

```typescript

  tenantId: 'tenant001',
  userId: 'user123',
  grantId: generateGrantId('subscription', subscriptionId),
  features: [...],
  sourceType: 'subscription',
  sourceId: subscriptionId
```

### 修正4: RDBスキーマ - flow_execution_logsテーブル追加

**推定工数**: 0.5日

#### 現状の問題

- **統括責務が必要とするフロー実行履歴テーブルのみ未実装**

#### テーブル目的

- 各フロー（購入、変更、解約、Webhookイベント処理）の実行状態を記録
- 部分失敗時のロールバック・リトライ判断に使用
- デバッグと監査ログとして機能
- パフォーマンス分析（各ステップの実行時間記録）

#### 必要な修正

- [ ] `004_create_flow_execution_logs_table.sql` マイグレーションファイル作成（0.3日）
- [ ] マイグレーション実行と検証（0.2日）

#### スキーマ定義（抜粋）

```sql
CREATE TABLE flow_execution_logs (
  flow_execution_id UUID PRIMARY KEY,
  flow_type VARCHAR(50) NOT NULL,  -- 'purchase' | 'change_plan' | 'cancel' | 'webhook_event'
  user_id VARCHAR(255) NOT NULL,
  tenant_id VARCHAR(255) NOT NULL,
  status VARCHAR(50) NOT NULL,  -- 'processing' | 'completed' | 'failed'
  input_params JSONB NOT NULL,
  error_info JSONB,
  step_results JSONB,  -- 各ステップの実行結果を配列で記録
  created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
  completed_at TIMESTAMP WITH TIME ZONE,

  CHECK (flow_type IN ('purchase', 'change_plan', 'cancel', 'webhook_event')),
  CHECK (status IN ('processing', 'completed', 'failed'))
);

-- インデックス
CREATE INDEX idx_flow_execution_logs_user_id_created_at ON flow_execution_logs(user_id, created_at);
CREATE INDEX idx_flow_execution_logs_tenant_id_created_at ON flow_execution_logs(tenant_id, created_at);
CREATE INDEX idx_flow_execution_logs_status_created_at ON flow_execution_logs(status, created_at);
```

### 修正5: EventBridge - ルール作成

**推定工数**: 0.5日

#### 現状の問題

- イベントバス（デフォルトバス）は実装済み ✅
- イベント形式は統括責務の期待仕様と**完全一致** ✅
- ビジネスイベントマッピング機能も実装済み ✅
- Stripe → ビジネスイベント変換（payment.succeeded等）実装済み ✅
- **唯一の不足**: EventBridgeルールが未作成 ❌

#### 必要なルール

統括責務のWebhookハンドラーLambda関数に以下のイベントをルーティング:

| イベントタイプ | 目的 | 処理内容 |
|--------------|------|---------|
| payment.succeeded | 支払い更新成功 | サブスクリプション期限延長 |
| payment.failed | 支払い失敗 | 状態をpast_dueに更新、通知送信 |
| subscription.canceled | キャンセル | サブスクリプション終了、権限剥奪、デフォルトプラン遷移 |
| payment.refunded | 返金 | 返金記録、権限剥奪、デフォルトプラン遷移 |

#### 実装方針（推奨）

単一ルールで全イベントを処理し、Lambda関数内で`detail-type`に応じて処理を分岐:

```typescript
const allWebhookEventsRule = new events.Rule(this, 'AllWebhookEventsRule', {
  eventBus: events.EventBus.fromEventBusName(this, 'EventBus', 'default'),
  eventPattern: {
    source: ['billing.payment-gateway'],
    detailType: [
      'payment.succeeded',
      'payment.failed',
      'subscription.canceled',
      'payment.refunded',
    ],
  },
  description: 'Route all payment webhook events to orchestrator',
});
allWebhookEventsRule.addTarget(new targets.LambdaFunction(orchestratorWebhookHandler));
```

- [ ] EventBridgeルール作成（単一または4つ）（0.3日）

## 重要な発見事項

### 1. 既存実装の高品質

既存の実装は非常に高品質で、以下の点で優れています：

- **Payment Gateway**: ビジネスイベントマッピング機能まで実装済み
- **RDBスキーマ**: 外部キー制約、インデックス、自動更新トリガーが完璧
- **scheduled_termination対応**: データモデルとリポジトリ層で完全実装済み
- **検証保留機能**: pending_verification状態、手動承認・却下APIまで実装済み

### 2. scheduled_cancellation表現の明確化

**重要な発見**: Subscription Managementでは`scheduled_cancellation`を独立したステータスではなく、以下の組み合わせで表現しています：

```
subscription_status: 'active'
cancel_at_period_end: true
```

これは**Stripe標準の実装方式と一致**しており、Apple/Googleでも同様のパターンが一般的です。

**推奨対応**: 技術実装詳細.mdにこの表現方法を明記する（ドキュメント修正のみ）

### 3. リポジトリ層とAPI層の実装格差

Subscription ManagementとPlan Managementは、リポジトリ層が充実している一方、統括責務が必要とする内部用Lambda関数が未実装です。

これは、既存実装が「管理者向けインターフェース」として開発されてきたことに起因します。

**影響**: Lambda関数のラッパーを作成するだけで済むため、実装工数は比較的小さい

## リスクと対策

### リスク1: 権限管理サービスの連携

**リスク**: approveSubscription、rejectSubscription、cancelFlowでのOpenFGA/カウント機構連携がTODOコメント

**対策**:
- 短期: 統括責務実装時に`authorizationService`を作成し、呼び出しを実装
- 長期: 承認・却下処理のTODO箇所を完成させる

### リスク2: Lambda-to-Lambda呼び出しのレイテンシー

**リスク**: 統括責務のフロー実行時間が増加

**対策**:
- 各Lambda関数の処理時間を最適化
- 必要に応じて並列実行を検討
- タイムアウト設定の適切な調整（購入フロー: 60秒、その他: 30秒）

### リスク3: RDB接続プール枯渇

**リスク**: 同時実行数が多い場合にDB接続エラー

**対策**:
- RDS Proxyの接続プール設定を調整
- Lambda関数内での適切な接続管理（接続リークの防止）
- CloudWatch Metricsで接続数を監視

## まとめ

### 実装可能性

統括責務の実装に必要な修正は明確に特定でき、実装に進むことができます。

### 既存実装の評価

既存の実装は非常に高品質であり、以下の点で統括責務の実装を支える準備ができています：

- ✅ データモデルは完璧（scheduled_termination、適用ソース対応済み）
- ✅ リポジトリ層は充実したCRUD操作を完備
- ✅ Payment Gatewayはイベント配信まで完全実装
- ✅ Authorization Serviceは機能として完全実装

### 必要な修正の性質

必要な修正は、**「機能の不足」ではなく「インターフェースの追加」**という性質です：

- Subscription Management: 既存リポジトリを活用した内部用Lambda追加
- Plan Management: 既存リポジトリを活用したAPI層追加
- Authorization Service: 既存機能へのLambda Invoke対応
- RDB: 1テーブル追加のみ
- EventBridge: ルール作成のみ

この性質により、実装リスクは比較的低く、工数も明確に見積もることができます。
