## 2. EventBridge設定（最優先・必須）

### 実装状況: **0% - 完全に未実装**

### 問題点

1. **EventBridgeルール3つが未定義**
   - Stripe Webhook用ルール
   - Apple Webhook用ルール
   - Google Webhook用ルール

2. **デッドレターキュー（DLQ）が未実装**
   - `${environment}-webhook-event-dlq` SQSキューが存在しない
   - リトライポリシー未設定

3. **Webhookイベント配信経路が断絶**
   - Webhook受信Lambda → EventBridge送信: ✅ 実装済み
   - EventBridge → 統括責務Lambda起動: ❌ **未実装**

### 必須修正内容

```
1. EventBridgeルール3つの作成
   - イベントパターン: source: ["billing.payment-gateway"], detail-type: ["{Platform} Webhook Event"]
   - ターゲット: webhookEventFlow Lambda関数

2. SQSデッドレターキューの作成
   - キュー名: ${environment}-webhook-event-dlq
   - メッセージ保持期間: 14日間
   - リトライ設定: 最大3回、指数バックオフ

3. OrchestrationConstruct内でのルール定義
```

### 影響

**Webhook通知（自動更新、支払い失敗、返金など）が処理されず、サブスクリプション状態が同期されません。**

## 3. Payment Gateway Internal関数（最優先・必須）

### 実装状況: **実装済みだが呼び出しインターフェースが不適切**

### 問題点

1. **API Gateway経由のエンドポイントとして実装**
   - 技術実装詳細: Lambda同期呼び出し（`InvokeCommand`）想定
   - 実装: API Gateway経由のHTTPエンドポイント
   - 統括責務から直接Lambda invokeで呼び出せない

2. **パラメータ名の不一致**
   - `newPlanId` → `newPriceId`
   - `prorate` → `isUpgrade`
   - `atPeriodEnd` → `cancelImmediately`（論理が逆）

3. **Internal関数の公開プロパティが存在しない**
   - 技術実装詳細: `paymentGatewayFunctions.verifyReceipt` 等
   - 実装: `verifyReceiptFunction`（API Gateway用）

### 必須修正内容

```
1. Internal Lambda関数の新規作成（最優先）
   - verifyReceipt.ts（internal版）
   - updateSubscription.ts（internal版）
   - cancelSubscription.ts（internal版）
   - 配置: packages/cdk/lambda/billing/payment-gateway/internal/

2. 入出力形式の変更
   - 入力: プレーンなJSONオブジェクト（APIGatewayProxyEvent形式ではない）
   - 出力: プレーンなJSONオブジェクト（statusCode、bodyラップなし）

3. CDK Constructでの公開
   - internalFunctions プロパティの追加
   - OrchestrationConstructへの参照渡し

4. パラメータ名の統一
```

### 影響

**購入フロー、プラン変更フロー、解約フローが実装できません。**

## 4. Plan Management Internal関数（高優先度・必須）

### 実装状況: **実装済みだが重大な差異あり**

### 問題点

#### 4-1. applyPlanToUser関数

**問題**: 権限付与が実装されていない

- 技術実装詳細: `grantId`（権限付与ID）を返すことを期待
- 実装: `applicationId`（プラン適用ID）を返すが、権限付与処理が欠落
- **影響**: 購入フロー・プラン変更フローで権限が付与されない

**必須修正**:
```
1. 出力に grantId を追加（または技術実装詳細を applicationId に修正）
2. Authorization責務の grantPermission を呼び出す処理を追加
```

#### 4-2. terminatePlanApplication関数

**問題1**: `immediate`パラメータが欠落

- 技術実装詳細: `immediate: boolean` で即時終了か期限終了時終了かを制御
- 実装: パラメータ自体が存在せず、常に `expired` に変更
- **影響**: 「期限終了時解約」が実装できない

**問題2**: `planApplicationId`ではなく`applicationSourceId`で検索

- 技術実装詳細: `planApplicationId` で直接プラン適用を特定
- 実装: `applicationSourceId`（サブスクリプションID）から検索
- **影響**: 統括責務が `applicationSourceId` を管理する必要がある

**必須修正**:
```
1. immediate パラメータの追加
2. immediate: true → expired、immediate: false → scheduled_termination に分岐
3. パラメータを planApplicationId に変更（または技術実装詳細を修正）
```

#### 4-3. updatePlanApplicationStatus関数

**問題**: パラメータ名の軽微な不一致

- 技術実装詳細: `planApplicationId`
- 実装: `applicationId`
- **影響**: 軽微（統括責務側で applicationId として渡せば動作する）

**推奨修正**:
```
パラメータ名を planApplicationId に統一（一貫性向上）
```

### 影響

**購入フロー、プラン変更フロー、解約フローが正しく動作しません。特に権限付与が行われないため、ユーザがサービスにアクセスできません。**

## 5. Subscription Management Internal関数（中優先度・調整必要）

### 実装状況: **4関数すべて実装済み**

### 問題点

パラメータ名が技術実装詳細と異なる箇所があるため、統括責務のClientモジュール実装時にマッピング調整が必要。

| 関数名 | 技術実装詳細 | 実装 | 対応 |
|-------|------------|------|------|
| createSubscription | `platform` | `platformType` | マッピング必要 |
| createSubscription | `receiptData` | （存在しない） | 追加パラメータ必要 |
| updateSubscriptionStatus | `status` | `newStatus` | マッピング必要 |
| updateSubscriptionStatus | `statusReason` | （存在しない） | オプション、なくても動作可 |
| extendSubscriptionPeriod | `newExpiresAt` | `newPeriodStart` + `newPeriodEnd` | マッピング必要 |

### 必須修正内容

```
1. subscriptionManagementClient.ts 実装時にパラメータマッピングを適切に実施
2. createSubscription 呼び出し時に subscriptionStatus, currentPeriodStart, currentPeriodEnd を渡す
3. extendSubscriptionPeriod 呼び出し時に newPeriodStart, newPeriodEnd の2つを渡す
```

### 影響

**パラメータマッピングを正しく実装すれば動作します。機能的な欠落はありません。**

## 7. Authorization機構（低優先度・連携実装必要）

### 実装状況: **実装済みだが統括責務との連携が未実装**

### 問題点

1. **統括責務（Orchestration）が未実装**
   - 権限付与・剥奪を呼び出す側が存在しない

2. **Plan Management責務からの呼び出しが未実装**
   - `applyPlanToUser.ts` は権限付与を呼び出していない
   - `terminatePlanApplication.ts` は権限剥奪を呼び出していない

3. **authorizationClientモジュールが未実装**
   - 統括責務から呼び出すためのクライアントが存在しない

### 必須修正内容

```
1. authorizationClient.ts モジュールの作成
   - grantPermission(tenantId, userId, grantId, features, sourceType, sourceId)
   - revokePermission(tenantId, grantId)

2. 統括責務のLambda関数にIAM権限付与
   - lambda:InvokeFunction for grantPermissionFunction
   - lambda:InvokeFunction for revokePermissionFunction

3. 統括責務の各フローからの呼び出し実装
   - purchaseFlow → grantPermission
   - planChangeFlow → revokePermission + grantPermission
   - cancellationFlow → revokePermission
   - webhookEventFlow (refund) → revokePermission

4. プラン情報から features への変換ロジック実装
```

### 影響

**権限付与・剥奪が行われないため、ユーザがサービスにアクセスできません。ただし、統括責務実装後に連携すれば動作します。**

## 実装の推奨順序

統括責務を実装する前提として、以下の順序で修正を進めることを推奨します:

### フェーズ1: インフラ基盤の整備（最優先）

1. **Payment Gateway Internal関数の作成**
   - verifyReceipt、updateSubscription、cancelSubscription のInternal版
   - CDK Constructでの internalFunctions プロパティ公開

2. **Plan Management Internal関数の修正**
   - applyPlanToUser に immediate パラメータ追加
   - terminatePlanApplication に immediate パラメータ追加

3. **EventBridge設定の作成**
   - EventBridgeルール3つ
   - SQS DLQ

### フェーズ2: 統括責務の実装

4. **OrchestrationConstructの作成**
   - DynamoDBテーブル定義
   - 共通モジュール（flowOrchestrator、stepExecutor、rollbackHandler）
   - Clientモジュール（planManagement、subscriptionManagement、paymentGateway、authorization）

5. **購入フローの実装**
   - purchaseFlow.ts
   - 権限付与連携

6. **その他フローの実装**
   - planChangeFlow.ts
   - cancellationFlow.ts
   - webhookEventFlow.ts

### フェーズ3: 統合テスト

7. **エンドツーエンドテスト**
   - 購入フロー → プラン適用 → 権限付与
   - プラン変更フロー → 権限剥奪 → 権限付与
   - 解約フロー → 権限剥奪
   - Webhookイベント処理 → 期限延長
