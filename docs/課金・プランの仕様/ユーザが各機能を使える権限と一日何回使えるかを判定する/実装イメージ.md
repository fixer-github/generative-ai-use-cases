# ユーザが各機能を使える権限と一日何回使えるかを判定する - 実装イメージ

## 概要

この責務は、ユーザがある機能にアクセスしようとした時に、「このユーザはこの機能を使える権限があるか」「今日あと何回使えるか」を判定します。プラン適用の結果として、ユーザが「何ができるか」を決定します。

この責務の特徴は以下の通りです：

- **OpenFGAとDynamoDBを組み合わせて使用**: OpenFGAは権限の有無を管理し、DynamoDBは回数制限とカウント情報を管理します
- **プランという概念を持たない**: プラン管理の責務と疎結合を維持するため、「権限付与ID」という抽象的な識別子のみを扱います
- **Database Per Tenantsパターンでマルチテナント対応**: Lambda関数は共通リソース、DynamoDBはテナント専用リソースとして管理します

---

## 実装イメージの全体像

この責務は、大きく分けて5つの仕事をします。

### 1つ目の仕事：権限を付与する

他の責務から「このユーザにこの機能への無制限アクセスと、あの機能への一日100回の制限付きアクセスを与えてください。この権限のIDは〇〇です」という依頼を受け取ります。すると、OpenFGAに「このユーザはこの機能を使えます」という関係性を登録し、DynamoDBに「このユーザはあの機能を一日100回まで使えます。現在の利用回数は0回です」というカウンター情報を記録します。

### 2つ目の仕事：権限を剥奪する

他の責務から「権限ID〇〇で付与した権限をすべて取り消してください」という依頼を受け取ります。すると、OpenFGAから該当する関係性を削除し、DynamoDBから該当するカウンター情報を削除します。

### 3つ目の仕事：権限をチェックする

ユーザが機能を使おうとしたとき、「このユーザはこの機能を使えますか」という問い合わせを受け取ります。すると、まずOpenFGAに「このユーザはこの機能にアクセスできますか」と聞きます。次に、DynamoDBに「このユーザの今日の利用回数はあと何回残っていますか」と聞きます。両方の答えが「OK」の場合だけ、「使えます」と答えます。どちらか一方でも「NG」なら「使えません」と答えます。

### 4つ目の仕事：カウントを増やす

ユーザが実際に機能を使ったら、DynamoDBのカウンターを1増やします。例えば、ある機能を使う前は「今日あと98回使えます」だったのが、使った後は「今日あと97回使えます」に変わります。

### 5つ目の仕事：カウントをリセットする

毎日決まった時刻（例えば午前0時）に、EventBridgeから「日次カウントをリセットしてください」という指示を受け取ります。すると、DynamoDBの日次カウンターをすべてゼロに戻します。月次制限も同じように、毎月決まった日にリセットします。

## 具体的なコンポーネント構成

### Lambda関数（共通リソース）

Lambda関数は、テナントごとに用意するのではなく、全テナント共通で1つずつ用意します。どのテナントのデータを扱うかは、リクエストの中に含まれるテナントIDから判断します。

以下のLambda関数が必要です：

#### 権限付与Lambda関数

- **呼び出し元**: プラン管理などの他の責務
- **役割**: OpenFGAとDynamoDBに権限情報を登録します
- **入力**: ユーザID、付与する機能のリスト（機能IDと回数制限のペア）、権限付与ID、テナントID
- **処理内容**:
  1. OpenFGAに機能へのアクセス権限を登録
  2. 回数制限がある機能については、DynamoDBにカウンター情報を作成
  3. 権限付与履歴をDynamoDBに記録
- **出力**: 権限付与完了の通知

#### 権限剥奪Lambda関数

- **呼び出し元**: プラン管理などの他の責務
- **役割**: OpenFGAとDynamoDBから権限情報を削除します
- **入力**: 権限付与ID、テナントID
- **処理内容**:
  1. DynamoDBの権限付与履歴から該当する権限情報を取得
  2. OpenFGAから該当する関係性を削除
  3. DynamoDBから該当するカウンター情報を削除
  4. 権限付与履歴の状態を「revoked」に更新
- **出力**: 権限剥奪完了の通知

#### 権限チェックLambda関数

- **呼び出し元**: 機能を提供している部分（各種API）
- **役割**: OpenFGAとDynamoDBに問い合わせて「使えるか使えないか」を判定します
- **入力**: ユーザID、機能ID、テナントID
- **処理内容**:
  1. OpenFGAに権限の有無を問い合わせ
  2. DynamoDBに利用回数の残数を問い合わせ
  3. 両方がOKの場合のみ、アクセスを許可
- **出力**: 許可/拒否の判定結果、残り利用回数

#### カウント加算Lambda関数

- **呼び出し元**: 機能を実際に使った直後（各種API）
- **役割**: DynamoDBのカウントを1増やします
- **入力**: ユーザID、機能ID、テナントID
- **処理内容**:
  1. DynamoDBの該当カウンターを1増やす（アトミックな更新）
- **出力**: 更新後のカウント値

#### カウントリセットLambda関数

- **呼び出し元**: EventBridgeから定期的に呼ばれます
- **役割**: DynamoDBのカウントをゼロに戻します
- **入力**: リセット期間タイプ（日次または月次）
- **処理内容**:
  1. 全テナントのDynamoDBテーブルを順番に処理
  2. 各テナントのテーブルから該当期間のカウント情報を取得
  3. 現在のカウントをゼロに戻す
  4. 次回のリセット日時を更新
- **出力**: リセット完了の通知

### DynamoDB（テナント専用リソース）

DynamoDBテーブルは、テナントごとに専用のものを用意します。これにより、あるテナントのデータが別のテナントから見えることを防ぎます。

#### 利用回数カウントテーブル

**テーブル名**: `{tenant-id}-usage-counter`

**主キー構成**:

- パーティションキー: `userId` (String) - ユーザID
- ソートキー: `featureId#period` (String) - 機能IDと期間タイプの複合キー（例: `feature-model-a#daily`）

**属性**:

- `userId` (String): ユーザID
- `featureId` (String): 機能ID
- `periodType` (String): 期間タイプ（`daily` または `monthly`）
- `currentCount` (Number): 現在の利用回数
- `limitCount` (Number): 上限回数
- `nextResetTime` (Number): 次回リセット日時（Unixタイムスタンプ）
- `grantId` (String): 権限付与ID（どの権限付与で追加されたか）
- `createdAt` (Number): 作成日時
- `updatedAt` (Number): 更新日時

**GSI (Global Secondary Index)**:

- `grantId-index`: 権限付与IDで検索（権限剥奪時に使用）
  - パーティションキー: `grantId`
- `nextResetTime-index`: リセット日時で検索（バッチリセット処理で使用）
  - パーティションキー: `periodType`
  - ソートキー: `nextResetTime`

**データ例**:

```json
{
  "userId": "user-123",
  "featureId#period": "feature-model-b#daily",
  "featureId": "feature-model-b",
  "periodType": "daily",
  "currentCount": 30,
  "limitCount": 50,
  "nextResetTime": 1699747200,
  "grantId": "GRANT-456",
  "createdAt": 1699660800,
  "updatedAt": 1699700000
}
```

#### 権限付与履歴テーブル

**テーブル名**: `{tenant-id}-permission-grants`

**主キー構成**:

- パーティションキー: `grantId` (String) - 権限付与ID

**属性**:

- `grantId` (String): 権限付与ID
- `userId` (String): ユーザID
- `features` (List): 付与された機能のリスト
  - 各要素: `{ featureId: String, limitType: String, limitCount: Number }`
  - `limitType`: `unlimited`, `daily`, `monthly` のいずれか
- `status` (String): 状態（`active` または `revoked`）
- `sourceType` (String): 付与元のタイプ（`subscription`, `trial`, `campaign`, `manual` など）
- `sourceId` (String): 付与元のID（サブスクリプションID、キャンペーンIDなど）
- `grantedAt` (Number): 付与日時
- `revokedAt` (Number, optional): 剥奪日時

**GSI (Global Secondary Index)**:

- `userId-status-index`: ユーザIDと状態で検索
  - パーティションキー: `userId`
  - ソートキー: `status`

**データ例**:

```json
{
  "grantId": "GRANT-456",
  "userId": "user-123",
  "features": [
    {
      "featureId": "feature-a",
      "limitType": "unlimited",
      "limitCount": null
    },
    {
      "featureId": "feature-b",
      "limitType": "daily",
      "limitCount": 50
    }
  ],
  "status": "active",
  "sourceType": "subscription",
  "sourceId": "sub-789",
  "grantedAt": 1699660800,
  "revokedAt": null
}
```

### OpenFGA（既存）

OpenFGAには、「ユーザAは機能Bにアクセスできる」という関係性だけを登録します。回数制限の情報は含めません。なぜなら、OpenFGAは「できるかできないか」の二択の判定には向いていますが、「あと何回できるか」という数値の管理には向いていないためです。

**関係性の例**:

```
user:user-123 can access feature:feature-a
user:user-123 can access feature:feature-b
```

権限剥奪時は、これらの関係性を削除します。

### EventBridge（共通リソース）

EventBridgeのスケジュール機能を使って、決まった時刻にカウントリセットLambda関数を自動的に起動します。

**スケジュール設定例**:

- **日次カウントリセット**: 毎日午前0時（UTC）
  - Cron式: `cron(0 0 * * ? *)`
  - ターゲット: カウントリセットLambda関数
  - 入力パラメータ: `{ "periodType": "daily" }`

- **月次カウントリセット**: 毎月1日の午前0時（UTC）
  - Cron式: `cron(0 0 1 * ? *)`
  - ターゲット: カウントリセットLambda関数
  - 入力パラメータ: `{ "periodType": "monthly" }`

## 処理の流れの具体例

### 例1：プラン適用時に権限を付与する流れ

1. **プラン管理の責務から依頼を受ける**
   「ユーザID123に、機能Aへの無制限アクセスと、機能Bへの一日50回の制限付きアクセスを付与してください。権限付与IDはGRANT-456です」という依頼が権限付与Lambda関数に届きます。

2. **OpenFGAに関係性を登録**
   権限付与Lambda関数は、まずOpenFGAに「ユーザID123は機能Aにアクセスできる」「ユーザID123は機能Bにアクセスできる」という2つの関係性を登録します。

3. **DynamoDBにカウント情報を記録**
   次に、テナント専用のDynamoDBに、機能Bの利用回数カウント情報を記録します。「ユーザID123、機能B、日次、現在0回、上限50回、リセット日時は明日の午前0時、権限付与IDはGRANT-456」という内容です。機能Aは無制限なので、カウント情報は作りません。

4. **権限付与履歴を記録**
   さらに、DynamoDBの権限付与履歴テーブルに「権限付与ID GRANT-456、ユーザID123、付与日時、状態はactive」という記録を残します。

5. **完了を返答**
   「権限付与が完了しました」と呼び出し元に返答します。

### 例2：機能を使うときに権限をチェックする流れ

1. **問い合わせを受ける**
   ユーザID123が機能Bを使おうとします。機能を提供している部分から「ユーザID123は機能Bを使えますか」という問い合わせが権限チェックLambda関数に届きます。

2. **OpenFGAで権限の有無を確認**
   権限チェックLambda関数は、まずOpenFGAに「ユーザID123は機能Bにアクセスできますか」と問い合わせます。OpenFGAは「はい、できます」と答えます。

3. **DynamoDBで利用回数を確認**
   次に、テナント専用のDynamoDBに「ユーザID123の機能Bの今日の利用回数はあと何回残っていますか」と問い合わせます。DynamoDBを見ると「上限50回、現在30回使用済み」なので「あと20回使えます」という答えが返ってきます。

4. **判定結果を返答**
   両方の答えがOKなので、権限チェックLambda関数は「使えます。あと20回残っています」と呼び出し元に返答します。

5. **カウントを増やす**
   ユーザが実際に機能Bを使った直後、カウント加算Lambda関数が呼ばれて、DynamoDBのカウントを30回から31回に増やします。次に同じ問い合わせがあったら「あと19回使えます」と答えるようになります。

### 例3：毎日カウントをリセットする流れ

1. **EventBridgeから起動される**
   午前0時になると、EventBridgeが自動的にカウントリセットLambda関数を起動します。

2. **全テナントのテーブルを処理**
   カウントリセットLambda関数は、全テナントのDynamoDBテーブルを順番に処理します。各テナントのテーブルから「日次」のカウント情報をすべて取得します。

3. **カウントをリセット**
   取得した各カウント情報について、現在のカウントをゼロに戻し、リセット日時を明日の午前0時に更新します。

4. **結果**
   これにより、昨日たくさん使って上限に達していたユーザも、今日は再び上限いっぱいまで使えるようになります。

### 例4：プラン解約時に権限を剥奪する流れ

1. **剥奪依頼を受ける**
   プラン管理の責務から「権限付与ID GRANT-456で付与した権限をすべて取り消してください」という依頼が権限剥奪Lambda関数に届きます。

2. **権限情報を取得**
   権限剥奪Lambda関数は、まずDynamoDBの権限付与履歴テーブルから「権限付与ID GRANT-456」の記録を探します。そこに「ユーザID123、機能A、機能B」という情報が含まれています。

3. **OpenFGAから関係性を削除**
   OpenFGAから「ユーザID123は機能Aにアクセスできる」「ユーザID123は機能Bにアクセスできる」という関係性を削除します。

4. **DynamoDBからカウント情報を削除**
   DynamoDBの利用回数カウントテーブルから「権限付与ID GRANT-456」に紐づくすべてのカウント情報を削除します。

5. **履歴を更新**
   DynamoDBの権限付与履歴テーブルで、権限付与ID GRANT-456の状態を「active」から「revoked」に変更します。

6. **完了を返答**
   「権限剥奪が完了しました」と呼び出し元に返答します。

## プランという概念を持たない設計

この責務では、「プラン」という言葉は一切登場しません。代わりに、「権限付与ID」という抽象的な識別子だけを扱います。

### 設計の意図

**疎結合の維持**: プラン管理の責務と権限判定の責務を疎結合に保つことで、それぞれが独立して変更可能になります。

**再利用性の向上**: プランという概念がない別の形（例えばToB向けの企業単位の権限管理など）でも、同じ権限判定の仕組みを再利用できます。

### 具体例

例えば、プラン管理の責務は内部的に次のように考えています：

- 「Standardプランを適用するから、機能Aと機能Bへの権限を付与して」

しかし、この権限判定の責務からは次のように見えます：

- 「権限付与ID GRANT-456で、機能Aと機能Bへの権限を付与してください」

どのプラン由来かは知りません。知る必要もありません。

### インターフェースの設計

権限付与Lambda関数のAPIは、次のような形になります：

```typescript
interface GrantPermissionRequest {
  tenantId: string; // テナントID
  userId: string; // ユーザID
  grantId: string; // 権限付与ID（呼び出し元が生成）
  features: Array<{
    featureId: string; // 機能ID
    limitType: 'unlimited' | 'daily' | 'monthly';
    limitCount?: number; // limitTypeが'unlimited'以外の場合に必須
  }>;
  sourceType: string; // 付与元のタイプ（ログ用）
  sourceId: string; // 付与元のID（ログ用）
}
```

プランという概念は一切含まれていません。これにより、プラン以外の文脈（トライアル、キャンペーン、手動付与、ToB向けの企業契約など）からも同じインターフェースで利用できます。

## マルチテナント対応の実現方法

Database Per Tenantsパターンを採用し、Lambda関数は共通リソース、DynamoDBはテナント専用リソースとして管理します。

### Lambda関数の共有

Lambda関数は全テナント共通で1つだけ用意します。これにより：

- **コストの最適化**: Lambda関数のコードは共有されるため、デプロイやメンテナンスのコストが削減されます
- **一貫性の保証**: すべてのテナントが同じロジックを使用するため、動作の一貫性が保証されます

### テナントIDによるデータ分離

Lambda関数が呼ばれるとき、リクエストの中に必ず「テナントID」が含まれています。Lambda関数は、そのテナントIDを見て「どのテナントのDynamoDBテーブルにアクセスすべきか」を判断します。

**テーブル名の命名規則**:

- テナントAのDynamoDBテーブル: `tenant-a-usage-counter`
- テナントBのDynamoDBテーブル: `tenant-b-usage-counter`

**Lambda関数の処理**:

```typescript
// テナントIDからテーブル名を動的に生成
const tableName = `${tenantId}-usage-counter`;

// そのテーブルに対してDynamoDB操作を実行
const result = await dynamoDB.getItem({
  TableName: tableName,
  Key: { userId, featureIdPeriod },
});
```

### データ分離の保証

こうすることで：

- **完全なデータ分離**: あるテナントのユーザが別のテナントのデータを見ることは絶対にできません
- **テナント単位のスケーリング**: テナントごとにDynamoDBのキャパシティを調整できます
- **テナント単位のバックアップ**: テナントごとに独立してバックアップやリストアが可能です

### セキュリティの考慮事項

**IAMポリシーの設計**: Lambda関数には、すべてのテナントのDynamoDBテーブルにアクセスする権限を付与しますが、リクエストに含まれるテナントIDのテーブルにのみアクセスするようにコード側で制御します。

**テナントIDの検証**: リクエストに含まれるテナントIDは、認証済みユーザのテナントIDと一致することを必ず検証します。これにより、別のテナントのデータへの不正アクセスを防ぎます。

## まとめ

この責務の実装は、次のような特徴を持ちます：

### 設計原則

1. **責務の明確な分離**: OpenFGAとDynamoDBの2つを組み合わせて、「権限の有無」と「回数制限」の両方を判定します。それぞれの技術を、その得意な領域に特化して使用します。

2. **疎結合の維持**: 「プラン」という概念を持たず、「権限付与ID」という抽象的な識別子で管理することで、他の責務と疎結合を維持します。

3. **マルチテナント対応**: Lambda関数は共通リソースとして全テナントで共有し、DynamoDBは各テナント専用に分離します。

### 5つの明確な仕事

1. **権限の付与**: 他の責務からの依頼を受けて、OpenFGAとDynamoDBに権限情報を登録します
2. **権限の剥奪**: 他の責務からの依頼を受けて、OpenFGAとDynamoDBから権限情報を削除します
3. **権限のチェック**: ユーザが機能を使おうとしたときに、使えるかどうかを判定します
4. **カウントの加算**: ユーザが機能を使ったときに、カウンターを1増やします
5. **カウントのリセット**: EventBridgeからの指示を受けて、決まった時刻にカウントをリセットします

### 他の責務との関係

この設計により：

- **プラン管理の責務**は「どのプランにどの機能が含まれるか」に集中できます
- **権限判定の責務**は「ユーザが機能を使えるかどうか」の判定に集中できます
- それぞれが自分の仕事だけに専念できるため、変更に強く、理解しやすいシステムになります

### 技術的な利点

- **スケーラビリティ**: Lambda関数とDynamoDBの組み合わせにより、高いスケーラビリティを実現します
- **可用性**: マネージドサービスを活用することで、高い可用性を実現します
- **コスト効率**: Lambda関数の共有とDynamoDBのオンデマンドモードにより、コスト効率の良い運用が可能です
- **セキュリティ**: テナントごとのデータ分離により、高いセキュリティを実現します
