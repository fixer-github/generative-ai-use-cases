# 「Stripe/Apple/Googleの決済システムとのやり取りを一本化する」責務の技術実装構成

## 目的
この資料は、`Stripe/Apple/Googleの決済システムとのやり取りを一本化する`責務について、実装時に必要となる技術的な構成を明示します。コード実装そのものは含まず、どのようなファイルがどこに配置され、どのような処理が含まれ、どのようなAWSリソースが追加されるかを示します。

## 前提：現在のシステム構成の特徴

本システムは以下の構成パターンを採用しています：

- **Lambda関数配置**: `packages/cdk/lambda/` 配下
- **API定義**: `packages/cdk/lib/construct/api/` 配下でCDK Constructとして定義
- **データアクセス層**: Repositoryパターンを使用（`packages/cdk/lambda/repositories/`配下）
- **データストア**:
  - RDS（PostgreSQL）：プラン・サブスクリプションの構造化データ
  - DynamoDB：テナント専用リソースとして、イベントログ・キャッシュなど
- **マルチテナント**: Database Per Tenantsパターン（DynamoDBはテナント別、Lambda関数は共通リソース）

## 2. Lambda関数の追加

### 2.1. Webhookエンドポイント（3つ）

#### 2.1.1. Stripe Webhookエンドポイント
**ファイル**: `packages/cdk/lambda/billing/payment-gateway/webhook/stripe/receiveWebhook.ts`

**トリガー**: API Gateway（POST `/billing/webhook/stripe`）

**実行される処理の流れ**:
1. リクエストボディとヘッダーを取得
2. Stripe署名検証（`stripe-signature`ヘッダーを使用）
3. 署名検証失敗 → 401エラーを返す
4. 署名検証成功 → イベントIDを抽出（`event.id`）
5. `webhookEventRepository.findByEventId()` で重複チェック
6. 重複している → 200 OKを返す（冪等性保証）
7. 重複していない → イベント全体を`webhookEventRepository.save()`で保存
8. EventBridgeのイベントバスに以下のフォーマットで送信:
   ```json
   {
     "source": "payment-gateway.webhook",
     "detail-type": "StripeWebhookReceived",
     "detail": {
       "platform": "stripe",
       "eventId": "evt_xxx",
       "eventType": "customer.subscription.updated",
       "eventData": { /* イベントのペイロード全体 */ },
       "tenantId": "tenant-xxx"
     }
   }
   ```
9. 200 OKを返す

**環境変数**:
- `STRIPE_WEBHOOK_SECRET`: Webhook署名検証用シークレット（Secrets Managerから取得）
- `EVENT_BUS_NAME`: EventBridgeのイベントバス名
- `TENANT_ID`: テナントID（Lambda環境変数として設定）
- `WEBHOOK_EVENT_TABLE_NAME`: Webhookイベントログテーブル名（テナント専用DynamoDB）

**必要な外部ライブラリ**:
- `stripe`: Stripe SDK（署名検証に使用）
- `@aws-sdk/client-eventbridge`: EventBridge SDK
- `@aws-sdk/client-dynamodb`: DynamoDB SDK

**IAMポリシー**:
- EventBridgeへのイベント送信権限（`events:PutEvents`）
- DynamoDBへの読み書き権限（`dynamodb:GetItem`, `dynamodb:PutItem`）
- Secrets Managerからの読み取り権限（`secretsmanager:GetSecretValue`）

**タイムアウト**: 30秒

**メモリ**: 256MB

### 2.2. レシート検証処理

#### 2.2.1. 統一レシート検証インターフェース
**ファイル**: `packages/cdk/lambda/billing/payment-gateway/verification/verifyReceipt.ts`

**トリガー**: Lambda関数の直接呼び出し（他のLambda関数から`lambda:InvokeFunction`で呼び出される）

**実行される処理の流れ**:
1. 呼び出し元から以下のペイロードを受け取る:
   ```json
   {
     "platformType": "stripe" | "apple" | "google",
     "receipt": "...",  // プラットフォーム固有のレシート情報
     "tenantId": "tenant-xxx"
   }
   ```
2. `platformType`に基づいて適切な検証実装を選択:
   - `stripe` → `stripeVerifier.verify()`
   - `apple` → `appleVerifier.verify()`
   - `google` → `googleVerifier.verify()`
3. 検証処理を実行:
   - 検証成功 → 結果を`receiptCacheRepository.save()`でキャッシュに保存（TTL: 24時間）
   - 検証失敗（ネットワークエラー等） → `receiptCacheRepository.findByReceiptHash()`でキャッシュを確認
     - キャッシュヒット＆TTL有効 → キャッシュ結果を返す（フォールバック成功）
     - キャッシュミス → 短い待機時間（2秒）後に再検証を1回試行
     - 再検証も失敗 → 検証失敗結果を返す
4. 検証結果を呼び出し元に返す:
   ```json
   {
     "success": true | false,
     "data": {
       "subscriptionId": "sub_xxx",
       "productId": "price_abc123",
       "expiresAt": "2025-12-31T23:59:59Z",
       ...
     },
     "cached": false | true  // キャッシュから取得したか
   }
   ```

**環境変数**:
- `RECEIPT_CACHE_TABLE_NAME`: レシート検証キャッシュテーブル名（テナント専用DynamoDB）
- `STRIPE_API_KEY`: Stripe APIキー（Secrets Managerから取得）
- `APPLE_SHARED_SECRET`: Apple共有シークレット（Secrets Managerから取得）
- `GOOGLE_SERVICE_ACCOUNT_KEY`: Google Cloud認証情報（Secrets Managerから取得）
- `TENANT_ID`: テナントID

**必要な外部ライブラリ**:
- `stripe`: Stripe SDK
- `node-fetch`: HTTP リクエスト（Apple検証用）
- `google-auth-library`: Google認証ライブラリ
- `@aws-sdk/client-dynamodb`
- `@aws-sdk/client-secrets-manager`

**IAMポリシー**:
- DynamoDBへの読み書き権限
- Secrets Managerからの読み取り権限

**タイムアウト**: 60秒（外部API呼び出しを含むため）

**メモリ**: 512MB

### 2.3. 決済操作実行

#### 2.3.1. Checkout Session作成（Stripe）
**ファイル**: `packages/cdk/lambda/billing/payment-gateway/operations/createCheckoutSession.ts`

**トリガー**: Lambda関数の直接呼び出し（統括責務から呼び出される）

**実行される処理の流れ**:
1. 呼び出し元から以下のペイロードを受け取る:
   ```json
   {
     "userId": "user-xxx",
     "priceId": "price_abc123",  // Stripeの価格ID
     "successUrl": "https://...",
     "cancelUrl": "https://...",
     "tenantId": "tenant-xxx"
   }
   ```
2. Stripe SDKを使って`stripe.checkout.sessions.create()`を呼び出し:
   - `customer_email`: ユーザーのメールアドレス（Cognitoから取得）
   - `mode`: "subscription"
   - `line_items`: `[{ price: priceId, quantity: 1 }]`
   - `success_url`, `cancel_url`: リダイレクト先
   - `metadata`: `{ userId, tenantId }` （Webhookでユーザーを特定するため）
3. Checkout SessionのURLを取得
4. 結果を返す:
   ```json
   {
     "sessionId": "cs_xxx",
     "url": "https://checkout.stripe.com/pay/cs_xxx"
   }
   ```

**環境変数**:
- `STRIPE_API_KEY`: Stripe APIキー（Secrets Managerから取得）
- `USER_POOL_ID`: Cognito User Pool ID（ユーザー情報取得用）

**必要な外部ライブラリ**:
- `stripe`: Stripe SDK
- `@aws-sdk/client-cognito-identity-provider`: Cognito SDK
- `@aws-sdk/client-secrets-manager`

**IAMポリシー**:
- Cognitoへの読み取り権限（`cognito-idp:AdminGetUser`）
- Secrets Managerからの読み取り権限

**タイムアウト**: 30秒

**メモリ**: 256MB

#### 2.3.3. サブスクリプションキャンセル

   ```json
   {
     "platformType": "stripe" | "apple" | "google",
     "subscriptionId": "sub_xxx",
     "cancelImmediately": true | false,  // 即時キャンセルか期限終了時キャンセルか
   ```

   - **Google**: `purchases.subscriptions.cancel`を呼び出し
3. 結果を返す:
   ```json
   {
     "success": true,
     "canceledAt": "2025-11-12T00:00:00Z",
     "serviceEndDate": "2025-12-12T00:00:00Z"  // サービス終了日
   }
   ```

**環境変数**: 各プラットフォームのAPIキー

**必要な外部ライブラリ**: 各プラットフォームのSDK

**IAMポリシー**: Secrets Manager読み取り権限

### 2.4. ユーティリティ

#### 2.4.1. プラットフォーム種別判定
**ファイル**: `packages/cdk/lambda/billing/payment-gateway/utils/platformDetector.ts`

**説明**: これはLambda関数ではなく、共通ユーティリティモジュールです。他の関数から`import`して使用します。

**提供する関数**:
```typescript
export function detectPlatformFromReceipt(receipt: string): 'stripe' | 'apple' | 'google' | null
```

**処理内容**:
- レシート文字列のフォーマットから、どのプラットフォームのものか判定する
- 例: `sub_xxx` → Stripe、JWSフォーマット → Apple、Base64エンコード → Google

---

#### 2.4.2. Webhook署名検証
**ファイル**: `packages/cdk/lambda/billing/payment-gateway/utils/signatureVerifier.ts`

**説明**: 共通ユーティリティモジュール。

**提供する関数**:
```typescript
export function verifyStripeSignature(payload: string, signature: string, secret: string): boolean
export function verifyAppleJws(jws: string): Promise<boolean>
```

**処理内容**:
- Stripe: HMAC-SHA256でペイロードとシークレットからハッシュを計算し、ヘッダーの署名と比較
- Apple: JWS検証（Appleのルート証明書で検証）

---

#### 2.4.3. イベント重複チェック
**ファイル**: `packages/cdk/lambda/billing/payment-gateway/utils/eventDeduplicator.ts`

**説明**: 共通ユーティリティモジュール。

**提供する関数**:
```typescript
export async function isDuplicateEvent(eventId: string, tenantId: string): Promise<boolean>
```

**処理内容**:

## 9. マルチテナント対応の考慮事項

### 9.1. Lambda関数の扱い（共通リソース）

**方針**: すべてのLambda関数を共通リソースとして配置し、環境変数で`TENANT_ID`を受け取ることでテナントを識別します。

**理由**:
- Lambda関数は状態を持たないため、共通リソースとして管理できます
- テナント数が増えてもLambda関数の管理コストが増えません
- コードのデプロイが一元化されます

**テナント識別の方法**:
1. Webhookエンドポイント: URLパスに`tenantId`を含める（例: `/billing/webhook/stripe/{tenantId}`）、またはAPI Gatewayのステージ変数で設定
2. 決済操作関数: Cognitoユーザーのカスタム属性から`tenantId`を取得
3. レシート検証関数: 呼び出し元から`tenantId`を受け取る

---

### 9.2. DynamoDBテーブルの扱い（テナント専用リソース）

**方針**: Webhookイベントログとレシート検証キャッシュはテナント専用DynamoDBテーブルとして作成します。

**理由**:
- データの完全な分離が保証されます
- テナントごとに異なる課金プラットフォーム設定を持つため、データを混在させないことが重要です
- TTL設定やキャパシティモードをテナントごとに調整できます

**テーブル名の命名規則**: `{tenantId}-payment-gateway-{table-type}`

---

### 9.3. Webhookエンドポイントの分離戦略

**推奨**: 初期は共通Webhookエンドポイントを使用し、URLパスまたはクエリパラメータでテナントを識別します。

**共通エンドポイントの実装例**:
```
POST /billing/webhook/stripe?tenantId=tenant-xxx
```

または

```
POST /billing/webhook/stripe/tenant-xxx
```

**将来的な移行**: テナント数が増加した場合、テナント別のWebhookエンドポイントへの移行を検討します（`tenant-a.api.example.com/webhook/stripe` など）。

## 11. エラーハンドリングとリトライ

### 11.1. Webhook受信時のエラーハンドリング

**処理失敗時の動作**:
1. Lambda関数内でエラーが発生 → 例外をスロー
2. API Gatewayが5xxエラーを返す
3. 決済プラットフォーム側が自動リトライ（指数バックオフ）
4. 最大24時間リトライ（Stripeの場合）

**冪等性の保証**:
- イベントIDによる重複チェックで、同じイベントを複数回処理しないようにします

---

### 11.2. EventBridgeのリトライとDLQ

**リトライ設定**:
```typescript
new events.Rule(this, 'StripeWebhookRule', {
  eventBus: eventBus,
  eventPattern: { /* ... */ },
  targets: [
    new targets.LambdaFunction(orchestratorFunction, {
      retryAttempts: 3,
      maxEventAge: Duration.hours(2),
      deadLetterQueue: dlqQueue,
    }),
  ],
});
```

**デッドレターキュー（DLQ）**:
- 失敗したイベントをSQSキューに送信
- 管理者が手動で確認・再処理できるようにします

---

### 11.3. レシート検証のリトライとフォールバック

**リトライロジック**:
1. 検証失敗（ネットワークエラー等） → キャッシュを確認
2. キャッシュヒット＆TTL有効 → キャッシュ結果を返す
3. キャッシュミス → 2秒待機して再検証を1回試行
4. 再検証も失敗 → 検証失敗結果を返す（検証保留中状態に遷移）

**キャッシュのTTL**: 24時間

```typescript
receiveStripeWebhookFunction.addToRolePolicy(

      'dynamodb:PutItem',

  })
);

receiveStripeWebhookFunction.addToRolePolicy(
  new PolicyStatement({
    effect: Effect.ALLOW,
    actions: ['events:PutEvents'],
    resources: [eventBus.eventBusArn],

receiveStripeWebhookFunction.addToRolePolicy(
  new PolicyStatement({
    effect: Effect.ALLOW,

    resources: [stripeWebhookSecretArn],
  })
);
```

## まとめ

この資料では、`Stripe/Apple/Googleの決済システムとのやり取りを一本化する`責務の技術実装構成を明示しました。主なポイントは以下の通りです：

- **Lambda関数**: Webhookエンドポイント（3つ）、レシート検証、決済操作実行など、合計10個程度のLambda関数を追加
- **DynamoDB**: テナント専用テーブルを2つ追加（Webhookイベントログ、レシート検証キャッシュ）
- **API Gateway**: Webhookエンドポイントと決済操作エンドポイントを定義
- **EventBridge**: Webhookイベントを統括責務へ配信
- **Secrets Manager**: 各プラットフォームのAPIキーとシークレットを管理
- **マルチテナント**: Lambda関数は共通リソース、DynamoDBはテナント専用リソース
- **商品ID→プランID変換**: 既存のPlanRepositoryを活用

実装時にはこの構成を参考にしながら、具体的なコードを記述していくことになります。
