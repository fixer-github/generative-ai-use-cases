細屋の率直な意見

```
まず、プランのバージョン管理を行うのは違うと思っているんですよね
システム管理者向けの内部的な名称がつけられるような形にして、命名規則を決めるなりでいい感じで運用できると思います。
あと、イミュータブルってほどではないのですが、基本的に一度作ったプランは変更したりしないような感じの扱いになると思います。
例えばStandardプランで使える機能などがアップグレードするとなった時、以前のStandardプランとは別でStandardプランを作成するような形にします。
また、価格を変更するとなった際にも、別のStandardプランを作成します。
この二つのStandardプランは互いに干渉せず、データ上では完全に別のプランとして扱われるイメージです
これは、価格変更時やプランの提供する機能の変更などが行われた際、既存の加入ユーザに対し、グランドファザリングを適用するのか、それとも自動的に加入ユーザを移行するのかというのを柔軟に対応する必要があることが影響していると思っているからです
グランドファザリングをするのであれば、以前のStandardプランは「新規加入不可」のステータスに変更すれば良いし、価格据え置きで機能をアップグレードする際には、新しいStandardプランへユーザを移動させた上で、加入者0人になった古いStandardプランを廃止扱いにすればいいわけです。
また、プランはプラットフォームごとに別々で定義されるものと思っています。
Free, Standard, Proの二つのプランがあるとした場合、Stripe経由で購入可能なStandard, Proプランが存在し、iOSアプリ版で購入可能なStandard, Proプランが別で存在します。
Priceテーブルというものも必要な気がしてきました。いや、これが必要なのかは疑問が残るところかもしれませんけど
これは課金プラットフォーム側で作成された課金単位（Stripe BillingでいうところのProductなど）を表すものです。
プランとしてのデータには、このPriceテーブルのアイテムへの参照が含まれることになるイメージです。
ちなみに、これは実際のところStripe BillingなどのもつProduct Idをそのまま参照しても良いのでは？とも思っています。
```
