# データベーステーブル定義

## 概要

このドキュメントでは、プラン・サブスクリプション機能を実現するために必要な3つのデータベーステーブルの定義を説明します。

これらのテーブルは、以下の情報を記録するために使われます:
- どのようなプランが存在するか（プランテーブル）
- ユーザがどのサブスクリプション契約をしているか（サブスクリプションテーブル）
- ユーザに現在どのプランが適用されているか（ユーザプラン適用テーブル）

---

## プランテーブル

### 目的

このテーブルは、システムで提供される全てのプラン（例: Freeプラン、Standardプラン、Proプラン）の定義を保存します。

プランは一度作成したら基本的に変更せず、機能や価格を変更したい場合は新しいプランを作成します。これにより、既存のユーザに影響を与えずに、新しい条件でプランを提供できるようにします。

### カラム定義

#### plan_id（プランID）
- **データ型**: UUID
- **説明**: プランを一意に識別するためのIDです。システムが自動的に生成します。
- **制約**: 主キー（必須、重複不可）

#### internal_name（内部名称）
- **データ型**: 文字列（最大255文字）
- **説明**: システム管理者がプランを判別するための名前です。例えば「standard_2025_jan_stripe」や「pro_2025_feb_ios」のように、プラン種別、作成時期、プラットフォームが分かる名前をつけます。
- **制約**: 必須、重複不可

#### display_name（表示名）
- **データ型**: 文字列（最大255文字）
- **説明**: ユーザに表示されるプランの名前です。例えば「Standardプラン」や「Proプラン」のように、ユーザが理解しやすい名前を設定します。
- **制約**: 必須

#### description（説明）
- **データ型**: テキスト
- **説明**: プランの詳しい説明文です。ユーザに対して「このプランでは何ができるか」を説明するために使います。
- **制約**: 任意（NULLを許可）

#### platform_type（プラットフォーム種別）
- **データ型**: 文字列（最大50文字）
- **説明**: このプランがどの課金プラットフォームで提供されるかを示します。
  - `stripe`: Stripe Billing経由で提供されるプラン
  - `apple`: Apple App Store経由で提供されるプラン
  - `google`: Google Play Store経由で提供されるプラン
  - `internal`: 課金プラットフォームを経由しないプラン（Freeプランや、管理者が手動で付与するプランなど）
- **制約**: 必須

#### platform_product_id（プラットフォーム商品ID）
- **データ型**: 文字列（最大255文字）
- **説明**: 課金プラットフォーム側で作成された商品やPriceのIDです。
  - Stripeの場合: `price_xxxxx`（Stripe Price ID）
  - Appleの場合: `com.example.standard_monthly`（Product ID）
  - Googleの場合: `standard_monthly`（Product ID）
  - internalプラットフォームの場合: NULLまたは空文字列
- **制約**: 任意（NULLを許可）

#### permissions（権限・制限定義）
- **データ型**: JSON
- **説明**: このプランで利用できる機能と、利用回数の制限を定義したデータです。JSON形式で柔軟に記録できるようにしています。
- **JSON構造の例**:
  ```json
  {
    "features": ["feature_a", "feature_b", "feature_c"],
    "limits": {
      "model_a": {
        "type": "unlimited"
      },
      "model_b": {
        "type": "daily",
        "count": 100
      },
      "model_c": {
        "type": "monthly",
        "count": 400
      }
    }
  }
  ```
- **JSON構造の説明**:
  - `features`: このプランで使える機能の名前のリスト
  - `limits`: 各リソース（モデルなど）に対する利用制限
    - `type`: 制限の種類（`unlimited`は無制限、`daily`は一日ごと、`monthly`は一ヶ月ごと）
    - `count`: 制限回数（`unlimited`の場合は不要）
- **制約**: 必須

#### status（ステータス）
- **データ型**: 文字列（最大50文字）
- **説明**: このプランの現在の状態を表します。
  - `active`: 新規ユーザが加入できる状態
  - `closed_to_new`: 既存ユーザは継続できるが、新規ユーザは加入できない状態（グランドファザリング対応）
  - `deprecated`: 廃止された状態（加入者が0人になった後に設定）
- **制約**: 必須

#### created_at（作成日時）
- **データ型**: タイムスタンプ
- **説明**: このプランがシステムに登録された日時です。
- **制約**: 必須

#### updated_at（更新日時）
- **データ型**: タイムスタンプ
- **説明**: このプランの情報が最後に更新された日時です。
- **制約**: 必須

### インデックス

以下のインデックスを作成して、検索を高速化します:

1. **internal_nameによる検索**: システム管理者が内部名称で特定のプランを検索する際に使います
2. **platform_typeとstatusによる検索**: 特定のプラットフォームで提供中のプラン一覧を取得する際に使います（例: 「Stripeで新規加入可能なプラン一覧」）
3. **platform_product_idによる検索**: Webhookイベント処理で、プラットフォーム側の商品IDからプランを特定する際に使います

## サブスクリプションテーブル

### 目的

このテーブルは、ユーザが課金プラットフォーム経由で契約したサブスクリプション（定期購読）の情報を保存します。

サブスクリプションには「いつからいつまで有効か」「支払いは成功しているか」といった状態が含まれます。

### カラム定義

#### subscription_id（サブスクリプションID）
- **データ型**: UUID
- **説明**: サブスクリプションを一意に識別するためのIDです。システムが自動的に生成します。
- **制約**: 主キー（必須、重複不可）

#### user_id（ユーザID）
- **データ型**: 文字列（最大255文字）
- **説明**: このサブスクリプションを契約しているユーザのIDです。
- **制約**: 必須

#### plan_id（プランID）
- **データ型**: UUID
- **説明**: このサブスクリプションで契約されているプランのIDです。プランテーブルのplan_idを参照します。
- **制約**: 必須、外部キー（プランテーブル.plan_idを参照）

#### platform_type（プラットフォーム種別）
- **データ型**: 文字列（最大50文字）
- **説明**: このサブスクリプションがどの課金プラットフォームで契約されたかを示します。
  - `stripe`: Stripe Billing
  - `apple`: Apple App Store
  - `google`: Google Play Store
- **制約**: 必須

#### platform_subscription_id（プラットフォーム側サブスクリプションID）
- **データ型**: 文字列（最大255文字）
- **説明**: 課金プラットフォーム側で管理されているサブスクリプションのIDです。
  - Stripeの場合: `sub_xxxxx`（Subscription ID）
  - Appleの場合: `original_transaction_id`
  - Googleの場合: `purchaseToken`
- **制約**: 必須、重複不可

#### subscription_status（サブスクリプション状態）
- **データ型**: 文字列（最大50文字）
- **説明**: サブスクリプションの現在の状態を表します。
  - `active`: 有効（支払いが成功し、サービスを利用できる状態）
  - `pending_verification`: 検証保留中（レシート検証が失敗し、管理者の確認待ち）
  - `past_due`: 支払い失敗（課金プラットフォームが自動的に再試行中）
  - `canceled`: キャンセル済み（ユーザまたはシステムによって解約された）
  - `expired`: 期限切れ（有効期限が過ぎた）
- **制約**: 必須

#### current_period_start（現在の期間開始日時）
- **データ型**: タイムスタンプ
- **説明**: 現在のサブスクリプション期間がいつから始まったかを示します。
- **制約**: 必須

#### current_period_end（現在の期間終了日時）
- **データ型**: タイムスタンプ
- **説明**: 現在のサブスクリプション期間がいつ終わるかを示します。この日時が来ると、課金プラットフォームが次回の支払いを試みます。
- **制約**: 必須

#### cancel_at_period_end（期限終了時にキャンセル）
- **データ型**: 真偽値（Boolean）
- **説明**: このサブスクリプションが期限終了時にキャンセルされる予定かどうかを示します。
  - `true`: ユーザが解約を申し込んでおり、現在の期間終了時にキャンセルされます
  - `false`: 自動更新が有効で、次の期間も継続します
- **制約**: 必須

#### created_at（作成日時）
- **データ型**: タイムスタンプ
- **説明**: このサブスクリプションがシステムに登録された日時です。
- **制約**: 必須

#### updated_at（更新日時）
- **データ型**: タイムスタンプ
- **説明**: このサブスクリプションの情報が最後に更新された日時です。
- **制約**: 必須

### インデックス

以下のインデックスを作成して、検索を高速化します:

1. **user_idによる検索**: 特定のユーザのサブスクリプション情報を取得する際に使います
2. **platform_subscription_idによる検索**: Webhookイベント処理で、プラットフォーム側のIDから該当するサブスクリプションを特定する際に使います
3. **subscription_statusによる検索**: 特定の状態のサブスクリプション一覧を取得する際に使います（例: 「検証保留中のサブスクリプション一覧」）
4. **current_period_endによる検索**: 期限切れチェックバッチ処理で使います

## ユーザプラン適用テーブル

### 目的

このテーブルは、各ユーザに現在どのプランが適用されているかを記録します。

プランが適用される方法には複数のパターンがあります:
- サブスクリプション経由（課金プラットフォームでの購入）
- デフォルトプラン（新規登録時に自動適用）
- トライアル（期間限定の試用）
- キャンペーン（期間限定のキャンペーン適用）
- 手動付与（管理者が特別に付与）

### カラム定義

#### application_id（適用ID）
- **データ型**: UUID
- **説明**: プラン適用を一意に識別するためのIDです。システムが自動的に生成します。権限を剥奪する際に、このIDを使って「どの適用によって付与された権限か」を特定します。
- **制約**: 主キー（必須、重複不可）

#### user_id（ユーザID）
- **データ型**: 文字列（最大255文字）
- **説明**: プランが適用されているユーザのIDです。
- **制約**: 必須

#### plan_id（プランID）
- **データ型**: UUID
- **説明**: ユーザに適用されているプランのIDです。プランテーブルのplan_idを参照します。
- **制約**: 必須、外部キー（プランテーブル.plan_idを参照）

#### application_source（適用ソース）
- **データ型**: 文字列（最大50文字）
- **説明**: このプランがどのような方法で適用されたかを示します。
  - `subscription`: サブスクリプション経由での適用
  - `default`: デフォルトプランとしての適用
  - `trial`: トライアルとしての適用
  - `campaign`: キャンペーンとしての適用
  - `manual`: 管理者による手動付与
- **制約**: 必須

#### application_source_id（適用ソースID）
- **データ型**: 文字列（最大255文字）
- **説明**: 適用ソースに関連するIDです。
  - `subscription`の場合: サブスクリプションテーブルのsubscription_id
  - `campaign`の場合: キャンペーンID
  - `default`, `trial`, `manual`の場合: NULLまたは任意の識別情報
- **制約**: 任意（NULLを許可）

#### application_status（適用状態）
- **データ型**: 文字列（最大50文字）
- **説明**: このプラン適用の現在の状態を表します。
  - `active`: 有効（ユーザはこのプランの権限を使える状態）
  - `scheduled_termination`: 解約予定（期限まで有効だが、期限後は自動的に終了する）
  - `expired`: 期限切れ（既に無効になった）
- **制約**: 必須

#### valid_from（有効期間開始日時）
- **データ型**: タイムスタンプ
- **説明**: このプラン適用がいつから有効になるかを示します。
- **制約**: 必須

#### valid_until（有効期間終了日時）
- **データ型**: タイムスタンプ
- **説明**: このプラン適用がいつまで有効かを示します。
  - サブスクリプション経由の場合: サブスクリプションの有効期限と同期
  - トライアル・キャンペーンの場合: それぞれの期限
  - デフォルトプラン・手動付与で無期限の場合: 遠い未来の日時（例: 2099年12月31日）またはNULL
- **制約**: 任意（NULLを許可）

#### created_at（作成日時）
- **データ型**: タイムスタンプ
- **説明**: このプラン適用がシステムに登録された日時です。
- **制約**: 必須

#### updated_at（更新日時）
- **データ型**: タイムスタンプ
- **説明**: このプラン適用の情報が最後に更新された日時です。
- **制約**: 必須

### インデックス

以下のインデックスを作成して、検索を高速化します:

1. **user_idとapplication_statusによる検索**: 特定のユーザの有効なプラン適用を取得する際に使います（最も頻繁に使われるクエリ）
2. **application_source_idによる検索**: サブスクリプションIDからプラン適用を特定する際に使います
3. **valid_untilとapplication_statusによる検索**: 期限切れチェックバッチ処理で、期限が近いまたは過ぎたプラン適用を検索する際に使います

## テーブル間の関連

### プランテーブルとサブスクリプションテーブルの関連

サブスクリプションテーブルのplan_idカラムは、プランテーブルのplan_idカラムを参照します。これを「外部キー制約」と呼びます。

この制約により、以下が保証されます:
- 存在しないプランIDを持つサブスクリプションは作成できません
- サブスクリプションが参照しているプランは削除できません

### プランテーブルとユーザプラン適用テーブルの関連

ユーザプラン適用テーブルのplan_idカラムは、プランテーブルのplan_idカラムを参照します。

この制約により、以下が保証されます:
- 存在しないプランIDを持つプラン適用は作成できません
- プラン適用が参照しているプランは削除できません

### サブスクリプションテーブルとユーザプラン適用テーブルの関連

ユーザプラン適用テーブルのapplication_source_idカラムは、application_sourceが`subscription`の場合にサブスクリプションテーブルのsubscription_idを参照します。

ただし、この関連は外部キー制約としては設定しません。理由は以下の通りです:
- application_source_idは、適用ソースによって参照先が異なります（サブスクリプションID、キャンペーンID、NULLなど）
- 1つのカラムで複数のテーブルを参照することはできないため、外部キー制約を設定できません
- 代わりに、アプリケーション層で整合性を保証します

## 具体例

### 例1: Stripe経由でStandardプランを購入したユーザ

**プランテーブル**:
- plan_id: `123e4567-e89b-12d3-a456-426614174000`
- internal_name: `standard_2025_jan_stripe`
- display_name: `Standardプラン`
- platform_type: `stripe`
- platform_product_id: `price_1234567890`
- permissions: `{"features": ["feature_a", "feature_b"], "limits": {"model_c": {"type": "monthly", "count": 400}}}`
- status: `active`

**サブスクリプションテーブル**:
- subscription_id: `223e4567-e89b-12d3-a456-426614174001`
- user_id: `user_abc123`
- plan_id: `123e4567-e89b-12d3-a456-426614174000`（上記プランを参照）
- platform_type: `stripe`
- platform_subscription_id: `sub_1234567890`
- subscription_status: `active`
- current_period_start: `2025-01-01 00:00:00`
- current_period_end: `2025-02-01 00:00:00`
- cancel_at_period_end: `false`

**ユーザプラン適用テーブル**:
- application_id: `323e4567-e89b-12d3-a456-426614174002`
- user_id: `user_abc123`
- plan_id: `123e4567-e89b-12d3-a456-426614174000`（上記プランを参照）
- application_source: `subscription`
- application_source_id: `223e4567-e89b-12d3-a456-426614174001`（上記サブスクリプションを参照）
- application_status: `active`
- valid_from: `2025-01-01 00:00:00`
- valid_until: `2025-02-01 00:00:00`

### 例2: 新規登録したユーザにFreeプランが自動適用される

**プランテーブル**:
- plan_id: `423e4567-e89b-12d3-a456-426614174003`
- internal_name: `free_default`
- display_name: `Freeプラン`
- platform_type: `internal`
- platform_product_id: NULL
- permissions: `{"features": ["feature_a"], "limits": {"model_a": {"type": "daily", "count": 10}}}`
- status: `active`

**サブスクリプションテーブル**:
（エントリなし - デフォルトプランはサブスクリプションを経由しません）

**ユーザプラン適用テーブル**:
- application_id: `523e4567-e89b-12d3-a456-426614174004`
- user_id: `user_xyz789`
- plan_id: `423e4567-e89b-12d3-a456-426614174003`（Freeプランを参照）
- application_source: `default`
- application_source_id: NULL
- application_status: `active`
- valid_from: `2025-01-10 12:00:00`（ユーザ登録日時）
- valid_until: NULL（無期限）

### 例3: ユーザが期限終了時解約を申し込んだ場合

サブスクリプションの解約申し込み後、以下のように更新されます:

**サブスクリプションテーブル**:
- subscription_status: `active`（まだ有効期間中）
- cancel_at_period_end: `true`（期限終了時にキャンセル予定）

**ユーザプラン適用テーブル**:
- application_status: `scheduled_termination`（解約予定）
- valid_until: `2025-02-01 00:00:00`（期限はそのまま）

期限が到達すると、定期バッチ処理により以下のように更新されます:

**サブスクリプションテーブル**:
- subscription_status: `canceled`

**ユーザプラン適用テーブル**:
- application_status: `expired`

そして、ユーザはデフォルトプラン（Freeプラン）に自動的に戻されます（新しいユーザプラン適用レコードが作成されます）。

## まとめ

この3つのテーブルにより、以下が実現できます:

1. **プランテーブル**: どのようなプランが存在するかを管理し、機能や価格の変更時に新しいプランを作成することでグランドファザリングに対応します
2. **サブスクリプションテーブル**: ユーザの課金契約の状態を正確に記録し、課金プラットフォームとの同期を行います
3. **ユーザプラン適用テーブル**: ユーザに現在どのプランが適用されているかを管理し、様々な適用方法（サブスクリプション、デフォルト、トライアル等）に対応します

これらのテーブルは外部キー制約によってデータの整合性を保証しつつ、柔軟な運用を可能にする設計となっています。
