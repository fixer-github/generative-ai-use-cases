# インフラ構成

## 概要

この資料では、「プラン・サブスクリプションのデータモデルを管理する」という責務を実現するために必要なAWSリソースについて説明します。

結論を先に述べると、この責務を実現するために必要なAWSリソースは**RDS（リレーショナルデータベース）のみ**です。

---

## この責務はどのように実装されるか

「プラン・サブスクリプションのデータモデルを管理する」という責務は、独立したAWSサービスとして実装されるのではなく、**コード（クラスやモジュール）として実装されます**。

具体的には、以下のような形で実装されます：

### 実装の形態

この責務は、**データアクセス層（Repository層またはDAO層）**として実装されます。これは、以下のような意味です：

1. **Repositoryクラスまたはモジュールを作成します**
   - 例：`PlanRepository`クラス、`SubscriptionRepository`クラス、`UserPlanApplicationRepository`クラス

2. **これらのクラスは、他の責務のLambda関数から呼び出されます**
   - 例：「購入・変更・解約などの複数ステップの処理を統括する」責務がLambda関数として実装される際、その中で`SubscriptionRepository`を使ってデータベースにアクセスします

3. **Repositoryクラスは、RDSに接続してデータを読み書きします**
   - データベースへの接続、SQL実行、トランザクション管理などを担当します

### 具体的なイメージ

以下のような流れで動作します：

1. ユーザが「プランを購入したい」というリクエストを送ります
2. API Gatewayがリクエストを受け取り、Lambda関数を起動します（この部分は「購入・変更・解約などの複数ステップの処理を統括する」責務）
3. Lambda関数の中で、`SubscriptionRepository.create()`というメソッドを呼び出します
4. `SubscriptionRepository`が、RDSに接続してサブスクリプション情報をデータベースに保存します
5. 保存が成功したら、Lambda関数に制御が戻り、処理を続けます

このように、「プラン・サブスクリプションのデータモデルを管理する」責務は、**他の責務の中で使われるライブラリのような存在**です。

---

## 必要なAWSリソース

### RDS（リレーショナルデータベースサービス）

**目的**：プラン、サブスクリプション、ユーザプラン適用のデータを永続的に保存するために必要です。

**何を保存するか**：

- プランテーブル（どのようなプランが存在するか）
- サブスクリプションテーブル（ユーザがどのサブスクリプション契約をしているか）
- ユーザプラン適用テーブル（ユーザに現在どのプランが適用されているか）
- 履歴テーブル（サブスクリプション状態変更履歴、プラン適用履歴、支払い履歴）

**使用するデータベースエンジン**：

- PostgreSQLまたはMySQL

**なぜ必要か**：
データを永続的に保存する場所がなければ、ユーザのプラン情報やサブスクリプション情報を記録できません。RDSは、データの整合性を保証する外部キー制約やトランザクション機能を提供するため、この責務に適しています。

---

## 不要なAWSリソースとその理由

以下のAWSリソースは、「プラン・サブスクリプションのデータモデルを管理する」責務では**不要**です。

### Lambda関数：不要

**理由**：この責務は、他の責務のLambda関数の中で呼び出されるコード（Repositoryクラス）として実装されるため、独立したLambda関数を作る必要はありません。

**誰が作るか**：「購入・変更・解約などの複数ステップの処理を統括する」責務や、「ユーザのサブスクリプション契約の状態を記録・管理する」責務など、他の責務がLambda関数を作成します。

### API Gateway：不要

**理由**：この責務は、直接外部からアクセスされるAPIエンドポイントを持ちません。他の責務のLambda関数から内部的に呼び出されるだけです。

**誰が作るか**：「ユーザ向けセルフサービスインターフェースを提供する」責務や、「管理者向け運用管理インターフェースを提供する」責務が、API Gatewayを作成します。

### VPC、サブネット、セキュリティグループ：不要

**理由**：これらは、RDSを構築する際に一緒に作成されます。この責務は、既に存在するRDSを使う側なので、新たに作る必要はありません。

**誰が作るか**：RDSを構築する責務（例えば、全体のインフラを構築する責務）が作成します。

### EventBridge、SQS、DynamoDB：不要

**理由**：これらは、他の責務で使われるAWSリソースです。この責務は、データベースへのアクセスのみを担当するため、不要です。

**誰が使うか**：

- EventBridge：「Webhookイベントを受信層からビジネスロジック層へ配信する」責務
- SQS：「エラー時の再試行、監視、ログ記録でシステムの安定稼働を保証する」責務
- DynamoDB：使われない（この課金システムではRDBを使用）

## 他の責務との関係

「プラン・サブスクリプションのデータモデルを管理する」責務は、以下のような関係性で他の責務と連携します：

### この責務を呼び出す側（依存している責務）

以下の責務が、この責務のRepositoryクラスを使ってデータベースにアクセスします：

1. **ユーザのサブスクリプション契約の状態を記録・管理する**
   - `SubscriptionRepository`を使って、サブスクリプション情報を保存・更新します

2. **どんなプランがあって、誰がどのプランに入っているかを管理する**
   - `PlanRepository`と`UserPlanApplicationRepository`を使って、プラン情報とプラン適用情報を管理します

3. **購入・変更・解約などの複数ステップの処理を統括する**
   - 複数のRepositoryを組み合わせて、トランザクション内で一貫性のあるデータ操作を行います

これらの責務は、それぞれLambda関数として実装されます。その中で、Repositoryクラスを呼び出してRDSにアクセスします。

### この責務が依存する側

この責務は、以下のリソースに依存します：

1. **RDS（PostgreSQL/MySQL等）**
   - データの永続化、トランザクション実行、外部キー制約の適用、クエリ実行を依頼します

## 実装時の注意点

### コードの配置場所

Repositoryクラスは、以下のいずれかの方法で配置します：

1. **共有ライブラリとして実装する**
   - 複数のLambda関数から参照できるように、共通のディレクトリに配置します
   - 例：`src/repositories/PlanRepository.ts`

2. **Lambda Layersとして配置する**
   - 共通のコードをLambda Layersとしてパッケージ化し、複数のLambda関数から参照できるようにします
   - ただし、デプロイの複雑さが増すため、最初は共有ライブラリとして実装する方が簡単です

### データベース接続の管理

Lambda関数からRDSに接続する際は、以下の点に注意が必要です：

1. **接続プールを使用する**
   - Lambda関数は複数回呼び出されるため、毎回新しいデータベース接続を作成すると非効率です
   - 接続プールを使用して、接続を再利用します

2. **VPC設定が必要**
   - RDSはVPC内に配置されるため、Lambda関数もVPC内に配置する必要があります
   - ただし、これは「この責務」が設定するのではなく、Lambda関数を作成する責務が設定します

3. **認証情報の管理**
   - データベースのユーザー名とパスワードは、AWS Secrets Managerに保存します
   - Repositoryクラスは、Secrets Managerから認証情報を取得してRDSに接続します

---

## まとめ

「プラン・サブスクリプションのデータモデルを管理する」責務は：

1. **独立したAWSリソースではなく、コード（Repositoryクラス）として実装されます**
2. **必要なAWSリソースは、RDSのみです**
3. **Lambda、API Gateway、VPC等は、他の責務で既に作られるため不要です**
4. **他の責務のLambda関数から呼び出されるライブラリとして機能します**
