# プラン変更機能の実装方針

## 現在の状況

現在のシステムでは、ユーザがプランに契約することはできますが、プランを変更することはできません。具体的には次のような状態です。

### すでにできること

- 新しいユーザがプランに加入する（初めての契約）
- プランの一覧を見る
- 自分が今どのプランに入っているかを確認する
- 支払い処理を完了する
- 毎月の自動更新を行う

### まだできないこと

- すでにプランに入っているユーザが別のプランに変更する
- プランを解約する操作をユーザ画面から行う
- プランのアップグレード・ダウングレードを行う

## プラン変更とは何か

プラン変更とは、ユーザが現在契約しているプランから別のプランに移行することです。プラン変更には大きく分けて2つのパターンがあります。

### アップグレード

より高機能・高価格のプランに変更することです。たとえば、FreeプランからStandardプランに変更したり、StandardプランからPremiumプランに変更したりすることです。

アップグレードの場合、ユーザはすぐに新しいプランの機能を使いたいと考えているため、変更は即座に反映されるべきです。

### ダウングレード

より低機能・低価格のプランに変更することです。たとえば、PremiumプランからStandardプランに変更したり、StandardプランからFreeプランに変更したりすることです。

ダウングレードの場合、ユーザがすでに支払った料金を無駄にしないよう、現在の契約期間が終わるまでは現在のプランを使い続けられるようにするのが一般的です。

## プラン変更の実現方法

プラン変更を実現するためには、次の3つの要素を考える必要があります。

### 1. 技術的な実現方法

現在のシステムは、すでにサブスクリプション管理とプラン管理を分離して設計されています。この設計を活かして、次のような方法でプラン変更を実現します。

**方法1: 既存サブスクリプションの更新（推奨）** 採用

- 現在のサブスクリプションを維持したまま、プランだけを変更する
- Stripeの場合、Subscription Update APIを使用して、同じサブスクリプションIDのままプランを変更する
- Apple/Googleの場合も、同様に既存のサブスクリプションを更新する

この方法の利点：

- サブスクリプションの履歴が途切れない
- 支払いサイクルが維持される
- 課金プラットフォーム側での管理がシンプル

**方法2: サブスクリプションの置き換え** 不採用

- 現在のサブスクリプションを解約して、新しいサブスクリプションを作成する
- 解約と新規契約を同時に行い、サービスの中断を防ぐ

この方法の欠点：

- サブスクリプションの履歴が途切れる
- 支払いサイクルがリセットされる可能性がある
- 処理が複雑になりエラーが起きやすい

### 2. 料金の調整方法

プラン変更時の料金調整には、次の2つのパターンがあります。

**アップグレード時の料金調整**

- 新しいプランと古いプランの差額を計算する
- 残りの期間分の差額をすぐに請求する（日割り計算）
- 次回の請求から新しいプランの料金を適用する

たとえば、月額1000円のプランから月額2000円のプランに、月の半分が経過した時点で変更した場合：

- 差額1000円の半月分である500円をすぐに請求
- 次月からは2000円を請求

Stripeではこれを自動で処理することができます

```
// Stripeが自動で日割り計算
await stripe.subscriptions.update(subscriptionId, {
  items: [{
    id: subscription.items.data[0].id,
    price: 'price_new_plan',
  }],
  proration_behavior: 'create_prorations', // 自動で日割り
});
```

**ダウングレード時の料金調整**

- すでに支払った料金は返金しない
- 次回の更新日まで現在のプランを継続する
- 次回の更新時に新しいプランに切り替える

たとえば、月額2000円のプランから月額1000円のプランに変更した場合：

- 今月の残りの期間は2000円のプランのまま使える
- 来月から1000円のプランに切り替わる

Stripeでは下記を用いることができます。

```
// Subscription Schedulesで将来の変更を予約
const schedule = await stripe.subscriptionSchedules.create({
  from_subscription: subscriptionId,
  phases: [
    {
      items: [{ price: currentPriceId }],
      end_date: nextBillingDate,
    },
    {
      items: [{ price: downgradePriceId }],
      iterations: 12, // 12ヶ月継続など
    },
  ],
});

```

### 3. ユーザ体験の設計

プラン変更をスムーズに行うために、次のようなユーザ体験を提供します。

**プラン選択画面での表示**

- 現在のプランには「現在利用中」というバッジを表示（実装済み）
- 他のプランには「変更する」または「アップグレード」「ダウングレード」というボタンを表示
- 変更後の料金がどうなるかを明確に表示

**変更確認画面**

- 変更前と変更後のプランの比較表を表示
- 料金の変更内容を明確に表示（次回請求額、差額など）
- アップグレードの場合は「すぐに変更されます」と表示
- ダウングレードの場合は「次回更新時に変更されます」と表示

**変更完了後の通知**

- メールで変更完了を通知
- 新しいプランの内容と次回請求日を案内
- 領収書や請求書へのアクセス方法を案内

## 解約機能の実装

プラン変更と同時に、解約機能も実装する必要があります。解約には次の2つの方法があります。

### ~~即時解約~~ 不採用

- すぐにサービスを停止する
- 残りの期間の料金は返金しない（または返金する場合は返金処理を行う）
- ユーザはFreeプラン（デフォルトプラン）に戻る

### 期限終了時解約（推奨） 採用

- 現在の契約期間の終了まではサービスを継続する
- 次回の自動更新を停止する
- 契約期間終了後、自動的にFreeプラン（デフォルトプラン）に戻る

ほとんどのサブスクリプションサービスでは、期限終了時解約を採用しています。これは、ユーザがすでに支払った料金分のサービスを受けられるようにするためです。

## 実装の優先順位

プラン変更機能を段階的に実装する場合の優先順位は次のとおりです。

### 第1段階：解約機能の実装（必須）

まず、ユーザが自分でプランを解約できるようにします。これは、法的にも必要な機能です。

- 解約ボタンをUIに追加
- 解約確認画面を実装
- 期限終了時解約の処理を実装
- 解約完了通知を送信

### 第2段階：同一プラットフォーム内でのプラン変更

次に、Stripeで契約したユーザがStripe内で別のプランに変更できるようにします。

- プラン変更APIを実装
- アップグレード・ダウングレードの判定ロジックを実装
- 料金調整の処理を実装
- 変更確認画面を実装

### 第3段階：プラットフォームをまたぐプラン変更

最後に、異なるプラットフォーム間での変更に対応します（たとえば、Appleで契約したものをStripeに移行するなど）。

- プラットフォーム間の移行ロジックを実装
- 二重課金を防ぐ仕組みを実装
- 移行時の特別な通知を実装

## 注意すべき点

### 二重課金の防止

プラン変更時に最も注意すべきことは、二重課金を防ぐことです。特に次の場合に注意が必要です。

- 同時に複数のプランが有効になってしまう
- 解約と新規契約のタイミングがずれて、両方から請求される
- プラットフォームをまたぐ変更で、両方から請求される

### エラー処理

プラン変更は複数のステップからなる処理のため、途中でエラーが起きる可能性があります。

- 決済プラットフォームのAPIが失敗した場合
- ネットワークエラーが発生した場合
- 処理の途中でタイムアウトした場合

これらのエラーに対して、適切に処理を巻き戻したり、リトライしたりする仕組みが必要です。

### 監査とログ

プラン変更は課金に関わる重要な操作のため、すべての変更を記録する必要があります。

- 誰がいつどのプランに変更したか
- 変更前と変更後のプラン内容
- 料金の調整内容
- エラーが発生した場合の詳細

これらの情報は、後でトラブルが起きたときの調査や、会計処理のために必要になります。

## まとめ

プラン変更機能を実装するには、技術的な実装だけでなく、料金の調整方法やユーザ体験の設計も重要です。段階的に実装を進めることで、リスクを抑えながら確実に機能を追加していくことができます。

まずは解約機能から実装を始め、その後プラン変更機能を追加していくのが現実的な進め方です。各段階で十分なテストを行い、エラー処理や監査ログなどの運用面も含めて実装することで、安定した課金システムを構築できます。
