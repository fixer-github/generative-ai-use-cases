# 「購入・変更・解約などの複数ステップの処理を統括する」責務の技術実装詳細

## 1. 概要と位置づけ

### 1.1 この責務の役割

この責務は、ユーザーのプラン購入・変更・解約といった複数ステップのビジネスフローを統括する「オーケストレーター層」として機能します。既存の3つの責務実装（Payment Gateway、Plan Management、Subscription Management）を組み合わせて、エンドツーエンドのビジネスフローを実現します。

### 1.2 既存の実装との関係

```
既存実装:
- Payment Gateway (8 Lambda functions)
  - Webhook受信・署名検証・イベント配信
  - レシート検証
  - 決済操作（Checkout Session作成、サブスクリプション変更・キャンセル、請求書取得）

- Subscription Management (8 Lambda functions)
  - サブスクリプション情報のCRUD
  - 検証保留中サブスクリプションの承認・却下
  - プラットフォーム同期

- Plan Management (7 Lambda functions)
  - プラン定義のCRUD
  - プラン履歴管理
  - プランとサブスクリプションの統計情報取得

新規実装（今回）:
- Orchestrator (4 Lambda functions + EventBridge rules)
  - 購入フロー統括
  - プラン変更フロー統括
  - 解約フロー統括
  - Webhookイベント処理フロー統括
```

### 1.3 アーキテクチャパターン

- **イベント駆動型**: ユーザー操作（API呼び出し）とWebhookイベント（EventBridge経由）の2つのトリガー
- **ステートレス**: フロー実行状態はRDBとCloudWatch Logsに記録し、Lambda関数自体は状態を保持しない
- **Lambda-to-Lambda呼び出し**: 他の責務のLambda関数を直接呼び出し（SDK経由）
- **マルチテナント対応**: Cognito Identity Poolを使用したテナント分離とRDS IAM認証

## 3. Lambda関数の詳細仕様

### 3.1 購入フロー実行関数 (purchaseFlow.ts)

#### 責務
ユーザーがプランを購入する際の一連の処理を統括します。

#### トリガー
- API Gateway: `POST /billing/purchase`
- 認証: Cognitoオーソライザー必須

#### 入力パラメータ
```typescript
interface PurchaseRequest {
  tenantId: string;          // テナントID
  userId: string;            // ユーザーID
  planId: string;            // プランID
  platform: 'stripe' | 'apple' | 'google';  // 課金プラットフォーム
  receipt: string;           // レシート情報（プラットフォーム固有）
  paymentMethodId?: string;  // 支払い方法ID（Stripeの場合）
}
```

#### 処理フロー
1. **認証確認とプラン検証** (処理時間: ~100ms)
   - Cognitoトークンからユーザー情報を取得
   - Plan Management Serviceに問い合わせてプランの存在確認
   - プランが購入可能な状態（status: active）であることを確認

2. **フロー実行ログの初期化** (処理時間: ~50ms)
   - フロー実行IDを生成（UUID）
   - RDBに初期ログを記録（status: processing）

3. **レシート検証** (処理時間: 1-5秒)
   - Payment Gateway ServiceのverifyReceiptを呼び出し
   - 検証成功の場合: 次のステップへ
   - 検証失敗の場合:
     - キャッシュによるフォールバックを試行
     - フォールバックも失敗した場合: 検証保留フローへ分岐

4. **サブスクリプション記録** (処理時間: ~200ms)
   - Subscription Management ServiceのcreateSubscriptionを呼び出し
   - サブスクリプションID、プランID、有効期限などを記録

5. **プラン適用** (処理時間: ~300ms)
   - Plan Management ServiceのapplyPlanToUserを呼び出し
   - ユーザープラン適用テーブルに記録（適用ソース: subscription）

6. **権限付与** (処理時間: ~500ms)
   - Authorization ServiceのgrantPermissionsを呼び出し
   - OpenFGAに機能アクセス権限を登録
   - カウント機構に回数制限を登録

7. **フロー完了ログ記録** (処理時間: ~50ms)
   - RDBのフロー実行ログをstatus: completedに更新
   - 各ステップの実行結果を記録

8. **レスポンス返却**
   - 購入完了メッセージとサブスクリプション情報を返却

#### エラーハンドリング
- **検証保留フロー** (検証失敗時):
  1. Subscription Management Serviceでpending_verification状態のサブスクリプションを作成
  2. 管理者にアラート送信
  3. クライアントに保留中メッセージを返却

- **部分失敗時**:
  - どのステップまで完了したかをフロー実行ログに記録
  - 可能であればロールバック（サブスクリプション削除など）
  - 管理者にアラート送信
  - ユーザーにエラーメッセージ返却

#### Lambda設定
- **関数名**: `{environment}-billing-orchestrator-purchase-flow`
- **タイムアウト**: 60秒（レシート検証が時間がかかる可能性を考慮）
- **メモリ**: 512MB
- **環境変数**:
  - `TENANTS_TABLE_NAME`: テナントテーブル名
  - `IDENTITY_POOL_ID`: Cognito Identity PoolのID
  - `USER_POOL_ID`: Cognito User PoolのID
  - `PAYMENT_GATEWAY_FUNCTION_PREFIX`: Payment Gateway Lambda関数名プレフィックス
  - `SUBSCRIPTION_MGMT_FUNCTION_PREFIX`: Subscription Management Lambda関数名プレフィックス
  - `PLAN_MGMT_FUNCTION_PREFIX`: Plan Management Lambda関数名プレフィックス
  - `ENVIRONMENT`: 環境名

#### IAM権限
- Lambda呼び出し権限（他の責務のLambda関数）
- RDS接続権限（IAM認証）
- Cognito Identity Pool権限（AssumeRoleWithWebIdentity）
- CloudWatch Logs書き込み権限

### 3.2 プラン変更フロー実行関数 (changePlanFlow.ts)

#### 責務
ユーザーがプランをアップグレード/ダウングレードする際の一連の処理を統括します。

#### トリガー
- API Gateway: `POST /billing/change-plan`
- 認証: Cognitoオーソライザー必須

#### 入力パラメータ
```typescript
interface ChangePlanRequest {
  tenantId: string;          // テナントID
  userId: string;            // ユーザーID
  subscriptionId: string;    // サブスクリプションID
  newPlanId: string;         // 変更後のプランID
}
```

#### 処理フロー
1. **認証確認とサブスクリプション検証** (処理時間: ~150ms)
   - ユーザーが指定されたサブスクリプションの所有者であることを確認
   - Subscription Management Serviceで現在のサブスクリプション情報を取得
   - 変更後のプランが存在し、購入可能であることを確認

2. **フロー実行ログの初期化** (処理時間: ~50ms)

3. **アップグレード/ダウングレード判定** (処理時間: ~100ms)
   - Plan Management Serviceで現在のプランと新しいプランの情報を取得
   - 価格、機能レベルなどを比較して判定

4. **決済プラットフォームでのプラン変更** (処理時間: 1-3秒)
   - Payment Gateway ServiceのupdateSubscriptionを呼び出し
   - アップグレード: 即時変更（差額請求）
   - ダウングレード: 次回更新時に変更予約

5. **サブスクリプション情報更新** (処理時間: ~200ms)
   - Subscription Management ServiceでプランIDと変更予定情報を更新

6. **プラン適用更新** (処理時間: ~300ms)
   - Plan Management Serviceで古いプラン適用を終了
   - 新しいプラン適用を作成

7. **権限更新** (処理時間: ~700ms)
   - Authorization Serviceで古い権限を剥奪
   - 新しい権限を付与

8. **フロー完了ログ記録** (処理時間: ~50ms)

9. **レスポンス返却**

#### Lambda設定
- **関数名**: `{environment}-billing-orchestrator-change-plan-flow`
- **タイムアウト**: 30秒
- **メモリ**: 512MB
- **環境変数**: 購入フローと同様

### 3.3 解約フロー実行関数 (cancelFlow.ts)

#### 責務
ユーザーがサブスクリプションを解約する際の一連の処理を統括します。

#### トリガー
- API Gateway: `POST /billing/cancel`
- 認証: Cognitoオーソライザー必須

#### 入力パラメータ
```typescript
interface CancelRequest {
  tenantId: string;          // テナントID
  userId: string;            // ユーザーID
  subscriptionId: string;    // サブスクリプションID
  cancelType: 'immediate' | 'at_period_end';  // 解約タイプ
}
```

#### 処理フロー

##### パターンA: 即時解約 (cancelType: 'immediate')

1. **認証確認とサブスクリプション検証** (処理時間: ~150ms)
2. **フロー実行ログの初期化** (処理時間: ~50ms)
3. **決済プラットフォームでのキャンセル** (処理時間: 1-3秒)
   - Payment Gateway ServiceのcancelSubscriptionを呼び出し
4. **サブスクリプション状態更新** (処理時間: ~200ms)
   - status: canceled
5. **プラン適用終了** (処理時間: ~300ms)
   - Plan Management Serviceで即座に終了
6. **権限剥奪** (処理時間: ~500ms)
7. **デフォルトプランへの遷移** (処理時間: ~300ms)
   - Plan Management Serviceでデフォルトプラン（Freeプランなど）を適用
8. **フロー完了ログ記録** (処理時間: ~50ms)
9. **レスポンス返却**

##### パターンB: 期限終了時解約 (cancelType: 'at_period_end')

1. **認証確認とサブスクリプション検証** (処理時間: ~150ms)
2. **フロー実行ログの初期化** (処理時間: ~50ms)
3. **決済プラットフォームでの自動更新停止** (処理時間: 1-3秒)
   - Payment Gateway ServiceのcancelSubscription（at_period_end指定）を呼び出し
4. **サブスクリプション状態更新** (処理時間: ~200ms)
   - status: scheduled_cancellation
5. **プラン適用状態更新** (処理時間: ~200ms)
   - Plan Management Serviceでscheduled_terminationにマーク
   - 有効期限はそのまま維持
   - 権限は剥奪しない
6. **フロー完了ログ記録** (処理時間: ~50ms)
7. **レスポンス返却**
   - 有効期限までの残り日数を含む

#### Lambda設定
- **関数名**: `{environment}-billing-orchestrator-cancel-flow`
- **タイムアウト**: 30秒
- **メモリ**: 512MB
- **環境変数**: 購入フローと同様

### 3.4 Webhookイベントハンドラー関数 (webhookEventHandler.ts)

#### 責務
課金プラットフォームからのWebhookイベント（EventBridge経由）を受信し、イベント種別に応じた処理を統括します。

#### トリガー
- EventBridge: カスタムイベントバス経由
- イベントソース: Payment Gateway WebhookエンドポイントからEventBridgeに送信されたイベント

#### 入力イベント形式
```typescript
interface WebhookEvent {
  version: string;
  id: string;
  'detail-type': 'payment.succeeded' | 'payment.failed' | 'subscription.canceled' | 'payment.refunded';
  source: 'billing.payment-gateway';
  account: string;
  time: string;
  region: string;
  resources: string[];
  detail: {
    platform: 'stripe' | 'apple' | 'google';
    tenantId: string;
    eventId: string;
    eventType: string;
    subscriptionId: string;
    userId: string;
    planId?: string;
    expirationDate?: string;
    // プラットフォーム固有の情報
  };
}
```

#### 処理フロー

##### イベント種別1: 支払い更新成功 (payment.succeeded)

1. **イベント情報の抽出** (処理時間: ~50ms)
   - detail内の情報を取得
2. **フロー実行ログの初期化** (処理時間: ~50ms)
3. **サブスクリプション期限延長** (処理時間: ~200ms)
   - Subscription Management Serviceで有効期限を更新
4. **プラン適用状態の確認** (処理時間: ~150ms)
   - Plan Management Serviceで現在の状態を取得
   - scheduled_terminationの場合: 延長しない（予定通り終了）
   - activeの場合: 有効期限を延長
5. **支払い履歴記録** (処理時間: ~100ms)
   - Subscription Management Serviceで支払い履歴を記録
6. **フロー完了ログ記録** (処理時間: ~50ms)

##### イベント種別2: 支払い失敗 (payment.failed)

1. **イベント情報の抽出** (処理時間: ~50ms)
2. **フロー実行ログの初期化** (処理時間: ~50ms)
3. **サブスクリプション状態を猶予期間に更新** (処理時間: ~200ms)
   - Subscription Management Serviceでstatus: past_dueに更新
4. **支払い失敗履歴記録** (処理時間: ~100ms)
5. **ユーザーへの通知** (処理時間: ~300ms)
   - 通知サービスに「支払い方法を更新してください」を依頼
   - 注: 通知サービスはこのフェーズでは未実装の可能性あり（TODO）
6. **フロー完了ログ記録** (処理時間: ~50ms)

##### イベント種別3: キャンセル (subscription.canceled)

1. **イベント情報の抽出** (処理時間: ~50ms)
2. **フロー実行ログの初期化** (処理時間: ~50ms)
3. **サブスクリプション状態更新** (処理時間: ~200ms)
   - status: canceled
4. **プラン適用終了** (処理時間: ~300ms)
   - Plan Management Serviceで終了
5. **権限剥奪** (処理時間: ~500ms)
   - Authorization Serviceで権限削除
6. **デフォルトプランへの遷移** (処理時間: ~300ms)
7. **フロー完了ログ記録** (処理時間: ~50ms)

##### イベント種別4: 返金 (payment.refunded)

1. **イベント情報の抽出** (処理時間: ~50ms)
2. **フロー実行ログの初期化** (処理時間: ~50ms)
3. **返金記録** (処理時間: ~100ms)
   - Subscription Management Serviceで返金情報を記録
4. **サービス無効化** (処理時間: ~300ms)
   - Plan Management Serviceでプラン適用を終了
5. **権限剥奪** (処理時間: ~500ms)
6. **デフォルトプランへの遷移** (処理時間: ~300ms)
7. **フロー完了ログ記録** (処理時間: ~50ms)

#### Lambda設定
- **関数名**: `{environment}-billing-orchestrator-webhook-handler`
- **タイムアウト**: 30秒
- **メモリ**: 512MB
- **環境変数**: 購入フローと同様

## 4. API Gatewayエンドポイントの設計

### 4.1 エンドポイント一覧

```
既存のAPI構造:
/admin/billing/plans/*              # 管理者向けプラン管理
/admin/billing/subscriptions/*      # 管理者向けサブスクリプション管理
/billing/webhook/{tenantId}/*       # Webhook受信
/billing/operations/*               # 決済操作（内部用）

新規追加:
/billing/purchase                   # 購入フロー
/billing/change-plan                # プラン変更フロー
/billing/cancel                     # 解約フロー
```

### 4.2 詳細仕様

#### POST /billing/purchase
- **認証**: Cognitoオーソライザー必須
- **リクエストボディ**:
  ```json
  {
    "planId": "plan_standard_monthly",
    "platform": "stripe",
    "receipt": "pi_xxx...",
    "paymentMethodId": "pm_xxx..."
  }
  ```
- **レスポンス（成功）**:
  ```json
  {
    "success": true,
    "subscriptionId": "sub_xxx",
    "planId": "plan_standard_monthly",
    "expirationDate": "2025-12-12T00:00:00Z",
    "message": "Purchase completed successfully"
  }
  ```
- **レスポンス（検証保留）**:
  ```json
  {
    "success": false,
    "status": "pending_verification",
    "subscriptionId": "sub_xxx",
    "message": "Purchase received. Verification is taking longer than usual. You will be notified once complete."
  }
  ```

#### POST /billing/change-plan
- **認証**: Cognitoオーソライザー必須
- **リクエストボディ**:
  ```json
  {
    "subscriptionId": "sub_xxx",
    "newPlanId": "plan_pro_monthly"
  }
  ```
- **レスポンス**:
  ```json
  {
    "success": true,
    "subscriptionId": "sub_xxx",
    "oldPlanId": "plan_standard_monthly",
    "newPlanId": "plan_pro_monthly",
    "changeType": "immediate",
    "effectiveDate": "2025-11-12T10:30:00Z",
    "message": "Plan changed successfully"
  }
  ```

#### POST /billing/cancel
- **認証**: Cognitoオーソライザー必須
- **リクエストボディ**:
  ```json
  {
    "subscriptionId": "sub_xxx",
    "cancelType": "at_period_end"
  }
  ```
- **レスポンス**:
  ```json
  {
    "success": true,
    "subscriptionId": "sub_xxx",
    "cancelType": "at_period_end",
    "expirationDate": "2025-12-12T00:00:00Z",
    "remainingDays": 30,
    "message": "Cancellation scheduled. Service will remain active until 2025-12-12."
  }
  ```

### 4.3 認証とテナント識別

- **認証方式**: Cognito User Poolsオーソライザー
- **テナント識別**: Cognitoトークンの`custom:tenant_id`クレームから取得
- **ユーザー識別**: Cognitoトークンの`sub`クレームから取得
- **権限チェック**: Lambda関数内でユーザーがリソースの所有者であることを確認

## 5. EventBridgeイベントの設計

### 5.1 イベントバス

- **イベントバス名**: `default`（既存のPayment Gateway Webhookで使用しているものと同じ）
- **イベントソース**: `billing.payment-gateway`

### 5.2 イベントルール

#### ルール1: 支払い更新成功イベント
- **ルール名**: `{environment}-billing-orchestrator-payment-succeeded`
- **イベントパターン**:
  ```json
  {
    "source": ["billing.payment-gateway"],
    "detail-type": ["payment.succeeded"]
  }
  ```
- **ターゲット**: Webhookイベントハンドラー関数

#### ルール2: 支払い失敗イベント
- **ルール名**: `{environment}-billing-orchestrator-payment-failed`
- **イベントパターン**:
  ```json
  {
    "source": ["billing.payment-gateway"],
    "detail-type": ["payment.failed"]
  }
  ```
- **ターゲット**: Webhookイベントハンドラー関数

#### ルール3: キャンセルイベント
- **ルール名**: `{environment}-billing-orchestrator-subscription-canceled`
- **イベントパターン**:

## 6. データベーススキーマ（RDS）

### 6.1 テーブル配置方針

- **マルチテナント対応**: テナントごとに専用のRDSインスタンスまたはスキーマ
- **アクセス方式**: IAM認証を使用したRDS接続（既存のPlan ManagementやSubscription Managementと同様）

### 6.2 新規追加テーブル: flow_execution_logs

#### 目的
各フロー（購入、変更、解約、Webhookイベント処理）の実行状態とステップごとの結果を記録します。

#### スキーマ定義
```sql
CREATE TABLE flow_execution_logs (
  flow_execution_id UUID PRIMARY KEY,
  flow_type VARCHAR(50) NOT NULL,  -- 'purchase' | 'change_plan' | 'cancel' | 'webhook_event'
  user_id VARCHAR(255) NOT NULL,
  tenant_id VARCHAR(255) NOT NULL,
  status VARCHAR(50) NOT NULL,  -- 'processing' | 'completed' | 'failed'
  input_params JSONB NOT NULL,
  error_info JSONB,
  step_results JSONB,  -- 各ステップの実行結果を配列で記録
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  completed_at TIMESTAMP,

  INDEX idx_user_id_created_at (user_id, created_at),
  INDEX idx_tenant_id_created_at (tenant_id, created_at),
  INDEX idx_status_created_at (status, created_at)
);
```

#### カラム詳細

- **flow_execution_id**: フロー実行の一意識別子（UUID）
- **flow_type**: フローの種別
  - `purchase`: 購入フロー
  - `change_plan`: プラン変更フロー
  - `cancel`: 解約フロー
  - `webhook_event`: Webhookイベント処理フロー
- **user_id**: ユーザーID（Cognito sub）
- **tenant_id**: テナントID
- **status**: 実行ステータス
  - `processing`: 実行中
  - `completed`: 完了
  - `failed`: 失敗
- **input_params**: 入力パラメータ（JSON形式）
  - 例（購入フロー）: `{"planId": "plan_xxx", "platform": "stripe", "receipt": "pi_xxx"}`
- **error_info**: エラー情報（失敗時のみ、JSON形式）
  - 例: `{"step": "receipt_verification", "errorCode": "INVALID_RECEIPT", "message": "Receipt verification failed", "details": {...}}`
- **step_results**: 各ステップの実行結果（JSON配列）
  - 例:
    ```json
    [
      {"step": "auth_check", "status": "completed", "duration_ms": 120, "timestamp": "2025-11-12T10:30:00Z"},
      {"step": "receipt_verification", "status": "completed", "duration_ms": 1500, "timestamp": "2025-11-12T10:30:02Z"},
      {"step": "subscription_creation", "status": "completed", "duration_ms": 200, "subscriptionId": "sub_xxx", "timestamp": "2025-11-12T10:30:04Z"}
    ]
    ```
- **created_at**: 作成日時
- **updated_at**: 更新日時
- **completed_at**: 完了日時

#### インデックス

- `idx_user_id_created_at`: ユーザーIDと作成日時の複合インデックス（ユーザーごとの履歴取得に使用）
- `idx_tenant_id_created_at`: テナントIDと作成日時の複合インデックス（テナントごとの統計に使用）
- `idx_status_created_at`: ステータスと作成日時の複合インデックス（失敗したフローの検索に使用）

#### データ保持期間

- **保持期間**: 90日
- **アーカイブ**: 90日経過後、S3にアーカイブ（オプション）
- **削除方法**: バッチ処理で定期的に古いレコードを削除

## 9. エラーハンドリングとリトライ戦略

### 9.1 エラー分類

#### レベル1: リトライ可能な一時的エラー
- ネットワークエラー
- AWS API タイムアウト
- Lambda同時実行数制限
- RDB接続エラー（一時的）

**対応**:
- 自動リトライ（最大3回、指数バックオフ）
- リトライ後も失敗した場合、レベル3として扱う

#### レベル2: リトライ不可能な業務エラー
- プランが存在しない
- ユーザーが見つからない
- レシートが無効
- サブスクリプションが既に存在する

**対応**:
- リトライせず即座にエラーレスポンス返却
- フロー実行ログにエラー情報を記録
- ユーザーにエラーメッセージを返す（ただし詳細は伏せる）

#### レベル3: 部分失敗（途中まで成功、後半で失敗）
- サブスクリプションは作成されたが、プラン適用で失敗
- プラン適用は完了したが、権限付与で失敗

**対応**:
1. フロー実行ログに詳細を記録（どこまで成功、どこから失敗）
2. 可能であればロールバック（例: サブスクリプション削除）
3. 管理者にアラート送信（SNS経由でSlackなど）
4. ユーザーには「処理中にエラーが発生しました。サポートにお問い合わせください」と返す

### 9.2 ロールバック戦略

#### ロールバック可能なケース
- サブスクリプション作成後、プラン適用前に失敗
  → サブスクリプションを削除
- プラン適用後、権限付与前に失敗
  → プラン適用を削除

#### ロールバック不可能なケース
- 決済プラットフォームでの決済完了後
  → 決済は完了しているため、ロールバックせず、管理者が手動で対応

#### 実装方針
- トランザクション管理は行わない（複数のLambda関数にまたがるため）
- 失敗時の補償トランザクション（Compensating Transaction）パターンを使用
- ロールバック処理もフロー実行ログに記録

### 9.3 アラート設定

#### アラート対象
- レベル3エラー（部分失敗）が発生した場合
- 同じユーザー/サブスクリプションで3回以上連続してエラーが発生した場合
- 1時間あたりのエラー率が5%を超えた場合

#### アラート送信先
- SNSトピック経由でSlack、メール、PagerDutyなど
- 注: 通知サービスの実装はこのフェーズでは対象外（TODO）

## 11. デプロイと段階的ロールアウト

### 11.1 デプロイ順序

1. **フェーズ1**: Lambda関数とフロー実行ログテーブルのデプロイ
   - Orchestrator APIのCDK Constructを作成
   - BillingManagementStackにOrchestratorApiを追加
   - `cdk deploy` でデプロイ
   - Lambda関数が正常に作成されることを確認

2. **フェーズ2**: EventBridgeルールのデプロイ
   - EventBridgeルールを作成
   - Webhookイベントハンドラー関数がイベントを受信できることを確認
   - 既存のWebhookエンドポイントからEventBridgeにイベントが流れることを確認

3. **フェーズ3**: API Gatewayエンドポイントのデプロイ
   - `/billing/purchase`, `/billing/change-plan`, `/billing/cancel` を公開
   - 認証が正常に機能することを確認

### 11.2 段階的ロールアウト

#### ステージ1: 開発環境でのテスト
- 開発環境で全フローの動作確認
- エラーハンドリングのテスト（意図的にエラーを発生させる）
- フロー実行ログが正常に記録されることを確認

#### ステージ2: ステージング環境での統合テスト
- ステージング環境で本番に近いデータでテスト
- 他の責務（Payment Gateway、Subscription Management、Plan Management）との連携確認
- パフォーマンステスト（負荷テスト）

#### ステージ3: 本番環境でのカナリアリリース
- 一部のユーザー（例: 5%）に対してのみ新しいエンドポイントを公開
- CloudWatch Metricsで成功率とレイテンシーを監視
- 問題がなければ段階的に公開範囲を拡大（10% → 50% → 100%）

### 11.3 ロールバック計画

#### ロールバック条件
- エラー率が10%を超えた場合
- 致命的なバグが発見された場合
- パフォーマンスが著しく低下した場合

#### ロールバック手順
1. API Gatewayエンドポイントを無効化（または旧バージョンに戻す）
2. EventBridgeルールを無効化
3. Lambda関数を旧バージョンにロールバック（Lambda Versioningを使用）
4. 問題を修正後、再度デプロイ

### 14.3 依存関係と前提条件

#### 実装済みであることが前提
- Payment Gateway（レシート検証、決済操作）
- Subscription Management（サブスクリプションCRUD）
- Plan Management（プランCRUD、プラン適用）
- RDS（PostgreSQL）のセットアップ
- Cognito User Pool / Identity Pool
- EventBridge event bus

#### 実装されていない（今後必要）
- 権限管理サービス（OpenFGA/カウント機構）
  - 実装されるまでは、権限付与・剥奪の処理をスキップまたはモック化
- 通知サービス
  - 実装されるまでは、通知処理をスキップまたはログ出力のみ

### 14.4 リスクと対策

| リスク | 影響度 | 対策 |
|--------|--------|------|
| 権限管理サービスが未実装 | 高 | モック実装で代替、または実装完了を待つ |
| Lambda-to-Lambda呼び出しのレイテンシー | 中 | 各Lambda関数の処理時間を最適化、並列実行の検討 |
| RDB接続プール枯渇 | 中 | 接続プール設定の調整、接続リークの防止 |
| EventBridgeの遅延 | 低 | Webhookイベント処理は非同期のため許容範囲 |
| フロー実行ログテーブルの肥大化 | 低 | TTL設定により90日後に自動削除 |
