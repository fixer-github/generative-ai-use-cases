# 「購入・変更・解約などの複数ステップの処理を統括する」責務の実装イメージ

## この責務は何をするのか

この責務は、ユーザーがプランを購入したり、変更したり、解約したりする一連の流れ全体を管理する「指揮者」の役割を果たします。

例えるなら、オーケストラの指揮者のようなものです。オーケストラでは、バイオリン担当、フルート担当、ピアノ担当など、それぞれの楽器の演奏者がいます。指揮者は楽器を演奏しませんが、「ここでバイオリンが入って、次にフルートが入って、最後にピアノで締める」という全体の流れを指示します。

同じように、この責務は以下のような他の責務を組み合わせて、全体の流れを作ります：
- 決済システムとのやり取りを一本化する責務（決済の実行やレシート検証を担当）
- サブスクリプション契約の状態を記録・管理する責務（契約情報の記録を担当）
- プランを管理する責務（プラン適用や解除を担当）
- 権限判定の責務（ユーザーに機能を使える権限を付与・剥奪する担当）
- 通知の責務（ユーザーに結果を知らせる担当）

---

## なぜこの責務が必要なのか

もしこの責務がなかったら、どうなるでしょうか？

例えば、ユーザーがプランを購入する流れは、以下のような複数のステップで構成されています：

1. 決済システムで支払いを実行する
2. レシートが本物かを検証する
3. サブスクリプション情報をデータベースに記録する
4. ユーザーにプランを適用する
5. ユーザーに機能を使う権限を付与する
6. ユーザーに「購入完了しました」と通知する

これらのステップをバラバラの場所で管理すると、以下のような問題が起きます：

- **ステップの順序を間違える**：例えば、レシート検証をする前に権限を付与してしまい、不正な購入でもサービスを使えてしまう
- **ステップを忘れる**：例えば、サブスクリプション情報は記録したが、プラン適用を忘れてしまい、ユーザーが支払ったのにサービスを使えない
- **エラー時の対応が複雑になる**：例えば、途中でエラーが起きた時、どこまで完了してどこから失敗したのか分からなくなる

この責務を設けることで、「購入するときはこの順序でこれとこれをやる」というルールが一箇所に集約されるため、間違いが起きにくくなります。

## 具体的にどのように実装するのか

### 実装構成の全体像

この責務は、以下の2つの部分で構成されます：

#### 1. ユーザー向けAPI（ユーザーが直接呼び出す）

ユーザーがアプリから操作したときに呼ばれるAPIです。

**提供するエンドポイント**：
- プラン購入API（POST /billing/purchase）
- プラン変更API（POST /billing/change-plan）
- 解約API（POST /billing/cancel）

これらのAPIは、API GatewayとLambda関数で実装されます。

#### 2. Webhookイベント処理（課金プラットフォームから通知を受けて動く）

課金プラットフォーム（Stripe、Apple、Google）から「支払いが更新されました」「支払いに失敗しました」などの通知を受けたときに、自動的に動く処理です。

**処理するイベント**：
- 支払い更新成功イベント（サブスクリプションの有効期限を延長する）
- 支払い失敗イベント（サブスクリプションを猶予期間状態にする）
- キャンセルイベント（サブスクリプションを停止し、デフォルトプランに戻す）
- 返金イベント（サービスを無効化する）

これらは、EventBridge（イベントバス）経由でLambda関数が起動されます。

---

### 実装の詳細：各フローがどう動くか

#### フロー1：購入フロー

ユーザーがプランを購入するときの流れです。

**ステップ**：

1. **ユーザー認証とプラン検証**
   購入リクエストを受けたら、まず「このユーザーは本当にログインしているか？」「選択されたプランは実際に存在するか？」を確認します。

2. **決済開始**
   決済システムとのやり取りを一本化する責務に「このユーザーの決済を開始してください」と依頼します。Stripeの場合はCheckout Sessionが作成され、Apple/Googleの場合はアプリ内課金が開始されます。

3. **レシート検証**
   決済完了後、クライアントアプリから「購入しました」というレシート（領収書）が送られてきます。これが本物かを決済システムに確認します。

4. **検証成功の場合の処理**：
   - サブスクリプション契約の状態管理に「このユーザーはこのサブスクリプションでこのプランを契約しました」と記録を依頼します
   - プラン管理に「このユーザーにこのプランを適用してください」と依頼します
   - 権限判定に「このユーザーにこのプランに含まれる権限を付与してください」と依頼します
   - 最後にクライアントアプリに「購入完了」と返答します

5. **検証失敗の場合の処理**（ネットワークエラーなどでレシート検証ができなかった場合）：
   - サブスクリプション契約の状態管理に「このサブスクリプションを検証保留中として記録してください」と依頼します
   - 管理者にアラートを送信します
   - クライアントアプリには「購入処理を受け付けましたが、確認に時間がかかっています。完了次第通知します」と返答します

**実装方法**：
- Lambda関数：`packages/cdk/lambda/billing/orchestrator/purchaseFlow.ts`
- API Gatewayエンドポイント：`POST /billing/purchase`
- 認証：Cognitoオーソライザー必須

---

#### フロー2：プラン変更フロー

ユーザーがプランをアップグレード（例：Standard→Pro）またはダウングレード（例：Pro→Standard）するときの流れです。

**ステップ**：

1. **変更前後のプランを比較**
   アップグレードかダウングレードかを判定します。

2. **決済システムにプラン変更を依頼**
   - **アップグレードの場合**：即座にプランを変更し、差額を請求します
   - **ダウングレードの場合**：次回更新時（現在の契約期間が終わってから）にプランを変更する予約をします

3. **権限の更新**
   権限判定に「古い権限を剥奪して、新しい権限を付与してください」と依頼します。

4. **通知**
   ユーザーに「プラン変更が完了しました」と通知します。

**実装方法**：
- Lambda関数：`packages/cdk/lambda/billing/orchestrator/changePlanFlow.ts`
- API Gatewayエンドポイント：`POST /billing/change-plan`
- 認証：Cognitoオーソライザー必須

---

#### フロー3：解約フロー

ユーザーがサブスクリプションを解約するときの流れです。解約には2つのパターンがあります。

##### パターンA：即時解約（すぐにサービスが止まる）

**ステップ**：

1. **決済システムにキャンセルを依頼**
   決済システムとのやり取りを一本化する責務に「このユーザーのサブスクリプションをキャンセルしてください」と依頼します。

2. **サブスクリプション状態を更新**
   サブスクリプション契約の状態管理に「このサブスクリプションはキャンセルされました」と記録を依頼します。

3. **プラン適用を終了**
   プラン管理に「このプラン適用を即座に終了してください」と依頼します。

4. **権限を剥奪**
   権限判定に「このユーザーの権限を剥奪してください」と依頼します。

5. **デフォルトプランに戻す**
   プラン管理が「このユーザーをデフォルトプラン（通常はFreeプラン）に戻してください」と処理します。

6. **通知**
   ユーザーに「解約が完了しました」と通知します。

##### パターンB：期限終了時解約（有効期限までは使える）

**ステップ**：

1. **決済システムに自動更新停止を依頼**
   決済システムとのやり取りを一本化する責務に「このユーザーのサブスクリプションの自動更新を停止してください」と依頼します。

2. **サブスクリプション状態を「解約予定」に更新**
   サブスクリプション契約の状態管理に「このサブスクリプションは解約予定です」と記録を依頼します。

3. **プラン適用を「期限終了時に終了予定」としてマーク**
   プラン管理に「このプラン適用を期限終了時に終了予定としてマークしてください」と依頼します。
   プラン適用の状態が`scheduled_termination`（解約予定）に変更され、有効期限はそのまま維持されます。この時点では権限を剥奪しません。

4. **通知**
   ユーザーに「解約を受け付けました。サービスは〇〇日まで利用可能です」と通知します。

5. **期限到達時の自動処理**
   定期的な期限切れチェック処理（バッチ処理）により、有効期限が到達したら自動的に以下が実行されます：
   - 権限の剥奪
   - デフォルトプランへの遷移
   - サブスクリプション状態を`canceled`に更新
   - プラン適用状態を`expired`に更新

**実装方法**：
- Lambda関数：`packages/cdk/lambda/billing/orchestrator/cancelFlow.ts`
- API Gatewayエンドポイント：`POST /billing/cancel`
- 認証：Cognitoオーソライザー必須

---

#### フロー4：Webhookイベント処理フロー

課金プラットフォームから通知を受けたときの流れです。

**ステップ**：

1. **イベント種別を判定**
   受信したWebhookイベントが「支払い更新成功」「支払い失敗」「キャンセル」「返金」のどれかを判定します。

2. **イベント種別に応じた処理を実行**：

   - **支払い更新成功イベントの場合**：
     - サブスクリプション契約の状態管理に「期限を更新してください」と依頼
     - プラン管理に「プラン適用の有効期限を延長してください」と依頼
     - ただし、プラン適用の状態が`scheduled_termination`（解約予定）の場合は延長せず、予定通り期限で終了

   - **支払い失敗イベントの場合**：
     - サブスクリプション契約の状態管理に「ステータスを猶予期間（past_due）に変更してください」と依頼
     - ユーザーに「支払い方法を更新してください」と通知
     - 課金プラットフォーム側が自動的にリトライするため、システム側では何もせず待つ

   - **キャンセルイベントの場合**：
     - サブスクリプション契約の状態管理に「ステータスをキャンセル済みに変更してください」と依頼
     - プラン管理に「プラン適用を終了してください」と依頼
     - 権限判定に「権限を剥奪してください」と依頼
     - プラン管理が「デフォルトプランに戻してください」と処理
     - ユーザーに「キャンセルが完了しました」と通知

   - **返金イベントの場合**：
     - サブスクリプション契約の状態管理に「返金を記録してください」と依頼
     - プラン管理に「プラン適用を終了してください」と依頼
     - 権限判定に「権限を剥奪してください」と依頼
     - ユーザーに「返金が完了しました」と通知

**実装方法**：
- Lambda関数：`packages/cdk/lambda/billing/orchestrator/webhookEventHandler.ts`
- トリガー：EventBridge（既存のWebhook受信層から署名検証・重複チェック済みのイベントを受信）
- EventBridgeルール：イベントの種別ごとに異なるルールで振り分け

### データの持ち方

この責務は、基本的に「状態を持たない（ステートレス）」設計にします。つまり、自分自身でデータを保存せず、他の責務にデータの保存を依頼します。

ただし、以下のようなログは記録します：

#### フロー実行ログ

各フローの実行状態を記録します。

**保存する内容**：
- フロー実行ID（一意識別子）
- フロー種別（purchase/change_plan/cancel/webhook_event）
- ユーザーID
- 実行開始時刻
- 実行終了時刻
- 実行ステータス（processing/completed/failed）
- エラー情報（失敗した場合）
- 各ステップの実行結果

**保存先**：
- CloudWatch Logsに詳細ログを記録
- DynamoDB（テナント専用テーブル）にフロー実行履歴を記録

**目的**：
- トラブル調査：「この購入フローはどこで失敗したのか？」を特定できる
- 監視：「最近失敗が増えているか？」を確認できる
- 監査：「誰がいつ何を実行したか？」を追跡できる

---

### 他の責務とのやり取り

この責務は、以下の責務に依頼を出します（依存関係）：

#### 依存する責務（この責務が依頼を出す相手）

1. **Stripe/Apple/Googleの決済システムとのやり取りを一本化する**
   - 決済開始（Checkout Session作成など）
   - レシート検証
   - サブスクリプション変更API呼び出し
   - サブスクリプションキャンセルAPI呼び出し

2. **ユーザのサブスクリプション契約の状態を記録・管理する**
   - サブスクリプション情報の記録
   - サブスクリプション状態の更新
   - 有効期限の延長

3. **どんなプランがあって、誰がどのプランに入っているかを管理する**
   - プラン適用
   - プラン変更
   - デフォルトプランへの遷移
   - プラン適用の終了

4. **ユーザが各機能を使える権限と、一日何回使えるかを判定する**
   - 権限の付与
   - 権限の剥奪

5. **ユーザにビジネスイベントを通知する**
   - 購入完了通知
   - プラン変更完了通知
   - 解約完了通知
   - 支払い失敗通知

### インフラ構成

#### Lambda関数（4つ）

1. **購入フロー実行関数**
   - 関数名：`{environment}-billing-orchestrator-purchase-flow`
   - エントリーポイント：`packages/cdk/lambda/billing/orchestrator/purchaseFlow.ts`
   - トリガー：API Gateway（POST /billing/purchase）
   - タイムアウト：60秒（レシート検証が時間がかかる可能性があるため）

2. **プラン変更フロー実行関数**
   - 関数名：`{environment}-billing-orchestrator-change-plan-flow`
   - エントリーポイント：`packages/cdk/lambda/billing/orchestrator/changePlanFlow.ts`
   - トリガー：API Gateway（POST /billing/change-plan）
   - タイムアウト：30秒

3. **解約フロー実行関数**
   - 関数名：`{environment}-billing-orchestrator-cancel-flow`
   - エントリーポイント：`packages/cdk/lambda/billing/orchestrator/cancelFlow.ts`
   - トリガー：API Gateway（POST /billing/cancel）
   - タイムアウト：30秒

4. **Webhookイベントハンドラー関数**
   - 関数名：`{environment}-billing-orchestrator-webhook-handler`
   - エントリーポイント：`packages/cdk/lambda/billing/orchestrator/webhookEventHandler.ts`
   - トリガー：EventBridge（イベントの種別ごとに異なるルール）
   - タイムアウト：30秒

#### EventBridgeルール

Webhookイベントハンドラー関数を起動するために、以下のルールを作成します：

1. **支払い更新成功イベント用ルール**
   - イベントパターン：`detail-type`が`payment.succeeded`のイベント
   - ターゲット：Webhookイベントハンドラー関数

2. **支払い失敗イベント用ルール**
   - イベントパターン：`detail-type`が`payment.failed`のイベント
   - ターゲット：Webhookイベントハンドラー関数

3. **キャンセルイベント用ルール**
   - イベントパターン：`detail-type`が`subscription.canceled`のイベント
   - ターゲット：Webhookイベントハンドラー関数

4. **返金イベント用ルール**
   - イベントパターン：`detail-type`が`payment.refunded`のイベント
   - ターゲット：Webhookイベントハンドラー関数

#### API Gatewayエンドポイント

既存の`/billing`リソース配下に、以下のエンドポイントを追加します：

- `POST /billing/purchase` - 購入フロー実行
- `POST /billing/change-plan` - プラン変更フロー実行
- `POST /billing/cancel` - 解約フロー実行

すべてのエンドポイントでCognitoオーソライザーによる認証を必須とします。

#### DynamoDBテーブル（テナント専用）

フロー実行履歴を保存するテーブルを作成します：

- テーブル名：`{tenantId}-billing-flow-execution-logs`
- パーティションキー：`flow_execution_id`（フロー実行ID）
- ソートキー：`timestamp`（実行日時）
- TTL：90日後に自動削除

### エラーハンドリング

各フローでエラーが発生した場合、以下のように対応します：

#### リトライ可能なエラー（一時的な障害）

- ネットワークエラー
- タイムアウト
- 外部API（決済システムなど）の一時的な障害

**対応**：
- 自動的に数回リトライします（指数バックオフ：1秒→2秒→4秒と待ち時間を増やす）
- 最大3回までリトライ
- リトライしても失敗した場合は、次の「リトライ不可能なエラー」として扱います

#### リトライ不可能なエラー（恒久的な問題）

- レシート検証が「無効なレシート」と返ってきた（不正な購入）
- 存在しないプランIDが指定された
- ユーザーIDが見つからない

**対応**：
- フロー実行ログにエラー情報を記録
- 管理者にアラートを送信
- ユーザーにエラーメッセージを返す（ただし、詳細な理由は伏せてセキュリティを保つ）

#### 部分失敗（途中までは成功したが、後半で失敗）

例えば、「サブスクリプション情報の記録は成功したが、プラン適用で失敗した」というケースです。

**対応**：
- フロー実行ログに「どこまで成功して、どこから失敗したか」を詳細に記録
- 管理者にアラートを送信し、手動で対応できるようにする
- 可能であれば、成功した部分をロールバック（取り消し）する
- ただし、すべてのステップがロールバック可能とは限らないため、最終的には管理者が手動で整合性を修正する

## まとめ

この責務により、以下が実現できます：

### 利点

1. **一貫性の保証**
   購入、変更、解約の各フローが正しい順序で実行され、ステップの抜けや漏れが起きにくくなります。

2. **エラー対応の明確化**
   エラーが発生したときに、どこで失敗したかを特定しやすく、対応方法も明確になります。

3. **他の責務との疎結合**
   各責務は自分の仕事に集中でき、フロー全体の管理はこの責務が担当することで、責任が明確に分離されます。

4. **監視とデバッグの容易性**
   フロー実行ログにより、「どのユーザーがいつ何を実行したか」「どこで失敗したか」を追跡できます。

5. **柔軟性**
   新しいフロー（例：トライアル開始フロー、キャンペーン適用フロー）を追加する場合も、この責務に新しいLambda関数を追加するだけで済みます。

### 実装の配置

- **ディレクトリ構造**：`packages/cdk/lambda/billing/orchestrator/`
- **Lambda関数**：4つ（購入、変更、解約、Webhookイベント処理）
- **API Gatewayエンドポイント**：3つ（購入、変更、解約）
- **EventBridgeルール**：4つ（各イベント種別ごと）

### 関連資料との整合性

この実装イメージは、以下の資料と整合しています：

- `責務の境界分離.md`：定義された責務の役割と依存関係に従っています
- `課金のシーケンス図.md`：記載されたシーケンスフローを実装しています
- `プラン・サブスクリプションのデータモデル管理`：定義されたテーブル構造を活用しています
- 既存実装（Payment Gateway、Plan Management、Subscription Management）：これらの責務が提供する機能を組み合わせて、エンドツーエンドのフローを実現しています
