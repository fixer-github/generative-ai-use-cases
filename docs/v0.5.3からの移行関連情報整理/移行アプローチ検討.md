# v0.5.3 → develop 移行アプローチ検討

本ドキュメントは、v0.5.3からdevelopブランチへのアシスタント（Bot）データおよびRAGデータの移行アプローチをまとめたものです。

## 1. 前提条件

- 会話履歴の移行は不要（v0.5.3時点でBotの会話履歴を使用していないため）
- 移行対象はアシスタント設定（BotTableV3）とRAGデータ（S3）のみ

---

## 2. データ構造の差分

### 2.1 テーブル構造の比較

| 項目 | v0.5.3 (BotTableV3) | develop (Assistant) |
|------|---------------------|---------------------|
| **PK** | `UserId` | `user#{userId}` |
| **SK** | `BOT#{bot_id}` | `createdDate`（タイムスタンプ） |
| **ID属性** | `BotId`（任意形式） | `assistantId`（`assistant#{uuid}`形式） |
| **名前** | `Title` | `name` |
| **説明** | `Description` | `description` |
| **指示** | `Instruction` | `instruction` |
| **ナレッジ（ファイル）** | `Knowledge.filenames[]` | `knowledgeSources[{type:'file', storageKey}]` |
| **ナレッジ（URL）** | `Knowledge.source_urls[]` | `knowledgeSources[{type:'web', sourceUrl}]` |
| **クイックスターター** | `ConversationQuickStarters` | `firstQuestions` |
| **同期状態** | `SyncStatus` | `syncStatus` |
| **可視性** | `SharedScope` | `visibility`（'private' / 'public'） |

### 2.2 S3パス構造の比較

| 項目 | v0.5.3 | develop |
|------|--------|---------|
| **バケット名** | `bedrock-chat-docs-${env}-${tenantId}` | `docs-${env}-tenant-${tenantId}-${hash}` |
| **ファイルパス** | `{user_id}/{bot_id}/documents/{filename}` | `assistant-files/{userId}/{fileId}/{filename}` |

### 2.3 KnowledgeSource型の構造（develop）

```typescript
type KnowledgeSource = {
  id?: string;                    // ソースの一意識別子
  type?: 'file' | 'web' | 'url';  // ソースの種類
  name?: string;                  // 表示名
  storageKey?: string;            // S3キー（ファイルの場合）
  sourceUrl?: string;             // URL（Webの場合）
  status?: 'QUEUED' | 'SYNCING' | 'SUCCEEDED' | 'FAILED';
  error?: string;
};
```

## 3. 移行アプローチの比較

### 3.1 アプローチA: 移行スクリプトによる直接データ投入

```
[BotTableV3] ──変換→ [Assistantテーブル]
[旧S3] ──コピー→ [新S3（パス変換）]
```

**メリット**:
- 一括で高速に移行可能
- BotIdなどの参照を維持できる可能性

**デメリット**:
- syncStatusの初期化など、内部整合性の担保が手動
- OpenSearchインデックスを別途トリガーする必要あり
- テナント分離の整合性を自前で担保する必要あり

### 3.2 アプローチB: APIを経由したアシスタント再作成

```
[BotTableV3] ──JSON抽出→ [変換スクリプト]
                              ↓
                    [POST /assistant] ← ファイルアップロード
```

**メリット**:
- 新システムのバリデーション・整合性チェックが自動適用
- syncStatusやknowledgeSourcesのstatusが正しく初期化される
- OpenSearchへのインデックス処理が自動実行される

**デメリット**:
- ファイルを1つずつAPIでアップロードする必要があり、ボット数が多いと時間がかかる
- 新しいassistantIdが発行されるため、旧BotIdとの紐づけが切れる

### 3.3 アプローチC: ハイブリッドアプローチ（推奨）

```
[BotTableV3] ──変換→ [Assistantテーブル] (syncStatus: QUEUED)
[旧S3] ──コピー→ [新S3（パス変換）]
                        ↓
              [インデックス処理Lambda自動実行]
```

**メリット**:
- APIのオーバーヘッドを回避しつつ、インデックス処理は新システムの仕組みを活用
- データ投入は高速、整合性担保は新システムに委譲

**デメリット**:
- 変換スクリプトの実装が必要
- 新しいstorageKeyの生成とS3コピーが必要

## 4. 推奨アプローチ: ハイブリッドアプローチの詳細

### 4.1 移行フロー概要

```
┌─────────────────────────────────────────────────────────────┐
│ 1. データ抽出フェーズ                                         │
├─────────────────────────────────────────────────────────────┤
│  ・BotTableV3からBOT#で始まるアイテムをスキャン               │
│  ・S3バケットから全ファイルの一覧を取得                       │
│  ・抽出データをJSONファイルとして保存                         │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│ 2. 新環境デプロイフェーズ                                     │
├─────────────────────────────────────────────────────────────┤
│  ・npx cdk deploy で新スタック作成                           │
│  ・新しいAssistantテーブルとS3バケットが作成される            │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│ 3. データ変換・投入フェーズ                                   │
├─────────────────────────────────────────────────────────────┤
│  ・S3ファイルを新バケット・新パス構造にコピー                 │
│  ・Bot → Assistant スキーマ変換                              │
│  ・Assistantテーブルにレコード投入（syncStatus: QUEUED）      │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│ 4. インデックス再構築フェーズ                                 │
├─────────────────────────────────────────────────────────────┤
│  ・syncStatus: QUEUED のレコードを新システムが検出            │
│  ・OpenSearchへのインデックス処理が自動実行                   │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 データ変換ルール

#### 4.2.1 基本属性のマッピング

```javascript
// 変換元: BotTableV3のアイテム
const botItem = {
  PK: "user123",
  SK: "BOT#bot-abc-123",
  BotId: "bot-abc-123",
  Title: "サンプルボット",
  Description: "説明文",
  Instruction: "システムプロンプト",
  // ...
};

// 変換先: Assistantテーブルのアイテム
const assistantItem = {
  id: `user#${botItem.PK}`,                    // PK
  createdDate: Date.now().toString(),          // SK（新規生成）
  assistantId: `assistant#${crypto.randomUUID()}`,  // 新規UUID
  userId: `user#${botItem.PK}`,
  tenantId: `tenant#${tenantId}`,
  name: botItem.Title,
  description: botItem.Description,
  instruction: botItem.Instruction,
  modelId: "anthropic.claude-3-5-sonnet-20241022-v2:0",  // デフォルト値
  ragEnabled: true,
  visibility: botItem.SharedScope === "all" ? "public" : "private",
  syncStatus: "QUEUED",
  syncStatusReason: "",
  knowledgeSources: [],  // 後述の変換処理で設定
  firstQuestions: botItem.ConversationQuickStarters?.map(q => q.title) || [],
  updatedDate: Date.now().toString(),
};
```

#### 4.2.2 KnowledgeSourcesの変換

```javascript
// ファイルの変換
const fileKnowledgeSources = (botItem.Knowledge?.filenames || []).map((filename, index) => {
  const fileId = crypto.randomUUID();
  const sanitizedFileName = filename.replace(/[^a-zA-Z0-9.-]/g, '_');

  return {
    id: crypto.randomUUID(),
    type: 'file',
    name: filename,
    displayName: filename,
    storageKey: `assistant-files/${botItem.PK}/${fileId}/${sanitizedFileName}`,
    status: 'QUEUED',
  };
});

// URLの変換
const webKnowledgeSources = (botItem.Knowledge?.source_urls || []).map(url => ({
  id: crypto.randomUUID(),
  type: 'web',
  name: new URL(url).hostname,
  displayName: url,
  sourceUrl: url,
  status: 'QUEUED',
}));

// 結合
assistantItem.knowledgeSources = [...fileKnowledgeSources, ...webKnowledgeSources];
```

#### 4.2.3 S3ファイルのコピー

```bash
# 旧パス → 新パス
# 旧: s3://bedrock-chat-docs-{env}-{tenantId}/{user_id}/{bot_id}/documents/{filename}
# 新: s3://docs-{env}-tenant-{tenantId}-{hash}/assistant-files/{userId}/{fileId}/{filename}

aws s3 cp \
  s3://bedrock-chat-docs-${OLD_ENV}-${TENANT_ID}/${USER_ID}/${BOT_ID}/documents/${FILENAME} \
  s3://${NEW_BUCKET}/assistant-files/${USER_ID}/${FILE_ID}/${SANITIZED_FILENAME}
```

### 4.3 実装に必要なスクリプト

1. **データ抽出スクリプト** (`extract-v053-data.ts`)
   - BotTableV3のスキャン
   - S3ファイル一覧の取得
   - JSONファイルへの出力

2. **データ変換スクリプト** (`transform-to-assistant.ts`)
   - Bot → Assistant のスキーマ変換
   - knowledgeSourcesの構築
   - storageKeyの生成

3. **データ投入スクリプト** (`import-assistants.ts`)
   - S3ファイルのコピー
   - AssistantテーブルへのPutItem

## 5. 移行手順（ステップバイステップ）

### Step 1: 既存環境からデータ抽出

```bash
# 1-1. BotTableV3からデータをエクスポート
aws dynamodb scan \
  --table-name ${STACK_NAME}-Database-BotTableV3-XXXXX \
  --filter-expression "begins_with(SK, :prefix)" \
  --expression-attribute-values '{":prefix": {"S": "BOT#"}}' \
  --output json > bots-backup.json

# 1-2. S3バケットのファイル一覧を取得
aws s3 ls s3://bedrock-chat-docs-${ENV}-${TENANT_ID}/ --recursive > s3-files-list.txt

# 1-3. S3バケット全体をローカルに同期
aws s3 sync s3://bedrock-chat-docs-${ENV}-${TENANT_ID}/ ./s3-backup/
```

### Step 2: 新環境のデプロイ

```bash
# 2-1. developブランチに切り替え
git checkout develop
git pull

# 2-2. 依存関係のインストール
npm ci

# 2-3. CDKデプロイ
npx cdk deploy --all
```

### Step 3: データ変換・投入

```bash
# 3-1. 変換スクリプトの実行
npx ts-node scripts/transform-to-assistant.ts \
  --input bots-backup.json \
  --output assistants-import.json

# 3-2. S3ファイルのコピー（変換スクリプトが生成したマッピングファイルを使用）
npx ts-node scripts/copy-s3-files.ts \
  --mapping s3-mapping.json \
  --source-bucket bedrock-chat-docs-${OLD_ENV}-${TENANT_ID} \
  --target-bucket ${NEW_BUCKET}

# 3-3. Assistantテーブルへのデータ投入
npx ts-node scripts/import-assistants.ts \
  --input assistants-import.json \
  --table-name Assistant-${ENV}-tenant-${TENANT_ID}
```

### Step 4: 動作確認

```bash
# 4-1. Assistantテーブルのデータ確認
aws dynamodb scan \
  --table-name Assistant-${ENV}-tenant-${TENANT_ID} \
  --output json | jq '.Items | length'

# 4-2. syncStatusの確認（全てSUCCEEDEDになるまで待機）
aws dynamodb scan \
  --table-name Assistant-${ENV}-tenant-${TENANT_ID} \
  --projection-expression "assistantId, syncStatus" \
  --output json | jq '.Items'
```

## 6. 注意事項・リスク

### 6.1 Cognitoユーザープール

- 同一のCognitoユーザープールを継続使用する場合、userIdのマッピングは不要
- 異なるユーザープールを使用する場合、userIdのマッピングテーブルが必要

### 6.2 テナント構成

- シングルテナント環境の場合、テナントIDは固定値を使用
- マルチテナント環境の場合、テナントごとにテーブル・バケットが分離されていることを確認

### 6.3 ロールバック計画

- 移行前のBotTableV3とS3バケットは削除せず、一定期間保持することを推奨
- 問題発生時は旧環境に切り戻し可能な状態を維持

### 6.4 Knowledge Base IDの再作成

- v0.5.3の`BedrockKnowledgeBase.knowledge_base_id`は環境固有のため、移行後は自動的に再作成される
- 旧Knowledge Base IDは参照しない

## 7. 確認事項（移行実施前に確認）

移行スクリプトの詳細設計を進める前に、以下を確認する必要があります：

| 確認項目 | 確認内容 | 影響 |
|---------|---------|------|
| ボット数の規模 | 数個〜数十個 or 数百以上 | スクリプトの複雑さ |
| Cognitoユーザープール | 同一プール継続 or 新規作成 | userIdマッピングの要否 |
| テナント構成 | シングル or マルチ | テーブル・バケット名の決定 |
| modelIdのデフォルト | 使用するモデルID | 変換時のデフォルト値 |
