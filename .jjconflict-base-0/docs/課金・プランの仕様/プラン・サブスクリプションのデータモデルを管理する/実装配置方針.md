# 実装配置方針

## 概要

このドキュメントでは、Database Per Tenantsパターンを採用しているシステムにおいて、プラン・サブスクリプションのデータモデルを管理する責務をどのように実装するかを説明します。

特に重要なのは、「すべてのテナントで共通に使えるもの」と「各テナント専用に作るもの」を正しく分離することです。

---

## Database Per Tenantsパターンとは

### 基本的な考え方

Database Per Tenantsパターンとは、各テナント（システムを利用する組織や企業）が独立したデータベースを持つ設計のことです。

例えば、このシステムを3つの会社（A社、B社、C社）が使っている場合：
- A社専用のRDSインスタンスが1つ
- B社専用のRDSインスタンスが1つ
- C社専用のRDSインスタンスが1つ

このように、会社ごとに完全に独立したデータベースが存在します。

### なぜこの方式を採用するのか

この方式には以下のメリットがあります：

1. **データの完全な分離**: A社のデータとB社のデータが物理的に別のデータベースに保存されるため、セキュリティが高まります
2. **柔軟な運用**: 特定のテナントだけデータベースをアップグレードしたり、メンテナンスしたりできます
3. **障害の影響範囲が限定される**: A社のデータベースに問題が起きても、B社とC社には影響しません

---

## 3つの層の整理

プラン・サブスクリプション機能を実装する際、以下の3つの層を明確に区別する必要があります：

### 1. RDSインスタンス（テナント専用リソース）

**何を指すか**：
- 実際にデータを保存するデータベースサーバーそのものです
- テナントごとに独立したRDSインスタンスが作成されます

**どこに配置するか**：
- テナント専用スタックに含めます
- 既存の`TenantDynamoDBStack`と同様に、`TenantRDSStack`のような形で実装します

**具体例**：
- A社がシステムを利用し始めると、A社専用のRDSインスタンスがAWSに作成されます
- そのRDSインスタンスには、A社のプラン情報、サブスクリプション情報、ユーザプラン適用情報が保存されます
- B社、C社もそれぞれ独自のRDSインスタンスを持ちます

### 2. Repositoryクラス（共通コード）

**何を指すか**：
- データベースにアクセスするためのコード（プログラム）です
- 例えば、「プラン情報を取得する」「サブスクリプション情報を保存する」といった処理を行うクラスです

**どこに配置するか**：
- テナント専用リソースではなく、システム全体で共通に使えるコードとして配置します
- `packages/cdk/lambda/repositories/`のようなディレクトリに配置します
- この責務の外側に存在するものとして扱います

**なぜ共通にするのか**：
- すべてのテナントで同じロジックでデータにアクセスするため、コードを重複させる必要がありません
- 1箇所でバグを修正すれば、すべてのテナントに反映されます
- Lambda関数から呼び出されるライブラリのように機能します

**具体例**：
- `PlanRepository`クラス：プランテーブルにアクセスするためのクラス
- `SubscriptionRepository`クラス：サブスクリプションテーブルにアクセスするためのクラス
- `UserPlanApplicationRepository`クラス：ユーザプラン適用テーブルにアクセスするためのクラス

これらのクラスは、A社のデータにアクセスする時もB社のデータにアクセスする時も同じコードが使われます。違うのは、接続先のRDSインスタンスだけです。

### 3. スキーマ定義（要注意：2つに分けて考える）

スキーマ定義については、「スキーマ定義ファイル」と「スキーマ適用処理」を分けて考える必要があります。

#### 3-1. スキーマ定義ファイル（共通リソース）

**何を指すか**：
- データベースのテーブル構造を定義したファイルです
- SQLファイルや、マイグレーションスクリプトと呼ばれるものです
- 例：「プランテーブルを作成するSQL」「サブスクリプションテーブルにカラムを追加するSQL」

**どこに配置するか**：
- テナント専用リソースではなく、システム全体で共通に使えるファイルとして配置します
- `packages/cdk/database/migrations/`のようなディレクトリに配置します

**なぜ共通にするのか**：
- すべてのテナントで同じテーブル構造を持つべきだからです
- A社のデータベースにあるプランテーブルとB社のデータベースにあるプランテーブルは、まったく同じ構造でなければなりません
- もし構造が異なると、Repositoryクラスが正しく動作しなくなります
- スキーマのバージョン管理を一元化できます

**具体例**：
- `001_create_plans_table.sql`：プランテーブルを作成するSQL
- `002_create_subscriptions_table.sql`：サブスクリプションテーブルを作成するSQL
- `003_create_user_plan_applications_table.sql`：ユーザプラン適用テーブルを作成するSQL
- `004_add_campaign_fields_to_plans.sql`：プランテーブルにキャンペーン関連のカラムを追加するSQL

#### 3-2. スキーマ適用処理（テナント専用リソース）

**何を指すか**：
- 上記のスキーマ定義ファイル（SQLファイル）を実際にデータベースに適用する処理です
- 「マイグレーション実行」とも呼ばれます

**どこに配置するか**：
- テナント専用スタックに含めます
- `TenantRDSStack`の中で、Custom Resource（Lambda関数）として実装します

**なぜテナント専用にするのか**：
- 各テナントのRDSインスタンスに対して、独立してスキーマを適用する必要があるからです
- A社のRDSインスタンスにスキーマを適用する処理と、B社のRDSインスタンスにスキーマを適用する処理は、それぞれ独立して実行されます
- テナントごとに、どのマイグレーションが適用済みかを記録・管理する必要があります

**具体的な動き**：
1. A社がシステムを利用し始めると、A社専用の`TenantRDSStack`が作成されます
2. その中に含まれるCustom Resourceが、A社専用のRDSインスタンスに接続します
3. `packages/cdk/database/migrations/`に置かれたSQLファイルを順番に読み込みます
4. まだ適用されていないSQLファイルだけを、A社のRDSインスタンスに対して実行します
5. どのSQLファイルを適用したかを、A社のRDS内のマイグレーション管理テーブルに記録します

この処理はA社、B社、C社それぞれに対して独立して実行されます。

## なぜスキーマ定義とスキーマ適用を分けるのか

スキーマ定義ファイルを共通リソースとして管理し、スキーマ適用処理をテナント専用リソースとして管理することで、以下のメリットがあります：

### 1. すべてのテナントで一貫したスキーマ構造を保証できる

スキーマ定義ファイルが1箇所にまとまっているため、すべてのテナントが同じテーブル構造を持つことが保証されます。

悪い例（スキーマ定義もテナント専用にした場合）：
- A社のRDSには`plan_priority`カラムがあるが、B社のRDSにはない
- このような不整合が起きると、Repositoryクラスが正しく動作しません

良い例（スキーマ定義を共通にした場合）：
- すべてのテナントが同じスキーマ定義ファイルから作られる
- A社もB社もC社も、まったく同じテーブル構造を持つ

### 2. スキーマ変更時の影響範囲が明確

新しいカラムを追加したい時、スキーマ定義ファイルを1つ追加するだけで済みます。

例：プランテーブルに`discount_rate`カラムを追加したい場合
1. `005_add_discount_rate_to_plans.sql`を作成して、共通の`migrations/`ディレクトリに配置
2. 各テナントのスタックをデプロイする際、このSQLファイルが自動的に適用される
3. すべてのテナントに同じ変更が反映される

### 3. テナントごとの段階的なマイグレーションが可能

スキーマ適用処理がテナント専用リソースとして独立しているため、テナントごとに異なるタイミングでマイグレーションを実行できます。

例：
- 2025年1月1日：A社のスタックをデプロイ → A社のRDSに新しいスキーマが適用される
- 2025年1月5日：B社のスタックをデプロイ → B社のRDSに新しいスキーマが適用される
- 2025年1月10日：C社のスタックをデプロイ → C社のRDSに新しいスキーマが適用される

このように、テナントごとに段階的に展開できます。もしA社でトラブルが起きた場合、B社とC社のデプロイを延期することができます。

### 4. スキーマバージョンの監査が容易

どのテナントがどのバージョンのスキーマを使っているかを、簡単に確認できます。

例：
- A社のRDS内のマイグレーション管理テーブルを見ると、「001から005まで適用済み」と記録されている
- B社のRDS内のマイグレーション管理テーブルを見ると、「001から003まで適用済み」と記録されている
- つまり、B社はまだ004と005のマイグレーションを実行していないことがわかる

## 具体的なファイル配置

以下のように、ファイルを配置します：

### 共通リソース（すべてのテナントで共有）

```
packages/cdk/
├── database/
│   ├── migrations/
│   │   ├── 001_create_plans_table.sql
│   │   ├── 002_create_subscriptions_table.sql
│   │   ├── 003_create_user_plan_applications_table.sql
│   │   ├── 004_add_subscription_history_table.sql
│   │   └── 005_add_payment_history_table.sql
│   └── schema-version.json
└── lambda/
    └── repositories/
        ├── PlanRepository.ts
        ├── SubscriptionRepository.ts
        └── UserPlanApplicationRepository.ts
```

**配置場所の説明**：

1. **packages/cdk/database/migrations/**
   - スキーマ定義ファイル（SQLファイル）を配置します
   - ファイル名の先頭に番号をつけて、実行順序を明確にします
   - 一度適用したSQLファイルは、基本的に変更しません（新しいSQLファイルを追加します）

2. **packages/cdk/database/schema-version.json**
   - 現在のスキーマバージョンを記録します
   - どのマイグレーションファイルが最新かを管理します

3. **packages/cdk/lambda/repositories/**
   - Repositoryクラスを配置します
   - Lambda関数から呼び出されます

### テナント専用リソース（テナントごとに作成）

```
packages/cdk/
├── lambda/
│   └── database-migration/
│       ├── applyMigrations.ts
│       └── migrationRunner.ts
└── lib/
    ├── construct/
    │   └── tenant-rds.ts
    └── stacks/
        └── tenant/
            └── tenant-rds-stack.ts
```

**配置場所の説明**：

1. **packages/cdk/lambda/database-migration/**
   - マイグレーション実行用のLambda関数コードを配置します
   - `applyMigrations.ts`：Custom Resourceとして呼び出されるメインのハンドラー
   - `migrationRunner.ts`：実際にSQLファイルを読み込んで実行するロジック

2. **packages/cdk/lib/construct/tenant-rds.ts**
   - テナント専用RDSインスタンスを作成するConstructを定義します
   - VPC、サブネット、セキュリティグループの設定を含みます

3. **packages/cdk/lib/stacks/tenant/tenant-rds-stack.ts**
   - テナント専用のRDSスタックを定義します
   - `TenantRDSConstruct`を使ってRDSインスタンスを作成します
   - Custom Resourceを使って、マイグレーション実行Lambda関数を呼び出します

## マイグレーション戦略

### マイグレーションファイルの命名規則

マイグレーションファイルは、以下の命名規則に従います：

```
[連番]_[変更内容の説明].sql
```

例：
- `001_create_plans_table.sql`
- `002_create_subscriptions_table.sql`
- `003_add_campaign_fields_to_plans.sql`

**ルール**：
- 連番は3桁のゼロパディング（001、002、003...）
- 一度デプロイしたマイグレーションファイルは変更しない
- 新しい変更が必要な場合は、新しい番号のファイルを追加する

### マイグレーション管理テーブル

各テナントのRDSインスタンスには、`schema_migrations`という管理用テーブルを作成します。

**テーブル構造**：
- `version`：適用済みのマイグレーションファイルの番号（例：001、002、003）
- `applied_at`：そのマイグレーションを適用した日時

このテーブルを見ることで、どのマイグレーションがすでに適用されているかを判断できます。

### マイグレーション実行の流れ

1. **Custom Resourceの起動**
   - テナントスタックがデプロイされると、Custom Resource（Lambda関数）が起動します

2. **RDSへの接続**
   - Lambda関数が、テナント専用のRDSインスタンスに接続します
   - 接続情報（ホスト名、ユーザー名、パスワード）は、AWS Secrets Managerから取得します

3. **適用済みマイグレーションの確認**
   - `schema_migrations`テーブルを確認し、どのマイグレーションがすでに適用されているかを取得します

4. **未適用のマイグレーションファイルの検出**
   - `packages/cdk/database/migrations/`ディレクトリ内のSQLファイルをリストアップします
   - `schema_migrations`テーブルと比較し、まだ適用されていないファイルを特定します

5. **マイグレーションの実行**
   - 未適用のSQLファイルを、番号順に1つずつ実行します
   - 各SQLファイルの実行後、`schema_migrations`テーブルに記録します
   - もしエラーが発生したら、そこで処理を中断し、エラーを返します

6. **完了報告**
   - すべてのマイグレーションが成功したら、Custom Resourceに成功を報告します
   - CloudFormationスタックのデプロイが完了します

### ロールバック戦略

マイグレーションを元に戻したい場合の戦略：

1. **基本方針**：ロールバック用のSQLファイルは作成しません
2. **理由**：データベースの変更を自動的に元に戻すのは危険です（データ損失のリスク）
3. **対処方法**：問題が発生した場合は、新しいマイグレーションファイルを作成して修正します

例：
- `003_add_discount_rate_to_plans.sql`で`discount_rate`カラムを追加した
- 問題が発生したため、このカラムを削除したい
- この場合、`004_remove_discount_rate_from_plans.sql`を作成して対応します

## テナントスタックでの実装方法

### TenantRDSStackの実装イメージ

`TenantRDSStack`は、以下のような構成になります：

**含まれるリソース**：
1. RDSインスタンス（PostgreSQLまたはMySQL）
2. RDSのセキュリティグループ
3. RDSのサブネットグループ
4. マイグレーション実行用のCustom Resource
5. マイグレーション実行用のLambda関数

**処理の流れ**：
1. テナントがシステムに登録される
2. `TenantRDSStack`がデプロイされる
3. RDSインスタンスが作成される
4. Custom Resourceが起動し、マイグレーション実行Lambda関数を呼び出す
5. Lambda関数が、共通の`migrations/`ディレクトリからSQLファイルを読み込む
6. SQLファイルを順番に実行し、テーブルを作成する
7. スタックのデプロイが完了する

### 既存のテナントスタックとの関係

既存のシステムには、`TenantDynamoDBStack`などのテナント専用スタックがすでに存在します。

`TenantRDSStack`は、これらと並行して作成されます：

**テナント作成時に起動されるスタック**：
- `TenantVPCStack`：VPCとサブネットを作成
- `TenantDynamoDBStack`：DynamoDBテーブルを作成
- `TenantRDSStack`：RDSインスタンスとスキーマを作成（新規追加）
- `TenantOpenSearchStack`：OpenSearchドメインを作成
- その他のテナント専用スタック

`TenantRDSStack`は、`TenantVPCStack`が作成したVPCとサブネットを参照します。

### Repositoryクラスの呼び出し方

他の責務のLambda関数から、Repositoryクラスを以下のように呼び出します：

**例：サブスクリプション情報を保存する処理**

1. ユーザが「プランを購入したい」というリクエストを送る
2. API Gatewayが、「購入・変更・解約などの複数ステップの処理を統括する」責務のLambda関数を起動する
3. Lambda関数の中で、以下のコードを実行する：
   ```typescript
   import { SubscriptionRepository } from './repositories/SubscriptionRepository';

   // テナントIDから、RDS接続情報を取得
   const rdsConfig = await getRdsConfigForTenant(tenantId);

   // Repositoryインスタンスを作成（テナント専用のRDSに接続）
   const subscriptionRepo = new SubscriptionRepository(rdsConfig);

   // サブスクリプション情報を保存
   await subscriptionRepo.create({
     userId: 'user_abc123',
     planId: 'plan_xyz789',
     platformType: 'stripe',
     platformSubscriptionId: 'sub_1234567890',
     // その他のフィールド...
   });
   ```

4. `SubscriptionRepository`が、指定されたテナントのRDSインスタンスに接続してデータを保存する

**ポイント**：
- Repositoryクラス自体は共通コード
- 接続先のRDSインスタンスだけが、テナントによって異なる
- Lambda関数は、どのテナントのデータにアクセスするかを意識する必要がある

## データベース接続の管理

### 接続情報の保存

各テナントのRDS接続情報は、AWS Secrets Managerに保存します。

**保存する情報**：
- ホスト名（RDSエンドポイント）
- ポート番号
- データベース名
- ユーザー名
- パスワード

**Secretの命名規則**：
```
/tenant/{tenantId}/rds/credentials
```

例：
- A社のRDS接続情報：`/tenant/tenant-a/rds/credentials`
- B社のRDS接続情報：`/tenant/tenant-b/rds/credentials`

### 接続プールの利用

Lambda関数からRDSに接続する際は、接続プールを使用します。

**なぜ接続プールが必要か**：
- Lambda関数は複数回呼び出されるため、毎回新しいデータベース接続を作成すると非効率です
- 接続の確立にはコストがかかります（数百ミリ秒）
- 接続を再利用することで、処理速度が向上します

**実装方法**：
- Node.jsの場合：`pg`パッケージの接続プール機能を使用
- Lambda関数のグローバルスコープに接続プールを保持
- Lambda実行環境が再利用される限り、接続プールも再利用される

### VPC設定

RDSはVPC内に配置されるため、Lambda関数もVPC内に配置する必要があります。

**設定内容**：
- Lambda関数を、RDSと同じVPCに配置
- Lambda関数に、RDSのセキュリティグループへのアクセスを許可
- Lambda関数からインターネットにアクセスする必要がある場合は、NATゲートウェイを設置

**注意点**：
- VPC内のLambda関数は、コールドスタートが遅くなる場合があります
- 必要に応じて、Lambda関数のメモリサイズを増やすことで改善できます

## まとめ

プラン・サブスクリプションのデータモデルを管理する責務は、以下のように実装します：

### テナント専用リソースとして実装するもの

1. **RDSインスタンス**
   - 各テナントが独立したデータベースを持つ
   - `TenantRDSStack`として実装

2. **スキーマ適用処理**
   - 各テナントのRDSに対してマイグレーションを実行
   - Custom Resource（Lambda関数）として実装
   - `TenantRDSStack`に含める

### 共通リソースとして実装するもの

1. **スキーマ定義ファイル**
   - すべてのテナントで同じテーブル構造を保証
   - `packages/cdk/database/migrations/`に配置

2. **Repositoryクラス**
   - データベースアクセスのための共通コード
   - `packages/cdk/lambda/repositories/`に配置
   - この責務の外側に存在

### この設計のメリット

1. **一貫性の保証**：すべてのテナントが同じスキーマ構造を持つ
2. **保守性の向上**：スキーマ変更やバグ修正を1箇所で管理できる
3. **柔軟な運用**：テナントごとに異なるタイミングでマイグレーションを実行できる
4. **監査の容易さ**：どのテナントがどのバージョンのスキーマを使っているか追跡できる
5. **セキュリティ**：テナント間でデータが完全に分離される

この方針に従って実装することで、Database Per Tenantsパターンのメリットを最大限に活かしながら、保守性の高いシステムを構築できます。
