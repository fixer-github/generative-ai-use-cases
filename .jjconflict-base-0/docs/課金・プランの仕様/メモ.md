このシステムには、現在すでにOpenFGAによる認可の仕組みが実装されている
これを前提として、ToC向けのプラン・課金の仕組みを実装する必要がある
ToC用に展開されたテナント内では、個別のユーザがプランの契約および課金を行うことができる
プランとして、例えば下記のようなものが考えられる

```md
- Freeプラン
  モデルAが一日10回まで利用可能
  あと、機能Aと機能Bが使える

- Standardプラン
  モデルAとモデルBへの無制限アクセスが可能
  モデルCに対し、一ヶ月400回までの利用が可能
  あと、機能Aと機能B、そして機能Cも使える
```

このシステムは、現在Webアプリとして実装されているが、ネイティブアプリで展開することも計画されている
そのため、課金基盤としては、Stripe Billing, Apple・GooglePlayアプリ内課金の三つ全てに対応できるような仕組みにしている必要がある
ユーザに対し、プランが適用されるパターンは下記のようなものが考えられる

```md
- デフォルトのプランとして、新規登録されたユーザに対し自動で適用されるパターン（Freeプランなど）
- Stripeなどの課金プラットフォームによるサブスクリプション契約によって適用されるパターン
- 管理者による管理ページ上での操作により、特定のユーザに対して手動で適用されるパターン（例外的な処置として実施する可能性あり）
- トライアルやキャンペーンとして、期限付きでプランに加入できるパターン
```

このように、必ずしもユーザには課金プラットフォーム経由でプランが適用されるとは限らない

プランのオプションの中には、回数制限などが設けられているパターンも存在する
OpenFGA単体では、この要件に応えることが難しいため、利用回数のカウントをするような機構や、カウント数を保持するものがある必要がある

全体の構成を考える
全体の構成としては、

- ユーザの権限管理に責務を持つサービス
  - 含むもの
    - OpenFGA
    - +回数制限による制約を管理するために必要なもの - DynamoDB(利用回数やその他の情報を保持) - Lambda関数？
      カウントを追加する処理や、上限との比較を行い、判定結果を返す処理
      一日（一ヶ月）〇回利用可能というオプションの場合、決められたタイミングでカウントをリセットする処理などが必要
  - 外から何が見えるか
    - 認可チェックができるエンドポイント
      - 一旦はOpenFGAのエンドポイントをそのまま使う
      - +αとして、回数制限の観点での判定が行えるエンドポイントを追加で実装
    - カウントを+1, -1するエンドポイント
    - カウントを取得するエンドポイント
    - ユーザに対して権利を付与するエンドポイント
      例: このユーザは機能Aと機能Bに対する無制限アクセスと、モデルAへの一日〇〇回のアクセスの権利が適用される。この付与にはこのIdが割り当てられる。
    - 権利を無効化するエンドポイント
      例: このIdが割り当てられた権利の付与は剥奪する
  - 概念の説明
    - 特定ユーザの持つ権利を管理するという責務に集中するサービス
    - 「プラン」という概念は持たない。このサービスの外の概念
    - このサービスへ問い合わせるものは、後述の「ユーザのプランを管理するサービス」の他にも存在しうる
      - 「プラン」という概念はToC向けに展開される場合のみ登場するもので、例えば、ToB向けに提供する場合は、プランという概念を経由しない形で、別の形でユーザへ権限が付与されることになる。
    - いつまで有効であるかという概念も持たない。期限の概念は外部でもつことが前提。
- ユーザのプランを管理するサービス
  - 概念の説明
    - ユーザが所属しているプランを管理することに責務を集中させるサービス
    - 「ユーザの権限管理に責務を持つサービス」へ依存する
    - Stripe, Apple, GooglePlayアプリ内課金などの課金プラットフォームへも依存をする
      イベントの購読、問い合わせなどを行う
  - 外から何が見えるか
    - 指定のユーザの現在のプランを取得するエンドポイント
    - 指定のユーザのプランを変更するエンドポイント
    - 指定のユーザのプランの期限を延長するエンドポイント
    - 購入情報に基づいて
  - 中には何があるのか
    - それぞれの課金プラットフォームのイベントを購読し、イベントに基づいた処理を実行する
      - サブスクリプションの期限更新

  - 流れのイメージ
    - ユーザがStripeでの支払いでプランに加入した場合
      - ユーザがプランへ加入する操作を行う
      - 決済完了後、クライアントアプリから「このユーザがサブスクリプションによってこのプランへ加入しましたよ」というリクエストがこの「ユーザのプランを管理するサービス」へ渡される
      - このサービスは、まず課金プラットフォームのレシート検証APIを実行する。
      - 検証結果が問題なければ、「このユーザはこのサブスクリプションでこのプランをいつからいつまでの期間で契約しましたよ」という情報をDBに格納する。
    - プランの内容が更新された場合
      例えば、Standardプランの中身のオプションを変更したりした場合など

    必要な共通処理
    - このユーザの現在のサブスクリプションの状態

  - めも
    現在のユーザのプランと、現在のユーザのサブスクリプションは別
    サブスクは支払い
    プランは結果
