# 「Stripe/Apple/Googleの決済システムとのやり取りを一本化する」責務の実装イメージ

## この責務は何をするのか（概要）

この責務は、3つの異なる決済システム（Stripe、Apple App Store、Google Play Store）を一つの窓口で扱えるようにする「翻訳者」の役割を果たします。

例えるなら、英語、フランス語、中国語を話す3人とやり取りするときに、それぞれの言語を理解して通訳してくれる人のようなものです。システムの他の部分は「どの言語（決済システム）を使っているか」を気にせず、この通訳者に依頼すれば適切に処理してもらえます。

---

## この責務が必要な理由

このシステムはWebアプリとネイティブアプリの両方で展開される予定です。そのため、以下の3つの決済システムすべてに対応する必要があります：

- **Stripe Billing**: Webアプリでクレジットカード決済を行うときに使用
- **Apple App Store**: iOSアプリで課金を行うときに使用
- **Google Play Store**: Androidアプリで課金を行うときに使用

しかし、これらの決済システムは、それぞれ異なる方法で通信を行います：

- データの形式が異なる（Stripeは`price_id`、Appleは`product_id`など）
- 通知の方法が異なる（Webhookの仕組みやイベントの形式）
- 検証の方法が異なる（レシートの確認方法）

もしこの「翻訳者」がいないと、システムのあらゆる場所で「これはStripeなのか、Appleなのか、Googleなのか」を判断するコードを書かなければならず、複雑で間違いが起こりやすくなります。

この責務を設けることで、システムの他の部分は「購入を確認してください」と依頼するだけで済み、どの決済システムを使っているかを意識する必要がなくなります。

---

## 具体的に何を実装するのか（リソースと要素）

この責務は、以下の要素で構成されます。

### 1. Webhookエンドポイント（3つ）

**これは何か**
決済システムからの通知を受け取る窓口です。「ユーザーの支払いが成功しました」「支払いに失敗しました」「サブスクリプションがキャンセルされました」といった重要な出来事が起きたとき、決済システムがこのエンドポイントに通知を送ってきます。

**具体的な構成**
- Stripe用のWebhookエンドポイント
- Apple用のWebhookエンドポイント
- Google用のWebhookエンドポイント

それぞれ独立したエンドポイントとして実装されます。

**実装方法**
各エンドポイントは、API GatewayとLambda関数の組み合わせで実装されます。

**エンドポイントが行う処理**
1. 決済システムから通知を受け取る
2. 通知が本物かどうかを署名検証で確認する（なりすましを防ぐため）
3. 同じ通知を二重に処理しないよう、イベントIDで重複をチェックする
4. 通知の内容をログに記録する
5. 検証が完了したら、EventBridge（イベントバス）に通知を転送する

### 2. レシート検証処理

**これは何か**
ユーザーが「私は〇〇プランを購入しました」と主張してきたとき、その購入が本物かどうかを決済システムに確認する処理です。

**なぜ必要か**
悪意のあるユーザーが「購入した」と嘘をつく可能性があるため、必ず決済システムに直接確認する必要があります。

**具体的な処理の流れ**
1. クライアントアプリから購入情報（レシート）を受け取る
2. どの決済システムを使っているか判断する
3. 該当する決済システムのAPIに「このレシートは本物ですか？」と問い合わせる
4. 決済システムから「本物です」または「偽物です」という回答を受け取る
5. 回答を呼び出し元に返す

**キャッシュとフォールバック機能**
ネットワークの問題などで決済システムに確認できない場合でも、サービスを止めないための仕組みです：

1. 検証が成功したら、その結果を一時的に保存（キャッシュ）する（有効期限付き）
2. 次回の検証でエラーが発生したら、まずキャッシュを確認する
3. キャッシュに有効な検証結果があれば、それを使って処理を継続する
4. キャッシュがない、または期限切れの場合は、少し待ってから再度検証を試みる
5. それでも失敗した場合は、「検証保留中」として管理者に通知する

### 3. 商品IDとプランIDの変換

**これは何か**
決済システムで使われる商品IDから、システム内部で使われるプランIDを特定する処理です。

**なぜ必要か**
決済システムでは、プランのことを「商品」として扱います。例えば：

- Stripeでは `price_abc123` という商品ID
- Appleでは `com.example.standard_plan` という商品ID
- Googleでは `standard_monthly_plan` という商品ID

これらはすべて、システム内部では「Standardプラン（プランID: plan_002）」として扱われます。

Webhookイベントで「`price_abc123`という商品が購入されました」という通知を受け取った時、それがどのプランなのかを特定する必要があります。

**どのように実現するか**
商品IDとプランIDの対応関係は、「プラン・サブスクリプションのデータモデル管理責務」が管理するプランテーブルに保存されています。プランテーブルには以下のカラムがあります：
- `plan_id`: システム内部のプランID
- `platform_type`: 課金プラットフォーム種別（stripe/apple/google）
- `platform_product_id`: プラットフォーム側の商品ID

この責務は、PlanRepositoryを使ってプランテーブルを検索し、商品IDからプランを特定します。

**検索の例**
```typescript
// Webhookイベントから商品IDを取得
const platformProductId = 'price_abc123';
const platformType = 'stripe';

// PlanRepositoryを使ってプランテーブルを検索
const plan = await planRepository.findByPlatformProductId(
  platformType,
  platformProductId
);

// plan.plan_id が 'plan_002' (Standardプラン) として取得できる
```

### 4. 決済操作の実行

**これは何か**
システムの他の部分から「このユーザーのプランを変更してください」「このサブスクリプションをキャンセルしてください」といった依頼を受けたときに、適切な決済システムのAPIを呼び出して実行する処理です。

**具体的な操作**
- Checkout Sessionの作成（Stripe）: 支払い画面を作成する
- サブスクリプションの変更API呼び出し: プランをアップグレード/ダウングレードする
- サブスクリプションのキャンセルAPI呼び出し: 解約処理を行う
- トランザクション情報の取得（Apple/Google）: 購入履歴を取得する

**処理の流れ**
1. 依頼を受け取る（例: 「ユーザーAのサブスクリプションをキャンセルしてください」）
2. ユーザーAがどの決済システムを使っているか確認する
3. 該当する決済システムのAPIを適切な形式で呼び出す
4. 結果を呼び出し元に返す

### 5. 請求書PDF取得処理

**これは何か**
ユーザーが「請求書をダウンロードしたい」と依頼したときに、決済システムから請求書のPDFや情報を取得する処理です。

**決済システムごとの違い**
- **Stripe**: 請求書PDFのURLを取得できる
- **Apple**: プラットフォーム側の請求情報へのリンクを返す
- **Google**: プラットフォーム側の請求情報へのリンクを返す

## マルチテナント環境での考慮事項

このシステムは「Database Per Tenantsパターン」でのマルチテナント対応を実現しています。つまり、各テナント（企業やサービス提供者）ごとに独立したデータベースを持ちます。

### Lambda関数の扱い（共通リソース）

Lambda関数は「状態を持たないリソース」として、すべてのテナントで共通のリソースとして管理されます。

**理由**
Lambda関数は処理を行うだけで、データを保存しません。どのテナントの処理でも同じコードで実行できるため、テナントごとに別々のLambda関数を作る必要はありません。

**ただし、テナント専用にする選択肢もある**
以下のような理由で、Lambda関数をテナント専用リソースに含める判断もあり得ます：

1. **Webhookエンドポイントの分離**: 各テナントが異なるStripe Billingアカウントを使用する場合、Webhookエンドポイントもテナント別に分けた方が管理しやすい可能性がある
2. **セキュリティの強化**: テナント間で完全に処理を分離したい場合

**現時点での推奨**: 共通リソースとして開始し、必要に応じてテナント専用に移行する

### データベース・キャッシュの扱い（テナント専用リソース）

DynamoDBやキャッシュは「状態を持つリソース」として、テナント専用リソースとして管理されます。

**テナント専用で保存されるデータ**
- Webhookイベントのログ
- イベントIDの記録（重複チェック用）
- 商品IDとプランIDのマッピング情報
- レシート検証結果のキャッシュ

**理由**
各テナントは独自の課金プラットフォーム連携設定を持ちます。例えば：

- テナントA: Stripe Billingアカウント「A」を使用
- テナントB: Stripe Billingアカウント「B」を使用

そのため、商品IDとプランIDのマッピングもテナントごとに異なります。データを混在させないために、テナントごとに独立したDynamoDBテーブルが必要です。

### Webhookエンドポイントの分離戦略（2つの選択肢）

#### 選択肢1: 共通のWebhookエンドポイントを使用

**構成**
- すべてのテナントが同じWebhookエンドポイントURLを使用
- エンドポイントは、リクエストのヘッダーやパスパラメータからテナントを識別
- 識別したテナント情報に基づいて、適切なテナント専用データベースにアクセス

**メリット**
- インフラがシンプルになる
- エンドポイントの管理が容易

**デメリット**
- テナント識別のロジックが必要
- 1つのエンドポイントに障害が発生すると、すべてのテナントに影響する

#### 選択肢2: テナント別のWebhookエンドポイントを使用

**構成**
- 各テナント専用のWebhookエンドポイントURLを作成
- テナントAは `https://api.example.com/webhook/stripe/tenant-a`
- テナントBは `https://api.example.com/webhook/stripe/tenant-b`

**メリット**
- テナント間の完全な分離が実現できる
- 障害の影響範囲を限定できる
- デバッグやログ確認が容易

**デメリット**
- エンドポイントの数が増える
- インフラの管理が複雑になる

**推奨**: 初期は選択肢1（共通エンドポイント）で開始し、テナント数が増えたら選択肢2への移行を検討

## データの保存方法

この責務で保存するデータと、その保存先を説明します。

### 1. Webhookイベントのログ

**保存する内容**
- イベントID（重複チェック用）
- イベントの種別（支払い成功、支払い失敗、キャンセルなど）
- イベント本体（決済システムから送られてきたデータ全体）
- 受信日時
- 処理ステータス（処理済み、処理中、エラーなど）

**保存先**
テナント専用のDynamoDBテーブル

**テーブル設計の例**
- パーティションキー: `event_id`（イベントの一意識別子）
- ソートキー: `received_at`（受信日時）
- TTL: 90日後に自動削除（古いログは自動的に消える）

### 2. 商品IDとプランIDの対応関係（参照）

商品IDとプランIDの対応関係は、この責務では保存しません。代わりに、「プラン・サブスクリプションのデータモデル管理責務」が管理するプランテーブルを参照します。

**プランテーブルの構造**（詳細は「プラン・サブスクリプションのデータモデル管理責務」を参照）
- `plan_id`: システム内部のプランID
- `platform_type`: 課金プラットフォーム種別（stripe/apple/google/internal）
- `platform_product_id`: プラットフォーム側の商品ID
- その他のプラン定義情報

プランテーブルには`platform_product_id`によるインデックスが設定されており、高速な検索が可能です。

**なぜこの責務では保存しないのか**
- 商品IDとプランIDの対応関係は「プラン定義」の一部であり、プラン管理の責務に属します
- データを重複して持つと、整合性の問題が発生するリスクがあります
- 単一の真実の情報源（Single Source of Truth）の原則に従います

### 3. レシート検証結果のキャッシュ

**保存する内容**
- レシート情報（ハッシュ化）
- 検証結果（成功/失敗）
- 検証日時
- サブスクリプション情報（有効期限など）

**保存先**
テナント専用のDynamoDBテーブル

**テーブル設計の例**
- パーティションキー: `receipt_hash`（レシートのハッシュ値）
- TTL: 24時間後に自動削除（キャッシュは短期間のみ有効）

## 他の責務とのやり取り

この責務がどのように他の責務と連携するかを説明します。

### 依存する責務（この責務が依頼する相手）

#### 1. 外部の決済システム（Stripe/Apple/Google）

**依頼する内容**
- Checkout Sessionの作成（Stripe）
- レシートの検証（すべて）
- サブスクリプション情報の取得（すべて）
- サブスクリプションの変更・キャンセル（すべて）
- 請求書情報の取得（主にStripe）

**依頼のタイミング**
- レシート検証処理が実行されたとき
- サブスクリプション変更の依頼を受けたとき
- 定期的な状態同期のとき

#### 2. データ記録の仕組み（DynamoDB）

**依頼する内容**
- Webhookイベントの保存
- イベントIDの記録（重複チェック用）
- レシート検証結果キャッシュの保存と取得

**依頼のタイミング**
- Webhookイベントを受信したとき
- レシート検証を実行したとき

#### 3. プラン・サブスクリプションのデータモデルを管理する（RDB - PlanRepository）

**依頼する内容**
- 商品IDからプランIDへの変換（プランテーブルの検索）
- プラットフォーム種別と商品IDを指定して、対応するプラン情報を取得

**依頼のタイミング**
- Webhookイベントを受信し、商品IDからプランを特定する必要があるとき
- レシート検証後、購入された商品に対応するプランを特定するとき

#### 4. Webhookイベントを受信層からビジネスロジック層へ配信する（EventBridge）

**依頼する内容**
- 署名検証と重複チェックが完了したWebhookイベントの配信

**依頼のタイミング**
- Webhookエンドポイントでイベントの検証が完了したとき

### この責務を利用する責務（この責務に依頼してくる相手）

この責務の設計原則により、この責務は「自分を呼び出す側」を知りません。しかし、理解のために主な利用者を説明します。

#### 1. 購入・変更・解約などの複数ステップの処理を統括する責務

**依頼される内容**
- 決済の開始（Checkout Session作成など）
- レシート検証
- サブスクリプションの変更
- サブスクリプションのキャンセル

#### 2. ユーザのサブスクリプション契約の状態を記録・管理する責務

**依頼される内容**
- 定期的なサブスクリプション状態の取得（同期処理）

#### 3. ユーザ向けセルフサービスインターフェースを提供する責務

**依頼される内容**
- 請求書PDFの取得

## まとめ

この責務は、3つの異なる決済システムとの複雑なやり取りを一手に引き受ける「翻訳者」です。

**主な役割**
1. Webhookエンドポイントで決済システムからの通知を受け取る
2. レシート検証で購入の正当性を確認する
3. 商品IDとプランIDの変換を行う
4. 決済システムへの操作を代行する

**マルチテナント対応**
- Lambda関数は共通リソース（すべてのテナントで共有）
- データベースとキャッシュはテナント専用リソース（テナントごとに分離）
- Webhookエンドポイントは、初期は共通、将来的にテナント別分離も検討

**利点**
- システムの他の部分は、どの決済システムを使っているかを意識する必要がない
- 決済システムの仕様変更があっても、この責務だけを修正すれば良い
- 新しい決済システムを追加する場合も、この責務に追加するだけで済む

この責務により、複雑な決済システムの違いを吸収し、システム全体をシンプルに保つことができます。
