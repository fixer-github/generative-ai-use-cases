# 目的-手段ツリーの記述ルール

## 基本原則

このドキュメントで採用するツリー構造は、「目的-手段の連鎖」を表現します。
各項目は、その親項目に対して「それを実現するために何が必要か？」という問いの答えになっている必要があります。

### 親子関係の定義

```
親項目：達成したいこと
└─ 子項目1：親を達成するために必要なこと
└─ 子項目2：親を達成するために必要なこと
└─ 子項目3：親を達成するために必要なこと
```

重要なのは、**階層の深さではなく、論理的な繋がり**です。
ある項目が具体的なアクションレベルに達したら、それ以上掘り下げる必要はありません。

## 記述時のチェックリスト

各項目を書く際、以下を確認してください：

### 1. 必要十分性の確認

**子項目を見て親に問う：**

- 「これらの子項目をすべて達成すれば、親項目は達成できるか？」
- 「他に必要なものは漏れていないか？」

**親項目を見て子に問う：**

- 「この子項目は、本当に親項目の達成に必要か？」
- 「別の親項目に属すべきではないか？」

### 2. 抽象度の適切性

**抽象→具体の飛躍をチェック：**

- 親と子の間で抽象度の差が大きすぎないか？
- 間に入るべき中間的な項目がないか？

### 3. 並列性の確認

**同じ階層の項目同士：**

- 同じレベルの抽象度になっているか？
- 重複や包含関係がないか？
- 順序は論理的か、または意味のある順序か？

## よくある問題と対処法

### ❌ 問題1：論理的な飛躍

```markdown
悪い例：

- サービスの品質を保つ
  - テストコードを書く
```

**問題点：** 「品質を保つ」ために必要なのはテストだけではない。また、「テストコードを書く」は具体的すぎて、中間の概念が欠落している。

```markdown
良い例：

- サービスの品質を保つ
  - 主要な機能が壊れないことを保証する
    - 自動テストで機能を検証する
      - テストコードを実装する
      - テストを継続的に実行する環境を構築する
      - テスト失敗時の対応フローを確立する
  - パフォーマンスの劣化を防ぐ
    - （パフォーマンス関連の項目）
  - セキュリティを維持する
    - （セキュリティ関連の項目）
```

### ❌ 問題2：不完全な分解

```markdown
悪い例：

- ユーザーに安心してお金を払ってもらえるようにする
  - サブスクリプションをわかりやすく設計する
```

**問題点：** 「安心して払ってもらう」ために必要なのは「わかりやすさ」だけではない。

```markdown
良い例：

- ユーザーに安心してお金を払ってもらえるようにする
  - 何にいくら払うのかを明確にする
    - （料金の透明性に関する項目）
  - 決済が安全に処理されることを保証する
    - （決済の安全性に関する項目）
  - 課金状況をユーザーが把握できるようにする
    - （請求書・履歴に関する項目）
  - 解約・返金の手続きを明確にする
    - （解約フローに関する項目）
```

### ❌ 問題3：抽象度のバラつき

```markdown
悪い例：

- データを安全に扱う
  - 機密情報を保護する
  - APIキーを環境変数で管理する ← 具体的すぎる
  - 権限を適切に管理する
```

**問題点：** 「APIキーを環境変数で管理する」だけが具体的なアクションレベルになっている。

```markdown
良い例：

- データを安全に扱う
  - 機密情報を保護する
    - データを暗号化して保存する
    - シークレット情報を安全に管理する
      - APIキーやパスワードを環境変数で管理する
      - シークレット情報をコードに直接書かない
  - アクセス権限を適切に管理する
    - （権限管理に関する項目）
```

### ❌ 問題4：因果関係の誤り

```markdown
悪い例：

- テストを自動で実行する
  - プルリクエストを作成したときに実行する
  - 本番環境にデプロイする前に実行する
```

**問題点：** これらは「自動実行のタイミング」であり、「自動実行を実現するために必要なこと」ではない。

```markdown
良い例：

- テストを自動で実行する
  - CI/CDパイプラインを構築する
    - プルリクエスト作成時に実行されるようにする
    - デプロイ前に実行されるようにする
  - テスト実行環境を用意する
    - （環境に関する項目）
  - テスト失敗時の通知を設定する
    - （通知に関する項目）
```

## 記述の流れ

1. **最上位の目的を明確にする**
   - 「何を実現したいのか」を1文で表現する

2. **「そのために何が必要？」と問う**
   - 目的を達成するための必要要素を列挙する
   - 漏れがないか、論理的に網羅されているか確認する

3. **各項目について繰り返す**
   - 各子項目に対して、さらに「そのために何が必要？」と問う
   - 具体的なアクションに到達するまで繰り返す

4. **具体的なアクションで終える**
   - 「〜を実装する」「〜を決める」「〜を用意する」など
   - これ以上分解する必要がないレベルまで到達したら終了

5. **全体を見直す**
   - 親子関係が論理的に繋がっているか確認
   - 抽象度が適切か確認
   - 漏れや重複がないか確認

## 表現のガイドライン

### 項目名の書き方

- **目的・状態を表す場合：** 「〜できるようにする」「〜を保つ」「〜を実現する」
- **手段・方法を表す場合：** 「〜を行う」「〜を管理する」「〜を提供する」
- **具体的なアクション：** 「〜を実装する」「〜を決める」「〜を用意する」「〜を設定する」

### 推奨される表現

- ✅ ユーザーが安心できるようにする
- ✅ テストを自動で実行する仕組みを作る
- ✅ 解約手続きを明確にする
- ✅ エラー発生時の通知設定を行う
- ✅ 各プランの機能比較表を用意する

### 避けるべき表現

- ❌ よくする（何をどうよくするのか不明確）
- ❌ 整える（何をどう整えるのか不明確）
- ❌ 対応する（何に対してどう対応するのか不明確）

## まとめ

このルールの本質は、**「なぜそれが必要なのか」が常に明確である**ことです。

どの項目を見ても：

- 親項目を見れば「なぜこれが必要なのか」が分かる
- 子項目を見れば「これを実現するために何をすべきか」が分かる

この2つが成立していれば、論理的に一貫したツリー構造になっています。
