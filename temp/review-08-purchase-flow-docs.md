## 重大な問題（Critical）

### 1. トランザクション一貫性の保証が不十分

**問題箇所**: 実装イメージ.md、技術実装詳細.md全体

**詳細**:
- ドキュメントではロールバック処理について記載されているが、DynamoDBとLambda呼び出しを組み合わせた分散トランザクションにおいて、完全な一貫性を保証する仕組みが明確でない
- 特に以下のシナリオでの不整合リスクが高い:
  1. ステップ5（サブスクリプション記録）が成功したが、ステップ6（プラン適用）で失敗し、ロールバック処理自体も失敗した場合
  2. ロールバック処理の途中でLambda関数がタイムアウトした場合
  3. 複数のDynamoDBテーブルへの書き込みが部分的に成功した場合

**影響**:
- ユーザは決済が完了しているのにプランが適用されない、またはその逆の状態になる可能性
- データの不整合により、課金とサービス提供の不一致が発生
- 手動での復旧作業が頻繁に必要になる可能性

**推奨対応**:
1. **Sagaパターンまたは補償トランザクションの明示的な設計**を追加
   - 各ステップに対応する補償処理（Compensating Transaction）を明確に定義
   - ロールバック失敗時の検出とリカバリー手順を文書化
2. **べき等性の保証**を各ステップで実装
   - 同じリクエストが複数回実行されても安全であることを保証
   - リトライ時の重複実行を防ぐ仕組み（idempotency keyの使用など）
3. **最終的整合性の許容範囲**を明確化
   - どの程度の遅延や不整合を許容するかのビジネス判断を文書化
   - 不整合検出と自動修復のバッチ処理の設計を追加

### 2. 決済プラットフォームとの統合における重大な設計ギャップ

**問題箇所**: 実装イメージ.md 72-94行目、技術実装詳細.md 89-99行目（購入フロー）

**詳細**:
- 購入フローのステップ3「決済を開始してください」とステップ4「レシート検証」の間に設計ギャップがある
- Stripe、Apple、Googleでは決済フローが大きく異なる:
  - **Stripe**: Checkout Session作成 → クライアント側でリダイレクト → Webhook通知で完了確認
  - **Apple/Google**: クライアント側で決済完了 → レシートをサーバーに送信 → レシート検証
- 現在の設計では、Stripeの場合の「クライアント側リダイレクト→決済完了→Webhook通知」の非同期フローが考慮されていない

**影響**:
- Stripeでの購入フローが実装不可能、または設計が矛盾する
- 購入フロー統括Lambda関数が60秒のタイムアウト内に完了しない（Stripeの決済完了を待つ場合）
- クライアントとサーバー間の状態同期が不明瞭

**推奨対応**:
1. **プラットフォームごとの購入フロー分岐を明示的に設計**
   - **Stripe購入フロー**: Checkout Session作成で終了 → Webhook経由で後続処理
   - **Apple/Google購入フロー**: レシート検証から開始 → 同期的に後続処理
2. **購入フローの状態管理を追加**
   - `pending_payment`（決済待ち）、`payment_completed`（決済完了）、`subscription_active`（サブスク有効）などの中間状態を定義
   - クライアントが購入状態をポーリングまたはWebSocketで確認できる仕組み
3. **Webhook経由の購入完了処理を明確化**
   - Stripeの`checkout.session.completed`イベント受信時に、購入フローの後半（サブスク記録〜権限付与）を実行
   - WebhookイベントフローとPurchaseFlowの統合設計を明示

### 3. EventBridge統合における重複処理とイベント順序の問題

**問題箇所**: 技術実装詳細.md 679-770行目（EventBridge統合詳細）

**詳細**:
- Webhookイベントの重複検証は「決済システムとのやり取りを一本化する」責務で実施されるとあるが、EventBridge経由でWebhookイベント処理フロー統括Lambda関数が起動された後の重複チェックが不明
- 以下のシナリオで重複処理が発生するリスク:
  1. EventBridgeのリトライにより同じイベントが複数回配信される
  2. Stripeが同じWebhookイベントを複数回送信する（Stripe側のリトライ）
  3. Lambda関数がタイムアウトしたが、実際には処理が完了していた場合
- イベントの順序保証がない（例: `payment.succeeded`の前に`subscription.canceled`が処理される）

**影響**:
- 同じサブスクリプション更新が複数回適用され、有効期限が意図しない日時になる
- イベントの処理順序が逆転し、キャンセル後に更新処理が実行される
- フロー実行履歴テーブルに重複レコードが作成される

**推奨対応**:
1. **Webhookイベント処理フロー統括Lambda関数内での重複チェック実装**
   - イベントID（`eventId`）をDynamoDBに記録し、既存チェックを実施
   - TTL付きのイベント処理履歴テーブルを使用（例: 7日間保持）
2. **イベント順序制御の設計追加**
   - イベントのタイムスタンプ（`created`フィールド）を記録し、古いイベントを無視
   - サブスクリプションステータスの状態遷移ルールを明確化（例: `canceled`状態では更新処理をスキップ）
3. **べき等性の保証**
   - 有効期限延長処理が複数回実行されても安全であることを保証
   - 現在の有効期限と新しい有効期限を比較し、より新しい日時のみ適用

### 2. エラーハンドリングの分類基準が曖昧

**問題箇所**: 技術実装詳細.md 803-820行目（エラーハンドリングパターン）

**詳細**:
- 「一時的なエラー」「恒久的なエラー」「ビジネスロジックエラー」の分類基準は明確だが、実際の判断ロジックが不明
- 特に以下の判断が困難:
  1. 呼び出し先Lambda関数が返すビジネスロジックエラーが一時的か恒久的かの判断
  2. DynamoDBの`ProvisionedThroughputExceededException`（スロットリング）が発生した場合、一時的エラーとして扱うべきか
  3. 外部決済プラットフォームのAPI呼び出しエラーの分類（レート制限、サーバーエラー、不正なリクエストなど）

**推奨対応**:
1. エラーコードごとのリトライ可否判定表を作成
2. 呼び出し先Lambda関数が返すエラーレスポンスの標準化（`errorType: 'retryable' | 'permanent'`フィールドを含める）
3. リトライロジックの実装例をコードスニペットで追加

### 3. フロー実行時間とタイムアウトの設計

**問題箇所**: 技術実装詳細.md 115-117行目、194-196行目（各Lambda関数のタイムアウト設定）

**詳細**:
- 購入フロー、プラン変更フロー、解約フローのタイムアウトが60秒に設定されているが、根拠が不明
- 各ステップの想定実行時間の積算が60秒以内に収まるかの検証が必要
- 特にレシート検証やLambda関数間の呼び出しで遅延が発生した場合、タイムアウトのリスクがある

**推奨対応**:
1. 各ステップの想定実行時間を明記（例: レシート検証5秒、サブスク記録2秒、など）
2. 余裕を持ったタイムアウト設定（例: 90秒）への変更を検討
3. タイムアウト発生時の具体的なリカバリー手順を文書化

### 4. DynamoDBテーブル設計のパフォーマンス懸念

**問題箇所**: 技術実装詳細.md 600-648行目（フロー実行履歴テーブル）、649-677行目（ステップ実行履歴テーブル）

**詳細**:
- フロー実行履歴テーブルのGSI `status-startedAt-index`において、`status`をパーティションキーとすることで、特定のステータス（特に`failed`）にアクセスが集中するリスク
- パーティションキーのカーディナリティが低い（4種類: `in_progress`, `completed`, `failed`, `rolled_back`）ため、ホットパーティション問題が発生する可能性
- 大量のフロー実行が発生した場合、GSIへの書き込みスループットが不足する可能性

**推奨対応**:
1. GSI設計の見直し: `tenantId-status-index`（テナントIDとステータスの複合キー）への変更を検討
2. 失敗したフロー検索には別の方法を使用（例: CloudWatch Logs Insightsでのクエリ）
3. オンデマンドモードのスロットリング監視を運用手順に追加

## 総合評価

**要修正**

本ドキュメントは、購入・変更・解約フローの全体像を理解する上で非常に有用であり、実装イメージと技術詳細の両面から丁寧に記述されています。しかしながら、以下の重大な問題により、現状のままでは実装に進むべきではありません。

### 最優先で対応すべき項目（Critical）:

1. **トランザクション一貫性の保証メカニズムの明確化**
   - Sagaパターンまたは補償トランザクションの詳細設計を追加
   - ロールバック失敗時のリカバリー手順を文書化
   - べき等性保証の実装方針を明記

2. **決済プラットフォームごとの購入フロー分岐設計**
   - Stripe（非同期）とApple/Google（同期）の違いを明示的に設計
   - Webhook経由の購入完了処理フローを追加
   - クライアントとの状態同期メカニズムを設計

3. **EventBridge統合における重複処理とイベント順序制御**
   - Webhookイベント処理Lambda関数内での重複チェック実装を追加
   - イベント順序制御の設計を明確化
   - べき等性の保証メカニズムを文書化

これらの重大な問題が解決されない限り、実装時に設計の根本的な見直しが必要となり、大幅な手戻りが発生するリスクが高いです。特にトランザクション一貫性と決済プラットフォーム統合の問題は、システムの信頼性とビジネスへの影響が大きいため、最優先で対応すべきです。

### ポジティブな点:

1. **責務の分離が明確**: オーケストレーションレイヤーと各責務の分離が明確で、保守性が高い設計
2. **実行履歴の永続化**: トラブルシューティングと監査対応のための履歴記録設計が充実
3. **エラーハンドリングの考慮**: リトライ戦略とロールバック処理が設計されている
4. **運用監視の考慮**: CloudWatch MetricsとAlarmsを活用した監視設計が含まれている

1. 上記「重大な問題（Critical）」3項目の設計詳細化
