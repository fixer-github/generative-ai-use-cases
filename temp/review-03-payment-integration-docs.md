## 重大な問題（Critical）

### C1. 技術実装構成.md: EventBridgeのイベントソース名が統一されていない

**問題箇所**:
- 技術実装構成.md 93-107行目: EventBridgeのソースが `payment-gateway.webhook`
- 統括責務が必要とするイベント形式定義.md 42行目: EventBridgeのソースが `billing.payment-gateway`

**詳細**:
技術実装構成.mdでは、Stripe Webhookエンドポイントが送信するEventBridgeイベントのソースを `payment-gateway.webhook` としていますが、統括責務が必要とするイベント形式定義.mdでは `billing.payment-gateway` と定義されています。この不整合により、EventBridgeのルール設定とイベント送信が噛み合わず、イベントが正しくルーティングされない可能性があります。

**影響**:
- Webhookイベントが統括責務に届かない
- EventBridgeルールが正常に動作しない
- 実装時の混乱を招く

**推奨対応**:
`billing.payment-gateway` に統一することを推奨します（統括責務が必要とするイベント形式定義.mdの定義が、より階層的で明確なため）。技術実装構成.mdの以下の箇所を修正してください：
- 2.1.1節（93-107行目）のサンプルJSONの `source` フィールド
- 5.1節（707-734行目）のEventBridgeルール定義のeventPatternの `source` 配列

### C2. 技術実装構成.md: EventBridgeのdetail-typeが不整合

**問題箇所**:
- 技術実装構成.md 97行目: detail-typeが `StripeWebhookReceived`
- 統括責務が必要とするイベント形式定義.md 45行目: detail-typeがビジネスイベントタイプ（`payment.succeeded` など）

**詳細**:
技術実装構成.mdでは、Webhookエンドポイントが `StripeWebhookReceived` というプラットフォーム固有のdetail-typeを送信する設計になっていますが、統括責務が必要とするイベント形式定義.mdでは、Webhookエンドポイントでビジネスイベントへの正規化を行い、`payment.succeeded` などのビジネスイベントタイプをdetail-typeとして送信する設計になっています。

この不整合は、責務分離の観点から重大な設計上の問題です。統括責務が必要とするイベント形式定義.mdでは、「Payment Gateway Webhook層で、プラットフォーム固有イベントからビジネスイベントへの変換を実施」と明記されており、Webhookエンドポイントでの正規化が前提となっています。

**影響**:
- 統括責務がプラットフォーム固有のイベントタイプを処理する必要が生じ、決済システムへの依存が発生
- EventBridgeルールでビジネスイベントごとのフィルタリングができない
- 責務の境界が曖昧になる

**推奨対応**:
統括責務が必要とするイベント形式定義.mdの設計（Webhookエンドポイントでビジネスイベントへ正規化）を採用し、技術実装構成.mdを以下のように修正してください：
1. 2.1.1節のストライプWebhookエンドポイントの処理フローに、ビジネスイベントへのマッピング処理を追加
2. EventBridge送信時のdetail-typeをビジネスイベントタイプに変更
3. 同様の修正をAppleとGoogleのWebhookエンドポイントにも適用

### C3. Stripe_Billing_イベント形式仕様.md: Cloverバージョンの情報抽出パスと技術実装構成の不整合

**問題箇所**:
- Stripe_Billing_イベント形式仕様.md 100-128行目: Cloverバージョンでの情報抽出パス
- 技術実装構成.md 438-440行目: 旧バージョンのAPIを前提とした記述

**詳細**:
Stripe_Billing_イベント形式仕様.mdでは、Cloverバージョン（2025-10-29.clover）での重要な変更点を詳細に記述しています：
- Invoice.payment_intentフィールドの廃止
- Invoice Payments APIまたはinvoice.payments（インクルーダブル）の使用が必要
- 価格IDの取得パスが `lines.data[].pricing.price_details.price` に変更

しかし、技術実装構成.mdの統括責務が必要とするイベント形式定義の情報抽出ロジック（5.1節）では、これらの変更が反映されておらず、旧バージョンのAPIを前提とした記述になっています：
```typescript
// invoice内のline itemsからpriceIdを取得し、それをplanIdにマッピング
const priceId = event.data.object.lines.data[0].price.id;
```

**影響**:
- 実装時にCloverバージョンのAPIを使用すると、コードが動作しない
- 価格IDが正しく取得できず、プランIDへのマッピングが失敗する
- payment_intentの取得方法が不正確

**推奨対応**:
技術実装構成.mdの5.1節（Stripe情報抽出ロジック）を、Stripe_Billing_イベント形式仕様.mdの推奨パス（94-128行目）に合わせて更新してください：
- priceIdの取得パスを `lines.data[].pricing.price_details.price` に変更
- expirationDateの取得パスを `lines.data[].period.end` に明記
- payment_intentの取得方法をInvoice Payments API使用に変更

## 総合評価

**評価: 軽微な問題あり（修正推奨）**

### 評価理由

本ドキュメント群は、Stripe/Apple/Googleの3つの決済システムを統合するための包括的な設計資料として、以下の優れた点があります：

#### 優れている点

1. **責務分離が明確**: Payment Gateway層でプラットフォーム固有の処理を吸収し、統括責務がビジネスロジックに集中できる設計が明確に示されている

2. **Cloverバージョン対応**: Stripe Billingの最新API（2025-10-29.clover）への対応が詳細に記載されており、実装時の混乱を防げる

3. **マルチテナント設計が明確**: Lambda関数は共通リソース、データストアはテナント専用リソースという設計方針が一貫している

4. **イベント駆動アーキテクチャの正しい理解**: EventBridgeを使った疎結合な設計、冪等性の確保、順序保証なしの前提など、イベント駆動アーキテクチャのベストプラクティスが反映されている

5. **セキュリティへの配慮**: Webhook署名検証、Secrets Managerの使用、IAMポリシーの最小権限など、セキュリティ要件が適切に組み込まれている

6. **運用への配慮**: CloudWatch Logs/Metricsの設定、エラーハンドリング、リトライ戦略など、運用を見据えた設計になっている

#### 改善が必要な点

一方で、以下の重大な問題（Critical）があり、実装前に修正が必要です：

1. **EventBridgeのイベントソースとdetail-typeの不整合**（C1, C2）: 技術実装構成.mdと統括責務が必要とするイベント形式定義.mdの間で、EventBridgeイベントの形式が一致していません。これは実装時に重大な障害を引き起こします。

2. **Cloverバージョンの情報抽出パスの不整合**（C3）: Stripe_Billing_イベント形式仕様.mdで詳細に記載されているCloverバージョンの変更点が、技術実装構成.mdに反映されていません。

これらの問題は、ドキュメント間の整合性に関わるものであり、内容の質自体は高いです。修正作業は比較的容易であり、修正後は実装に十分に耐える品質のドキュメントになると評価します。

### 修正優先順位

1. **最優先（実装前必須）**: C1, C2, C3の修正
2. **高優先（実装開始前推奨）**: W1, W2, W3, W5の修正
3. **中優先（実装中に対応可能）**: W4, I1～I8の検討・対応
